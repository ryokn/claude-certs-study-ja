## SLIDE: 1.4 プログラムによる強制 vs プロンプト ★
| 判断軸 | プログラムによる強制（フック／ゲート） | プロンプト（指示・few-shot） |
| 保証 | 決定論的（必ず守られる） | 確率的（たまに破られる） |
| 使う場面 | 金銭・本人確認・コンプライアンス・不可逆操作 | 口調、判断基準、曖昧なケースの扱い |
| 例 | get_customer が検証済みIDを返すまで process_refund をブロック | エスカレーション基準＋few-shot |

めたん: プログラムによる強制と、プロンプトのガイダンス。どう使い分けますの？
ずんだもん: プログラムによる強制は、フックや前提条件のゲートなのだ。決定論的で、必ず守られるのだ。
ずんだもん: プロンプトは、指示やフューショットなのだ。確率的で、たまに破られるのだ。
めたん: 金銭の操作の前の本人確認は？
ずんだもん: プログラムなのだ。プロンプトの指示だけでは、失敗率がゼロにならないのだ。金銭、本人確認、コンプライアンス、取り消せない操作は、プログラムなのだ。
めたん: 口調や判断の基準、曖昧なケースの扱いは、プロンプトですわね。

## SLIDE: サンプル問題1とハンドオフ
- サンプル問題1：12%で本人確認をスキップ → **プログラムによる前提条件** が正解
- × プロンプト強化・few-shot：確率的で不十分
- × ルーティング分類器：「順序」ではなく「利用可否」の対策でズレ
- ○ 複数の懸案を含むリクエスト → **項目に分解し、共有コンテキストで並列に調査 → 統一された回答に統合**
- ○ 人間の担当者は **会話記録を見られない** 前提 → 顧客ID・根本原因・返金額・推奨アクションを **構造化サマリー** で渡す

めたん: サンプル問題1は、まさにここですわね。
ずんだもん: エージェントが、12パーセントのケースで本人確認を飛ばしてしまう問題なのだ。正解は、プログラムによる前提条件なのだ。
めたん: プロンプトを強化するとか、フューショットを足すのは？
ずんだもん: 確率的だから、不十分なのだ。ルーティングの分類器も、ズレているのだ。問題は「順序」なのに、分類器は「使えるかどうか」の対策だからなのだ。
めたん: 1つの問い合わせに、複数の用件が入っていたら？
ずんだもん: 個別の項目に分解して、共有コンテキストで並列に調べて、1つの回答に統合するのだ。
めたん: 人間に引き継ぐときは？
ずんだもん: 人間の担当者は、会話記録を見られない前提なのだ。だから、顧客{ID|アイディー}、根本原因、返金額、推奨アクションを、構造化したサマリーで渡すのだ。

## SLIDE: 1.5 フック：PreToolUse と PostToolUse ★
| | PreToolUse（呼び出しのインターセプト） | PostToolUse |
| タイミング | ツールが 実行される前 | ツールの結果を モデルが処理する前 |
| できること | ポリシー違反を ブロック、入力の変更 | 結果の 変換（正規化・トリミング） |
| 例 | $500超の返金をブロック → 人間へのエスカレーションへ誘導 | Unix時刻・ISO 8601・数値ステータスを統一 |
| ひっかけ | 正規化に使う（入力側。結果は変えられない） | 禁止操作を事後に取り消す（もう実行済み） |

めたん: 次は、フックですわ。星印付きですわね。
ずんだもん: {PreToolUse|プレ ツールユース}と{PostToolUse|ポスト ツールユース}の違いが、よく問われるのだ。
ずんだもん: {PreToolUse|プレ ツールユース}は、ツールが実行される前に、呼び出しをインターセプトするのだ。ポリシー違反をブロックしたり、入力を変えたりできるのだ。
めたん: たとえば？
ずんだもん: 500ドルを超える返金をブロックして、人間へのエスカレーションに誘導するのだ。
めたん: {PostToolUse|ポスト ツールユース}は？
ずんだもん: ツールの結果を、モデルが処理する前に変換するのだ。{Unix|ユニックス}のタイムスタンプ、{ISO|アイエスオー} 8601、数値のステータスコードがばらばらなら、ここで統一するのだ。
めたん: ひっかけは？
ずんだもん: 正規化に{PreToolUse|プレ ツールユース}を選ぶのは間違いなのだ。入力側だから、結果は変えられないのだ。
ずんだもん: 逆に、禁止操作を{PostToolUse|ポスト ツールユース}で事後に取り消すのも間違いなのだ。もう実行されてしまっているのだ。

## SLIDE: 現行 SDK の事実（Agent SDK hooks）
- 主なイベント：PreToolUse、PostToolUse、PostToolUseFailure、UserPromptSubmit、Stop、SubagentStart、SubagentStop、PreCompact、PermissionRequest、Notification ほか
- PreToolUse：**permissionDecision**（allow／deny／ask／defer）、permissionDecisionReason（**理由がモデルに伝わる**）、updatedInput
- 複数フックの判定が割れたら **deny が最優先**
- PostToolUse：additionalContext（追記）、updatedToolOutput（置換）
- matcher はツール名（"Write|Edit" など）。MCP ツールは **mcp__<server>__<tool>**
- Claude Code の設定ファイル版フック：**exit code 2 でブロック**

めたん: 今の{SDK|エスディーケー}では、どんなイベントがありますの？
ずんだもん: {PreToolUse|プレ ツールユース}、{PostToolUse|ポスト ツールユース}のほかに、失敗時の{PostToolUseFailure|ポスト ツールユース フェイリャー}、{UserPromptSubmit|ユーザー プロンプト サブミット}、{Stop|ストップ}、サブエージェントの開始と終了、{PreCompact|プレ コンパクト}などがあるのだ。
めたん: {PreToolUse|プレ ツールユース}では、何を返しますの？
ずんだもん: {permissionDecision|パーミッション ディシジョン}で、{allow|アロウ}、{deny|ディナイ}、{ask|アスク}、{defer|ディファー}を返すのだ。理由を書くと、それがモデルに伝わるのだ。入力を書き換えることもできるのだ。
めたん: フックが複数あって、判定が割れたら？
ずんだもん: {deny|ディナイ}が最優先なのだ。
ずんだもん: {matcher|マッチャー}はツール名で指定するのだ。{MCP|エムシーピー}ツールは、エムシーピー、サーバー名、ツール名を、アンダースコア2つでつないだ名前なのだ。
めたん: {Claude Code|クロードコード}の設定ファイルに書くフックは？
ずんだもん: 終了コード2で、ブロックなのだ。

## SLIDE: $500超の返金をブロックするフック
```
async def refund_guard(input_data, tool_use_id, context):
    amt = input_data["tool_input"].get("amount", 0)
    if amt > 500:
        return {"hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": "$500超は人間の承認が必要。escalate_to_human へ"}}
    return {}  # 許可（変更なし）

options = ClaudeAgentOptions(hooks={
    "PreToolUse": [HookMatcher(matcher="mcp__support__process_refund", hooks=[refund_guard])]})
```

ずんだもん: コードだと、こうなるのだ。返金額が500ドルを超えたら、{deny|ディナイ}を返すのだ。
めたん: 理由のところに、{escalate_to_human|エスカレート トゥ ヒューマン}へ、と書いてありますわね。
ずんだもん: そうなのだ。ブロックするだけでなく、代わりのワークフローに誘導するのだ。
めたん: 「プロンプトを大文字や太字で強調して、何度も繰り返す」というのは？
ずんだもん: それも確率的なのだ。確実に守らせたいなら、フックなのだ。

## SLIDE: 1.6 タスク分解の戦略
| | 固定の逐次パイプライン（プロンプトチェーン） | 動的で適応的な分解 |
| 向いている | 予測可能な多面的レビュー（ファイルごとの分析 → ファイル横断の統合） | オープンエンドな調査（レガシーに包括的なテストを追加） |
| 進め方 | 手順が事前に決まっている | 構造把握 → 影響の大きい領域特定 → 優先順位付き計画 → 発見に応じて適応 |

めたん: タスク分解の戦略は、2種類ありますのね。
ずんだもん: 固定の逐次パイプライン、プロンプトチェーンと、動的で適応的な分解なのだ。
めたん: どう使い分けますの？
ずんだもん: 予測できる多面的なレビューなら、固定のパイプラインなのだ。ファイルごとに分析して、最後にファイル横断で統合するのだ。
ずんだもん: オープンエンドな調査、たとえばレガシーのコードに包括的なテストを追加するなら、動的な分解なのだ。
ずんだもん: 構造を把握して、影響の大きい領域を見つけて、優先順位付きの計画を作り、発見に応じて計画を変えるのだ。
## SLIDE: 大規模コードレビューの分解（サンプル問題12）
- ○ **ファイル単位のローカル分析パス**＋**ファイル横断の統合パス**
- → 注意の分散（attention dilution）と矛盾した指摘を回避
- × 全部まとめて1回で
- × 上位モデルで1パス（注意の質は解決しない）
- × 3回やって多数決（本物のバグを抑制）

めたん: サンプル問題12は？
ずんだもん: 大きなプルリクエストのレビューなのだ。ファイル単位のローカル分析と、ファイル横断の統合パスに分けるのが正解なのだ。注意の分散を防げるのだ。
めたん: 全部まとめて1回、上位モデルで1パス、3回やって多数決は、不正解ですわね。

## SLIDE: 1.7 セッションの再開・フォーク・新規 ★
| 状況 | 選択 |
| 以前のコンテキストがおおむね有効、変更は一部 | 再開（--resume）＋変更ファイルを具体的に伝える |
| 以前のツール結果が大きく古くなった | 新規セッション＋構造化サマリーの注入 |
| 同じ分析から2つの戦略を比較したい | fork_session |

- --resume <session-name>：名前付きセッションの再開（--name／-n で名前を付ける）
- フォークは **会話履歴の分岐**。**ファイルシステムの分岐ではない**

めたん: 最後は、セッションの管理ですわ。
ずんだもん: 3つの選択肢の使い分けが、ポイントなのだ。
ずんだもん: 以前のコンテキストがおおむね有効で、変更が一部だけなら、再開なのだ。{--resume|ハイフン ハイフン リジューム}で名前付きセッションを再開して、変更されたファイルを具体的に伝えるのだ。
めたん: 以前のツール結果が、すっかり古くなっていたら？
ずんだもん: 古い結果を抱えたまま再開するより、新しいセッションに構造化サマリーを注入したほうが、信頼性が高いことがあるのだ。
めたん: 同じ分析から、2つの戦略を比べたいときは？
ずんだもん: {fork_session|フォーク セッション}なのだ。共通のベースラインから、独立した枝を作るのだ。
めたん: フォークすると、ファイルも分かれますの？
ずんだもん: 分かれないのだ。フォークは会話履歴の分岐で、ファイルシステムの分岐ではないのだ。ここ、ひっかけ注意なのだ。
