## SLIDE: 4.4 エラーフィードバック付きリトライ
- **元の文書＋失敗した抽出結果＋具体的な検証エラー** を渡して自己修正させる
- リトライが効く：**形式の不一致、構造的な出力エラー**
- リトライの限界：情報が **ソースに存在しない**（提供していない別添付にだけある等）
- → 何度やっても無駄 → **null・人間レビュー・資料の入手**
- **意味的な検証エラー**（合計不一致、フィールドの取り違え） vs **スキーマ構文エラー**（tool use で排除）

めたん: 抽出結果の検証に失敗したら、どうしますの？
ずんだもん: エラーフィードバック付きでリトライするのだ。元の文書と、失敗した抽出結果と、具体的な検証エラーを渡して、自分で直させるのだ。
めたん: リトライは、いつでも効きますの？
ずんだもん: 効くのは、形式の不一致や、構造的な出力のエラーなのだ。
ずんだもん: 効かないのは、情報がそもそもソースにない場合なのだ。たとえば、渡していない別の添付書類にだけ書いてある、とかなのだ。
めたん: 何度やっても、無いものは無いですわね。
ずんだもん: そうなのだ。そのときは、ヌルのまま人間のレビューに回すか、資料を入手するのだ。

## SLIDE: 自己修正の工夫
- **stated_total**（記載の合計）と **calculated_total**（明細から計算）を両方抽出
- → 不一致を **conflict_detected** ブール値で検出
- レビューの指摘に **detected_pattern** フィールド
- → 開発者が却下した指摘のパターンを **体系的に分析**（誤検知の改善）

めたん: 前回のスキーマにあった、合計が2つというのは？
ずんだもん: 書かれている合計と、明細から計算した合計を、両方抽出するのだ。食い違ったら、{conflict_detected|コンフリクト ディテクティッド}を{true|トゥルー}にするのだ。
めたん: 意味的なエラーを、見える形にするのですわね。
ずんだもん: その通りなのだ。それから、コードレビューの指摘に、{detected_pattern|ディテクティッド パターン}というフィールドを付けると、開発者が却下した指摘のパターンを、体系的に分析できるのだ。
ずんだもん: 誤検知の改善に役立つのだ。

## SLIDE: 模試から：2種類の検証失敗（オリジナル）
- 契約書の抽出結果を検証したら、2種類の失敗
- (a) 契約日が "2026/11/03" 形式。スキーマは ISO 8601（2026-11-03）
- (b) 契約番号が本文になく、**入力していない別添付にだけ** 記載
- → (a) は **元の文書・失敗結果・具体的な検証エラーを含めてリトライ**
- → (b) は **リトライしても解決しない**。null のまま人間レビューか、添付書類を入手

めたん: 模擬試験から1問ですわ。契約日の形式が違うのと、契約番号が別の添付にしかないのと、2種類の失敗。
ずんだもん: 日付の形式は、リトライで直るのだ。具体的な検証エラーを付けて、自己修正させるのだ。
めたん: 契約番号は？
ずんだもん: 何度リトライしても、無いものは出てこないのだ。ヌルのまま人間のレビューに回すか、添付書類を入手するのだ。

## SLIDE: 4.5 Message Batches API ★
| 項目 | 内容 |
| コスト | 50%削減（ガイド） |
| 処理時間 | 最大24時間の処理ウィンドウ、レイテンシSLAの保証なし（多くは1時間以内＝現行ドキュメント。当てにしない） |
| 対応付け | custom_id でリクエストとレスポンスを対応（結果の順序に依存しない） |
| 非対応 | 単一リクエスト内でのマルチターンのツール呼び出し（途中でツールを実行して結果を返せない） |
| 結果種別（現行） | succeeded ／ errored ／ canceled ／ expired。結果は29日間取得可。1バッチ最大100,000リクエストまたは256MB |

めたん: 次は、{Message Batches API|メッセージ バッチズ エーピーアイ}ですわ。
ずんだもん: コストは50パーセント削減なのだ。そのかわり、処理ウィンドウは最大24時間で、レイテンシの{SLA|エスエルエー}は保証されないのだ。
めたん: 多くは1時間以内に終わる、とも聞きますわ。
ずんだもん: 今のドキュメントにはそう書いてあるけど、当てにしてはいけないのだ。
めたん: 結果と、リクエストの対応は？
ずんだもん: {custom_id|カスタムアイディー}で対応付けるのだ。結果の順序には依存しないのだ。
ずんだもん: そして大事なのが、1つのリクエストの中で、マルチターンのツール呼び出しはできないことなのだ。途中でツールを実行して、結果を返すことができないのだ。
めたん: エージェントのループには、向きませんのね。

## SLIDE: バッチの使いどころ（サンプル問題11）
- ○ ブロッキングな **マージ前チェック → 同期 API**
- ○ 夜間レポート・週次監査・夜間テスト生成 → **バッチ**
- ○ SLA 計算：**送信間隔（最大待ち時間）＋24時間 ≦ SLA**
- 例：30時間 SLA → **4時間ごと** の送信なら最大28時間で満たす
- ○ 失敗は **custom_id で特定し、失敗分だけ** 修正して再送信（例：コンテキスト超過の文書をチャンク分割）
- ○ 大量処理の前に **サンプルセットでプロンプトを改良**

めたん: どんな処理を、バッチにしますの？
ずんだもん: サンプル問題11なのだ。マージ前のチェックは、開発者が待っているブロッキングな処理だから、同期の{API|エーピーアイ}なのだ。
ずんだもん: 夜間のレポート、週次の監査、夜間のテスト生成は、バッチなのだ。
めたん: {SLA|エスエルエー}がある場合は？
ずんだもん: 送信の間隔、つまり最大の待ち時間に、24時間を足して、{SLA|エスエルエー}以内に収まればいいのだ。
ずんだもん: たとえば30時間の{SLA|エスエルエー}なら、4時間ごとに送れば、最大28時間で満たせるのだ。
めたん: 一部が失敗したら？
ずんだもん: {custom_id|カスタムアイディー}で特定して、失敗した分だけ直して送り直すのだ。コンテキストを超えた文書なら、分割するのだ。
ずんだもん: それから、大量に流す前に、サンプルのセットでプロンプトを磨いておくと、初回の成功率が上がるのだ。

## SLIDE: バッチのひっかけ
| ひっかけ | 正しくは |
| 両方バッチにして、遅ければリアルタイムにフォールバック | 不要な複雑さ。マージ前は同期 |
| マージ前チェックもバッチで安く | SLA の保証がない。開発者を待たせる |
| バッチは結果の順序が保証されないから使えない | custom_id で解決する |
| バッチの中でツールを往復させる | 単一リクエスト内のマルチターンのツール呼び出しは非対応 |

めたん: ひっかけを確認しますわ。わたくしが間違いを言いますわね。

めたん: 両方バッチにして、遅かったらリアルタイムにフォールバックする。
ずんだもん: ブブー、なのだ。不要な複雑さなのだ。マージ前は、最初から同期なのだ。
めたん: バッチは結果の順序が保証されないから、使えない。
ずんだもん: {custom_id|カスタムアイディー}で解決するのだ。
めたん: バッチの中で、ツールを往復させる。
ずんだもん: できないのだ。マルチターンのツール呼び出しは、非対応なのだ。

## SLIDE: 模試から：30時間の SLA（オリジナル）
- 請求書が1日を通して随時到着。**到着から30時間以内** に結果を渡す社内 SLA
- コスト削減のため Message Batches API（最大24時間、SLA 保証なし）を使う
- 送信方針として最も適切なのは？
- → **4時間ごとにまとめてバッチ送信**（最大待ち4時間＋24時間＝28時間 ≦ 30時間）
- × 1日1回まとめて送信（最大待ち24時間＋24時間＝48時間で超過）

めたん: 模擬試験からも、{SLA|エスエルエー}の問題ですわ。到着から30時間以内。
ずんだもん: 4時間ごとにまとめて送るのだ。待ちが最大4時間、処理が最大24時間で、合計28時間なのだ。
めたん: 1日1回まとめて送るのは？
ずんだもん: 待ちが最大24時間で、処理と合わせて48時間。超えてしまうのだ。

## SLIDE: 4.6 マルチインスタンス・マルチパスのレビュー ★
- **セルフレビューの限界**：同じセッションは生成時の推論を保持し、自分の判断を疑いにくい
- **独立したレビューインスタンス**（生成時の推論コンテキストなし）は、セルフレビュー指示や **拡張思考より** 微妙な問題を見つけやすい
- **マルチパス**：ファイル単位のローカル分析パス＋ファイル横断のデータフロー統合パス
- 各指摘に確信度を自己申告させる **検証パス** → キャリブレーションされたルーティング
- ※ 確信度は **ラベル付きデータでキャリブレーションして使う** 前提。素の自己申告をそのまま信じるのは NG

めたん: 最後は、レビューのアーキテクチャですわ。
ずんだもん: まず、セルフレビューの限界なのだ。コードを書いたのと同じセッションは、そのときの推論を覚えていて、自分の判断を疑いにくいのだ。
めたん: では、どうしますの？
ずんだもん: 生成時の推論コンテキストを持たない、独立したレビューインスタンスを使うのだ。
ずんだもん: セルフレビューを指示したり、拡張思考を使ったりするより、微妙な問題を見つけやすいのだ。
めたん: 大きなプルリクエストでは？
ずんだもん: マルチパスなのだ。ファイル単位のローカル分析と、ファイル横断のデータフローを見る統合パスに分けるのだ。注意の分散や、矛盾した指摘を防げるのだ。
めたん: 確信度を出させる検証パス、というのもありますのね。
ずんだもん: あるのだ。ただし、確信度はラベル付きデータでキャリブレーションして使う前提なのだ。素の自己申告を、そのまま信じてはダメなのだ。
