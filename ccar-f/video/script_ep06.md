めたん: 四国めたんですわ。今回から分野4、プロンプトエンジニアリングと構造化出力ですわね。

## SLIDE: 4.1 明示的な基準で誤検知を減らす ★
- ○ 曖昧な指示より **明示的な基準**
- ×「コメントが正確か確認」→ ◯「**主張された動作が実際のコードの動作と矛盾する場合のみ** 指摘」
- ×「保守的に判断せよ」「確信度の高いものだけ報告せよ」→ **カテゴリ別の具体的基準より効かない**
- 誤検知の多いカテゴリが **正確なカテゴリへの信頼まで損なう**
- → 誤検知の多いカテゴリを **一時的に無効化** してプロンプトを改善
- 重大度（severity）は **レベルごとに具体的なコード例** を付けて定義

めたん: コードレビューの誤検知を減らすには、どうしますの？
ずんだもん: 曖昧な指示ではなく、明示的な基準を書くのだ。
ずんだもん: たとえば「コメントが正確か確認して」ではなく、「コメントで主張された動作が、実際のコードの動作と矛盾する場合だけ指摘して」と書くのだ。
めたん: 「保守的に判断して」や、「確信度の高いものだけ報告して」は？
ずんだもん: カテゴリ別の具体的な基準より、効かないのだ。ここはよく出るひっかけなのだ。
めたん: 特定のカテゴリだけ、誤検知がひどいときは？
ずんだもん: 誤検知の多いカテゴリがあると、正確なカテゴリの指摘まで信用されなくなるのだ。だから、そのカテゴリを一時的に無効にして、プロンプトを直すのだ。
ずんだもん: それから重大度は、レベルごとに具体的なコード例を付けて定義すると、分類が一貫するのだ。

## SLIDE: 模試から：ボットの指摘が無視される（オリジナル）
- 自動コードレビューの誤検知が多く、開発者がほぼ無視するように
- 特に「命名スタイル」「コメントの正確性」で誤検知が多発
- プロンプトには既に「**確信度の高い指摘のみを報告すること**」と書いてある
- → **報告すべき問題とスキップすべき問題を具体的なカテゴリ基準で定義**し、
- **誤検知の多いカテゴリは改善するまで一時的に無効化**

めたん: 模擬試験から1問ですわ。誤検知が多くて、開発者がボットの指摘を無視するようになった。確信度の高いものだけ、とはもう書いてある。
ずんだもん: 報告すべき問題と、スキップすべき問題を、具体的なカテゴリの基準で定義するのだ。
ずんだもん: バグやセキュリティは報告、軽い スタイルや局所的な慣習はスキップ、という具合なのだ。
めたん: 命名スタイルとコメントの正確性は？
ずんだもん: 改善できるまで、一時的に無効にするのだ。

## SLIDE: 4.2 few-shot プロンプティング
- 詳細な指示だけで一貫しないとき、**few-shot が最も効果的**（形式の一貫性）
- 曖昧なケースの扱いを示す。**なぜその行動を選び、妥当な代替を選ばなかったか** の推論を含めた例を **2〜4個**
- 出力形式（場所、問題、重大度、修正案）を例で示す
- 許容されるパターンと本物の問題を区別する例 → 誤検知を減らしつつ **新しいパターンへ汎化**
- 抽出：多様な文書構造（インライン引用 vs 参考文献リスト など）を例示 → **必須フィールドが空／null** になる問題を低減
- △ サンプル問題2では「few-shot 5〜8件」は **不正解**（根本原因はツール説明の不足）

めたん: 次は、フューショットですわ。
ずんだもん: 詳しい指示を書いても一貫しないとき、形式をそろえるには、フューショットが最も効果的なのだ。
めたん: 例は、いくつくらい？
ずんだもん: 2つから4つなのだ。そして、なぜその行動を選んだか、なぜ妥当な代わりの行動を選ばなかったか、という推論を含めるのだ。
めたん: 出力の形式も、例で示せますわね。
ずんだもん: そうなのだ。許容されるパターンと本物の問題を区別する例を見せると、新しいパターンにも汎化するのだ。
ずんだもん: 抽出タスクでは、インライン引用と参考文献リストのように、いろいろな文書構造の例を見せるのだ。必須フィールドが空になる問題が減るのだ。
めたん: では、困ったらいつもフューショット、でよろしいの？
ずんだもん: それが落とし穴なのだ。サンプル問題2では、フューショットを5から8件足すのは不正解なのだ。
ずんだもん: 根本原因は、ツールの説明が足りないことだったのだ。フューショットは万能ではないのだ。

## SLIDE: 4.3 tool_choice の4種類 ★
| tool_choice | 挙動 | 使う場面 |
| {"type":"auto"}（ツールありの既定） | ツールを呼ぶか、テキストで答えるかをモデルが決める | 通常の対話エージェント |
| {"type":"any"} | 何らかのツールを必ず呼ぶ（どれかは選べる） | 抽出スキーマが複数あり、文書種別が不明なとき |
| {"type":"tool","name":"extract_metadata"} | 指定したツールを必ず呼ぶ | 特定の抽出をエンリッチメントより先に確実に実行 |
| {"type":"none"}（ツールなしの既定） | ツールを使わない | — |

めたん: {tool_choice|ツールチョイス}は、星印付きですわね。
ずんだもん: 4種類あるのだ。{auto|オート}は、ツールがあるときの既定なのだ。ツールを呼ぶか、テキストで答えるかを、モデルが決めるのだ。
めたん: {any|エニー}は？
ずんだもん: 何かしらのツールを、必ず呼ぶのだ。どのツールかは、モデルが選べるのだ。抽出スキーマが複数あって、文書の種類が分からないときに、構造化出力を保証できるのだ。
めたん: ツール名を指定する形は？
ずんだもん: 指定したツールを、必ず呼ぶのだ。たとえば、メタデータの抽出を、エンリッチメントより先に確実に実行させたいときなのだ。
めたん: 後続のツールは、どうしますの？
ずんだもん: フォローアップのターンで処理するのだ。そして{none|ノン}は、ツールを使わない設定なのだ。

## SLIDE: tool_use＋スキーマの強みと限界
- 現行 API：any／tool のとき API はアシスタント応答をプリフィル → tool_use の前に **自然言語の説明は出ない**。手動の拡張思考とは併用不可
- **tool_use＋JSON スキーマ（strict）＝構文エラーを排除する最も信頼性の高い方法**
- ただし **意味的エラー** は防げない（明細の合計が総額と合わない、値が別フィールドに入る）
- スキーマ設計：文書に無いかもしれない情報は **任意（nullable）** に → 必須にすると **値を捏造** しがち
- 拡張可能なカテゴリは **enum ＋ "other" ＋ 詳細文字列**。曖昧なケースは **"unclear"**
- 書式がばらつくソースには、スキーマと **あわせて正規化ルールをプロンプトに**

めたん: ツールユースとスキーマを使うと、何がうれしいですの？
ずんだもん: ツールユースと{JSON|ジェイソン}スキーマ、{strict|ストリクト}モードは、構文エラーをなくす、最も信頼性の高い方法なのだ。
めたん: では、抽出のミスもなくなりますの？
ずんだもん: そこが落とし穴なのだ。意味的なエラーは防げないのだ。明細の合計が総額と合わないとか、値が別のフィールドに入るとかなのだ。
めたん: スキーマ設計のコツは？
ずんだもん: 文書に無いかもしれない情報は、任意、つまりヌルを許すのだ。必須にすると、モデルが値を捏造しがちなのだ。
ずんだもん: 増えていくかもしれないカテゴリは、列挙型に{other|アザー}を足して、詳細の文字列を付けるのだ。曖昧なときは{unclear|アンクリア}なのだ。
ずんだもん: 書式がばらばらなソースには、スキーマと一緒に、正規化のルールをプロンプトに書くのだ。

## SLIDE: 抽出ツールのスキーマ例
```
{"name": "extract_invoice", "strict": true,
 "description": "請求書PDFのテキストから請求情報を抽出する。記載がない項目は null。",
 "input_schema": {"type": "object", "additionalProperties": false,
  "properties": {
   "invoice_number": {"type": "string"}, "po_number": {"type": ["string", "null"]},
   "category": {"type": "string",
     "enum": ["software", "hardware", "maintenance", "other", "unclear"]},
   "category_detail": {"type": ["string", "null"]},
   "stated_total": {"type": "number"}, "calculated_total": {"type": "number"},
   "conflict_detected": {"type": "boolean"}},
  "required": ["invoice_number", "po_number", "category", "..."]}}
```

ずんだもん: 請求書の抽出ツールの例なのだ。{po_number|ピーオー ナンバー}は、文字列かヌルなのだ。発注番号がない請求書もあるからなのだ。
めたん: カテゴリには、{other|アザー}と{unclear|アンクリア}がありますわね。
ずんだもん: そうなのだ。{other|アザー}のときは、{category_detail|カテゴリー ディテール}に中身を書くのだ。
めたん: 合計が2つありますわ。
ずんだもん: 書かれている合計と、計算した合計なのだ。食い違いを見つけるための工夫で、次回くわしくやるのだ。

## SLIDE: strict スキーマの制約（現行ドキュメント）
- オブジェクトは **additionalProperties: false**
- 数値の minimum／maximum や文字列長の制約は **非対応**（SDK ヘルパーが変換）
- enum の大文字小文字は **保証されない**
- stop_reason が **refusal や max_tokens** のときはスキーマ不一致になり得る
- 複雑さの上限：任意プロパティは全体で **24個**、union 型は **16個** まで
- 「無いかもしれない」は **["string","null"]** か、**required から外した任意プロパティ** で表現

めたん: {strict|ストリクト}モードには、制約もありますのね。
ずんだもん: 今のドキュメントでは、オブジェクトは{additionalProperties|アディショナル プロパティーズ}を{false|フォールス}にするのだ。数値の最小、最大や、文字列の長さの制約は使えないのだ。
めたん: 列挙型の大文字と小文字は？
ずんだもん: 保証されないのだ。それから、{stop_reason|ストップリーズン}が{refusal|リフューザル}や{max_tokens|マックストークンズ}のときは、スキーマに合わないことがあるのだ。
めたん: 試験では、どこまで覚えればよろしいの？
ずんだもん: ポイントは、無いかもしれない値を、ヌル許容か任意プロパティで表すこと、なのだ。数の上限は、参考程度でいいのだ。

## SLIDE: まとめ（分野4 その1）
- 誤検知 → **具体的なカテゴリ基準**、高誤検知カテゴリの **一時停止**。「保守的に」「確信度の高いものだけ」は効かない
- few-shot は **推論つきで2〜4個**。形式の一貫性に効くが **万能ではない**
- tool_choice：auto＝テキストもあり／**any＝どれか必ず**／**tool＝指定ツール必ず**
- **tool_use＋スキーマ＝構文エラー排除**、でも **意味的エラーは残る**
- 無いかもしれない値は **nullable**、カテゴリは **enum＋"other"＋詳細**、曖昧は **"unclear"**
- 次回：分野4 その2　検証とリトライ、Message Batches API、マルチパスレビュー
