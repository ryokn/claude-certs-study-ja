## SLIDE: 5.1 長い会話で重要情報を保持する
- **段階的な要約のリスク**：数値・パーセンテージ・日付・顧客が述べた期待が曖昧になる
- **lost in the middle**：長い入力の冒頭と末尾はよく処理されるが、**中間を見落とす** ことがある
- ツール結果は関連性に見合わないトークンを消費（40以上のフィールドが返るが必要なのは5つ）
- 後続のリクエストでは **完全な会話履歴** を渡す
- 現行（存在だけ）：コンテキスト編集（ベータ）、コンパクション、/compact、プロンプトキャッシング

めたん: 長い会話では、何が問題になりますの？
ずんだもん: 古いやり取りを段階的に要約すると、数値や日付、顧客が言った期待が、曖昧になってしまうのだ。
めたん: ロスト イン ザ ミドル、というのは？
ずんだもん: 長い入力の、最初と最後はよく処理されるけど、真ん中を見落とすことがある、という現象なのだ。
ずんだもん: それから、ツールの結果は、トークンを食いすぎるのだ。注文の照会で40以上のフィールドが返ってきても、必要なのは5つだけ、ということがあるのだ。
めたん: コンテキスト編集やコンパクションは？
ずんだもん: 存在を知っていればいいレベルなのだ。プロンプトキャッシングの詳細も、範囲外なのだ。

## SLIDE: 5.1 の対策 ★
| 対策 | 内容 |
| ケースの事実情報（case facts）ブロック | 金額・日付・注文番号・ステータスを、要約される履歴の外に置き、毎回のプロンプトに含める |
| 構造化された課題データ層 | 複数案件のセッションで注文ID・金額・ステータスを別レイヤーに永続化 |
| ツール出力のトリミング | 蓄積する前に関連フィールドだけに（PostToolUse フックで実装しやすい） |
| 位置を考慮した配置 | 集約入力の冒頭に主要な発見の要約、詳細はセクション見出しで整理 |
| 上流エージェントの出力を構造化 | 冗長な文章ではなく、主要な事実・引用・関連性スコア・メタデータ |

めたん: 対策は？
ずんだもん: いちばん大事なのが、ケースの事実情報、{case facts|ケース ファクツ}ブロックなのだ。金額、日付、注文番号、ステータスを、要約される履歴の外に置いて、毎回のプロンプトに含めるのだ。
めたん: 模擬試験にもありましたわね。127ドル50セントを、11月20日までに返金すると約束したのに、要約で「対応中」になってしまった、と。
ずんだもん: まさにそれなのだ。ツールの出力は、貯まる前に必要なフィールドだけにトリミングするのだ。{PostToolUse|ポスト ツールユース}フックで実装しやすいのだ。
めたん: ロスト イン ザ ミドルへの対策は？
ずんだもん: 集めた入力の冒頭に、主要な発見の要約を置くのだ。詳細は、セクションの見出しで整理するのだ。
ずんだもん: 上流のエージェントには、冗長な文章ではなく、主要な事実や引用、メタデータを、構造化して返させるのだ。

## SLIDE: 5.2 エスカレーションの判断 ★
| 状況 | 正しい行動 |
| 顧客が人間を明示的に要求 | 直ちにエスカレーション（先に調査しない） |
| 不満を示すが問題は対応可能 | 不満を受け止め解決を申し出る。重ねて人間を希望したらエスカレーション |
| ポリシーが曖昧／何も定めていない（競合の価格マッチ要求など） | エスカレーション |
| 有意義な進展が得られない | エスカレーション |
| ツール結果が複数の顧客に一致 | ヒューリスティックで選ばず、追加の識別情報を尋ねる |

めたん: 次は、エスカレーションですわ。星印付きですわね。
ずんだもん: 顧客が、人間と話したいと明示的に求めたら、直ちにエスカレーションなのだ。先に調査したりしないのだ。
めたん: 住所変更のように、簡単に自動で処理できる用件でも？
ずんだもん: そうなのだ。明示的な要求には従うのだ。必要な情報は、構造化して引き継ぐのだ。
めたん: 不満そうなだけ、のときは？
ずんだもん: 不満を受け止めて、解決を申し出るのだ。それでも重ねて人間を希望したら、エスカレーションなのだ。
ずんだもん: ポリシーが曖昧だったり、何も定めていなかったりするときも、エスカレーションなのだ。
ずんだもん: 自社サイトの価格調整しか規定がないのに、競合の価格に合わせてと言われた、という例なのだ。
めたん: 検索で、同じ名前の顧客が複数見つかったら？
ずんだもん: 推測で選ばずに、追加の識別情報を尋ねるのだ。

## SLIDE: エスカレーションのひっかけ（サンプル問題3）
- ○ エスカレーション基準を **few-shot 付きでシステムプロンプトに明示**
- × **感情分析** ベース（ケースの複雑さと相関しない）
- × **自己申告の確信度** ベース（キャリブレーション不良）
- × 別の分類器モデル（プロンプト改善前の過剰設計）
- △ トリガーは「複雑なケース」ではなく **「ポリシーの例外／空白」**

めたん: サンプル問題3は、簡単な案件をエスカレーションして、難しい案件を自分で抱えてしまう、という問題でしたわね。
ずんだもん: 正解は、エスカレーションの基準を、フューショット付きでシステムプロンプトに明示することなのだ。
めたん: 感情分析で判断するのは？
ずんだもん: ダメなのだ。感情は、ケースの複雑さと関係ないのだ。自己申告の確信度も、キャリブレーションされていないから、信頼できないのだ。
めたん: 別の分類器を作るのは？
ずんだもん: プロンプトを改善する前にやるのは、過剰設計なのだ。そして、トリガーは「複雑なケース」ではなく、「ポリシーの例外や空白」なのだ。

## SLIDE: 5.3 エラー伝播（サンプル問題8）
- ○ **構造化されたエラーコンテキスト**：失敗の種類、試行したクエリ、部分的な結果、代替アプローチ
- → コーディネーターが「別クエリでリトライ／代替／部分結果で続行」を判断
- × 汎用ステータス（「検索を利用できません」）は情報を隠す
- × **エラーの握りつぶし**（空結果を成功として返す）と × **単一の失敗で全体を終了**、の **両方** がアンチパターン
- ○ 統合出力に **カバレッジの注記**（裏付けのある知見／情報源が使えず不足している領域）
```
{"status": "partial_failure", "failureType": "timeout",
 "attemptedQuery": "AI music generation market 2025",
 "partialResults": [...], "alternatives": ["業界団体レポートで検索"], "retriedLocally": 2}
```

めたん: マルチエージェントで、サブエージェントが失敗したら？
ずんだもん: 構造化されたエラーコンテキストを返すのだ。失敗の種類、試したクエリ、部分的な結果、代わりのアプローチなのだ。
めたん: それで、コーディネーターが次の手を決められますのね。
ずんだもん: そうなのだ。サンプル問題8なのだ。「検索を利用できません」みたいな汎用のステータスは、情報を隠してしまうのだ。
めたん: 空の結果を、成功として返すのは？
ずんだもん: 握りつぶしなのだ。逆に、1つの失敗でワークフロー全体を止めるのも、ダメなのだ。両方ともアンチパターンなのだ。
ずんだもん: そして、統合した出力には、どこが十分に裏付けられていて、どこが情報不足かという、カバレッジの注記を付けるのだ。

## SLIDE: 5.4 大規模なコードベース探索
- **コンテキストの劣化**：長時間セッションで回答が一貫しなくなり、具体的なクラスではなく「典型的なパターン」に言及しだす
- ○ **スクラッチパッドファイル** に主要な発見を記録し、以降の質問で参照
- ○ 特定の問い（「すべてのテストファイルを見つける」）を **サブエージェント** に委譲。メインは高レベルの調整
- ○ フェーズ間で **主要な発見を要約** し、次フェーズの初期コンテキストに注入
- ○ **クラッシュ復旧**：各エージェントが既知の場所に状態をエクスポート → 再開時に **マニフェスト** を読み込む
- ○ 冗長な調査出力で埋まったら **/compact**（焦点を指示できる /compact [instructions]）

めたん: 長時間のコードベース探索では、何が起きますの？
ずんだもん: コンテキストの劣化なのだ。回答が一貫しなくなって、前に見つけた具体的なクラスではなく、「一般的にはこういうパターンが多いです」と言い出すのだ。
めたん: 対策は？
ずんだもん: 主要な発見を、スクラッチパッドのファイルに記録して、あとの質問で参照するのだ。特定の問いは、サブエージェントに任せて、メインは全体の調整に専念するのだ。
めたん: 途中でクラッシュしたら？
ずんだもん: 各エージェントが、決まった場所に状態を書き出しておくのだ。再開するときに、コーディネーターがマニフェストを読み込んで、プロンプトに注入するのだ。
ずんだもん: 調査の出力でコンテキストが埋まったら、{/compact|スラッシュ コンパクト}なのだ。今は、要約の焦点も指示できるのだ。

## SLIDE: 5.5 人間のレビューと確信度のキャリブレーション
- 全体の精度（例：**97%**）が、**特定の文書種別やフィールドの低性能を覆い隠す** リスク
- ○ **層化無作為抽出（stratified random sampling）** で高確信度の抽出のエラー率も継続測定
- ○ **フィールド単位の確信度** を出させ、**ラベル付き検証セットでキャリブレーション** してしきい値を決める
- ○ レビューを減らす前に、**文書種別・フィールド別** に一貫した性能を確認
- ○ 確信度が低い／ソースが曖昧・矛盾 → 人間レビューへ（限られた工数に優先度）

めたん: 全体で97パーセントの精度が出たら、人間のレビューはやめてよろしいの？
ずんだもん: 油断は禁物なのだ。全体の数字が、特定の文書の種類や、特定のフィールドの低い性能を、覆い隠しているかもしれないのだ。
めたん: では、どう確かめますの？
ずんだもん: 文書の種類別、フィールド別に精度を分析するのだ。そして層化無作為抽出で、確信度が高い抽出も含めて、エラー率を測り続けるのだ。
ずんだもん: 確信度はフィールド単位で出させて、ラベル付きの検証セットでキャリブレーションしてから、しきい値を決めるのだ。
めたん: 確信度が低いものや、ソースが曖昧なものは？
ずんだもん: 人間のレビューに回すのだ。限られたレビュー担当者の時間を、優先度の高いところに使うのだ。

## SLIDE: 5.6 情報の出所（provenance）と不確実性 ★
- 要約で **claim と source の対応** が失われると出典が消える → サブエージェントに **主張と情報源の対応付け**（URL、文書名、抜粋）を出させ、統合でも保持
- **矛盾する統計**：恣意的に1つを選ばず、**出典付きで矛盾を注記**。整合のさせ方は **コーディネーターが判断**
- **時間的データ**：公開日・データ収集日を構造化出力に（時期の違いを矛盾と誤解しない）
- **確立された知見と異論のある知見** をセクションで区別
- 表現は内容に合わせる：**財務データ＝表、ニュース＝文章、技術的知見＝構造化リスト**

めたん: 最後は、情報の出所ですわ。
ずんだもん: 要約のステップで、主張と情報源の対応が失われると、出典が消えてしまうのだ。
ずんだもん: だから、サブエージェントに、主張と{URL|ユーアールエル}、文書名、抜粋の対応を出させて、統合でも保持するのだ。
めたん: 信頼できる2つの情報源が、違う数字を出していたら？
ずんだもん: 勝手に1つを選ばないのだ。両方を出典付きで残して、矛盾を注記するのだ。どう整合させるかは、コーディネーターが判断するのだ。
めたん: 模擬試験では、2023年のデータと2025年のデータでしたわね。
ずんだもん: そうなのだ。公開日やデータの収集時期を残しておけば、時期の違いを矛盾と誤解しないのだ。
ずんだもん: レポートでは、確立された知見と、異論のある知見をセクションで分けるのだ。
ずんだもん: 財務データは表、ニュースは文章、技術的な知見は構造化したリスト、と形も内容に合わせるのだ。

## SLIDE: まとめ（分野5）
- 長い会話は **case facts ブロック**、ツール出力は **トリミング**、冒頭に要約（lost in the middle）
- エスカレーション：**明示的要求は即**、不満だけなら解決を申し出る、**ポリシーの空白**、複数一致は **追加の識別情報**
- **感情分析・自己申告の確信度は NG**。基準は few-shot 付きで明示
- エラーは **構造化して伝播**。握りつぶし・全体停止はどちらも NG。カバレッジの注記
- 長時間探索：**スクラッチパッド**、**サブエージェント委譲**、**マニフェスト**、/compact
- 97%でも **種別・フィールド別**、**層化無作為抽出**、**キャリブレーション**。矛盾は **出典・日付つきで注記**
- 次回：シナリオ別ウォークスルー（6シナリオ）
