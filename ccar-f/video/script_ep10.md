## SLIDE: シナリオ1：カスタマーサポート解決エージェント
> 前提：Agent SDK、MCP ツール get_customer／lookup_order／process_refund／escalate_to_human、初回解決率80%以上
| 典型的な問い | 答えの方向 |
| 本人確認の前に返金・注文操作が走る | プログラムによる前提条件ゲート |
| $500超の返金 | PreToolUse でブロック＋エスカレーションへ誘導 |
| get_customer と lookup_order の取り違え | ツール説明の拡充 |
| 簡単な案件をエスカレーション、難しい案件を自力処理 | 明示的なエスカレーション基準＋few-shot |
| 同姓同名で複数一致 | 追加の識別情報を尋ねる |
| 長い会話で金額・日付が曖昧に | case facts ブロック |
| 返金ツールのエラーが一律 | 構造化エラー（カテゴリ・リトライ可否） |

めたん: シナリオ1は、カスタマーサポートですわ。
ずんだもん: 前提は{Agent SDK|エージェント エスディーケー}と、4つの{MCP|エムシーピー}ツールなのだ。目標は、初回解決率80パーセント以上と、エスカレーションの見極めなのだ。
めたん: 本人確認の前に、返金が走ってしまったら？
ずんだもん: プログラムによる前提条件のゲートなのだ。500ドル超の返金は、{PreToolUse|プレ ツールユース}でブロックなのだ。
めたん: ツールの取り違えは、説明の拡充。エスカレーションの見極めは、明示的な基準とフューショット。
ずんだもん: 同姓同名は追加の識別情報、長い会話はケース ファクツ、一律のエラーは構造化エラーなのだ。
ずんだもん: ほかにも、「人間と話したい」なら即エスカレーション、人間への引き継ぎは構造化ハンドオフ、が問われそうなのだ。

## SLIDE: シナリオ2：Claude Codeによるコード生成
> 前提：コード生成・リファクタリング・デバッグ・ドキュメント。カスタムスラッシュコマンド、CLAUDE.md、プランモード vs 直接実行
| 典型的な問い | 答えの方向 |
| チーム共有の /review | .claude/commands/ |
| 新メンバーに規約が効かない | ユーザーレベル → プロジェクトレベルへ、/memory で確認 |
| 散在するテストファイルの規約 | .claude/rules/ ＋ paths |
| 冗長なスキル出力 | context: fork |
| マイクロサービス化・45以上のファイル移行／単一ファイルの明確なバグ | プランモード／直接実行 |
| 変換仕様がぶれる | 入出力例2〜3個、テスト駆動、インタビューパターン |
| 長い探索でコンテキストが劣化 | Explore サブエージェント、/compact、スクラッチパッド |

めたん: シナリオ2は、{Claude Code|クロードコード}でのコード生成ですわ。
ずんだもん: 分野3が中心なのだ。チーム共有のレビューコマンドは、{.claude/commands|ドット クロード コマンズ}なのだ。
めたん: 新メンバーに規約が効かなければ、ユーザーレベルからプロジェクトレベルへ。散らばったテストファイルの規約は、ルールズとパス。
ずんだもん: 冗長なスキルの出力は、{context: fork|コンテキスト フォーク}なのだ。大規模な変更はプランモード、単一ファイルの明確なバグは直接実行なのだ。
めたん: 仕様がぶれるなら、入出力の例を2、3個。長い探索で劣化したら？
ずんだもん: {Explore|エクスプロア}サブエージェント、{/compact|スラッシュ コンパクト}、スクラッチパッドなのだ。

## SLIDE: シナリオ3：マルチエージェントリサーチシステム
> 前提：コーディネーター＋サブエージェント（ウェブ検索、文書分析、統合、レポート生成）。出典付きの包括的レポート
| 典型的な問い | 答えの方向 |
| レポートの網羅性不足 | コーディネーターの分解が狭すぎる |
| サブエージェントに情報が届かない | プロンプトで明示的に・構造化して渡す |
| 並列化 | 1応答で複数の Task 呼び出し |
| 委任されない | allowedTools に "Task"、description の明確化 |
| 検索サブエージェントのタイムアウト | 構造化エラーコンテキスト |
| 統合エージェントの事実確認の往復 | スコープ限定の verify_fact |
| 統計の矛盾・出典の消失・時期の違い | claim-source マッピング、日付、矛盾の注記 |

めたん: シナリオ3は、マルチエージェントのリサーチですわ。
ずんだもん: レポートの網羅性が足りなければ、コーディネーターの分解が狭すぎるのだ。サブエージェントに情報が届かなければ、プロンプトで明示的に、構造化して渡すのだ。
めたん: 並列にしたいなら、1つの応答で複数の{Task|タスク}。委任されないなら、{allowedTools|アラウドツールズ}と{description|ディスクリプション}。
ずんだもん: タイムアウトは構造化エラー、事実確認の往復は{verify_fact|ベリファイ ファクト}なのだ。
めたん: 統計の矛盾や、出典の消失は？
ずんだもん: 主張と出典の対応付け、日付、そして矛盾の注記なのだ。下流のコンテキストが小さいなら、上流に構造化データを返させるのだ。

## SLIDE: シナリオ4：Claudeによる開発者の生産性向上
> 前提：Agent SDK、組み込みツール（Read/Write/Bash/Grep/Glob）、MCP サーバー統合。不慣れなコードベースの探索、反復作業の自動化
| 典型的な問い | 答えの方向 |
| Grep vs Glob、Edit 失敗時、段階的なコード理解 | 内容＝Grep、名前＝Glob、Read＋Write、Grep → Read |
| MCP ツールより Grep を使ってしまう | MCP ツールの説明を充実 |
| チーム共有 MCP と個人 MCP、トークン管理 | .mcp.json＋${VAR}、~/.claude.json |
| 探索の繰り返しを減らす | MCP リソースでカタログ公開 |
| レガシーへのテスト追加 | 動的・適応的な分解 |
| セッションの再開／フォーク | resume＋変更ファイルの通知、fork_session |
| 異種データ形式 | PostToolUse で正規化 |

めたん: シナリオ4は、開発者の生産性向上ですわ。
ずんだもん: 組み込みツールの選び方が出るのだ。中身は{Grep|グレップ}、名前は{Glob|グロブ}、{Edit|エディット}が失敗したら{Read|リード}と{Write|ライト}なのだ。
めたん: {MCP|エムシーピー}ツールより{Grep|グレップ}を使ってしまうなら、{MCP|エムシーピー}ツールの説明を充実。
ずんだもん: チーム共有は{.mcp.json|ドット エムシーピー ドット ジェイソン}と環境変数、個人用は{~/.claude.json|ホーム ドット クロード ドット ジェイソン}なのだ。探索の繰り返しを減らすなら、{MCP|エムシーピー}リソースなのだ。
めたん: レガシーへのテスト追加は、動的な分解。データ形式がばらばらなら？
ずんだもん: {PostToolUse|ポスト ツールユース}で正規化なのだ。

## SLIDE: シナリオ5：継続的インテグレーションのための Claude Code
> 前提：CI/CD で自動コードレビュー、テストケース生成、PR へのフィードバック。実用的なフィードバックと誤検知の最小化
| 典型的な問い | 答えの方向 |
| ハングする | -p |
| インラインコメント用の構造化出力 | --output-format json ＋ --json-schema |
| 重複コメント | 以前の指摘を渡し、新規／未対応だけ |
| 誤検知 | 明示的なカテゴリ基準、高誤検知カテゴリの一時停止、重大度の具体例 |
| 14ファイルの PR で矛盾 | ファイル単位＋統合パス |
| 生成と同じセッションでのレビュー | 独立インスタンス |
| コスト削減の Batch 化 | マージ前は同期、夜間はバッチ |

めたん: シナリオ5は、{CI|シーアイ}ですわ。
ずんだもん: ハングするならハイフン ピー、構造化出力ならアウトプットフォーマット ジェイソンとジェイソン スキーマなのだ。
めたん: 重複コメントは、以前の指摘を渡す。誤検知は、明示的なカテゴリの基準と、一時停止。
ずんだもん: 大きなプルリクエストは、ファイル単位と統合パス。レビューは独立したインスタンスなのだ。
めたん: コスト削減でバッチにするなら？
ずんだもん: マージ前は同期、夜間はバッチなのだ。テスト生成の質を上げるなら、既存のテストを渡して、{CLAUDE.md|クロード ドット エムディー}にテストの標準を書くのだ。

## SLIDE: シナリオ6：構造化データ抽出
> 前提：非構造化文書から抽出、JSON スキーマで検証、高精度、エッジケース処理、下流システム統合
| 典型的な問い | 答えの方向 |
| JSON 構文エラー | tool_use＋JSON スキーマ（strict） |
| 文書種別が不明で抽出スキーマが複数／特定の抽出を先に | tool_choice: "any"／強制選択 |
| 値の捏造 | nullable／任意フィールド、"other"＋詳細、"unclear" |
| 合計不一致 | 意味的エラー → calculated_total vs stated_total、conflict_detected |
| 多様な文書構造で空抽出 | few-shot |
| 大量処理・SLA | Batches、custom_id、失敗分だけ再送 |
| 97%の精度で完全自動化？ | 種別・フィールド別、層化抽出、キャリブレーション |

めたん: 最後のシナリオ6は、構造化データ抽出ですわ。
ずんだもん: {JSON|ジェイソン}の構文エラーには、ツールユースとスキーマなのだ。文書の種類が分からないなら{any|エニー}、特定の抽出を先にやるなら強制選択なのだ。
めたん: 値の捏造には、ヌル許容と、{other|アザー}と、{unclear|アンクリア}。合計の不一致は、意味的エラーですわね。
ずんだもん: 2つの合計を比べるのだ。いろいろな文書構造で空になるなら、フューショットなのだ。
めたん: 大量処理と、97パーセントの精度は？
ずんだもん: バッチと{custom_id|カスタムアイディー}、失敗分だけの再送なのだ。97パーセントでも、種類別、フィールド別の確認と、層化抽出とキャリブレーションなのだ。

## SLIDE: シナリオ問題の読み方 ★
- シナリオの **前提を最初にしっかり読む**（ツール名、目標値「初回解決率80%」、「誤検知を最小化」など）
- 問題文の修飾語が決め手：「**最も効果的な最初の一手**」「**最も保守しやすい**」「**確実に**」
- 「確実に」→ プログラム（フック・ゲート）／「最初の一手」→ 低労力・高効果
- 時間配分：4シナリオ×約15問 → **1シナリオ約30分**

めたん: シナリオ問題を解くコツは、ありますの？
ずんだもん: まず、シナリオの前提をしっかり読むのだ。ツールの名前、初回解決率80パーセントのような目標値、誤検知を最小化、といった条件なのだ。
めたん: 問題文では？
ずんだもん: 修飾語が決め手なのだ。「最も効果的な最初の一手」、「最も保守しやすい」、「確実に」、などなのだ。
ずんだもん: 「確実に」ならプログラム。「最初の一手」なら、低労力で効果が高いもの、なのだ。
めたん: 時間配分は？
ずんだもん: 4つのシナリオで約15問ずつだから、1シナリオ約30分が目安なのだ。
