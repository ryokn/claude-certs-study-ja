## SLIDE: 2.1 ツールの説明（description）★
- **ツールの説明は、LLM がツールを選ぶ主要な手がかり**。最小限の説明では類似ツール間の選択が不安定
- 説明に入れるもの：**入力形式、クエリ例、エッジケース、境界**（似たツールではなくこれを使う場面／使わない場面）、出力
- 曖昧・重複した説明 → **誤ルーティング**（例：ほぼ同じ説明の analyze_content と analyze_document）
- **システムプロンプトのキーワードに敏感な指示** が、良いツール説明を上書きすることがある → レビューする

めたん: ツール設計で、いちばん大事なことは？
ずんだもん: ツールの説明なのだ。モデルがどのツールを使うか選ぶときの、主な手がかりなのだ。説明が最小限だと、似たツールの間で選択が不安定になるのだ。
めたん: 説明には、何を書けばよろしいの？
ずんだもん: 入力の形式、クエリの例、エッジケース、そして境界なのだ。似たツールではなく、これを使う場面と、使わない場面を書くのだ。
めたん: 説明が曖昧だったり、重複していたりすると？
ずんだもん: 誤ルーティングが起きるのだ。コンテンツを分析します、文書を分析します、みたいなほぼ同じ説明のツールが2つあると、取り違えるのだ。
ずんだもん: それから、システムプロンプトの中の、キーワードに反応する一文が、良いツール説明を上書きしてしまうこともあるのだ。そこも見直すのだ。

## SLIDE: 説明の改善パターンと例
| 改善パターン | 例 |
| 改名＋説明更新で重複解消 | analyze_content → extract_web_results（ウェブ専用の説明） |
| 汎用ツールを目的別に分割（入出力の契約を定義） | analyze_document → extract_data_points ／ summarize_content ／ verify_claim_against_source |

```
{"name": "lookup_order",
 "description": "注文番号（例: #12345, A-1029）から注文の状態・明細・配送状況を取得する。
   顧客の本人確認や連絡先の取得には使わない（それは get_customer）。
   注文番号が不明なら先に get_customer で顧客IDを得てから customer_id で検索する。", ...}
```

めたん: 改善のしかたには、パターンがありますのね。
ずんだもん: 1つ目は、改名して説明を書き直すことなのだ。{analyze_content|アナライズ コンテント}を、{extract_web_results|エクストラクト ウェブ リザルツ}に改名して、ウェブ専用の説明にするのだ。
ずんだもん: 2つ目は、汎用のツールを目的別に分けることなのだ。データポイントの抽出、要約、主張の検証、のように分けて、入出力の契約を決めるのだ。
めたん: 下の例は、注文検索のツールですわね。
ずんだもん: 注文番号の例を書いて、本人確認には使わない、それは{get_customer|ゲット カスタマー}、と境界も書いているのだ。注文番号が分からないときの手順もあるのだ。

## SLIDE: サンプル問題2：最初の一手は？
| 選択肢の型 | 判定 |
| ツール説明を拡充（入力形式・例・エッジケース・境界） | 正解（最も効果的な最初の一手） |
| few-shot を5〜8件追加 | トークンが増えるだけで根本未解決 |
| キーワードのルーティング層を追加 | 過剰設計 |

めたん: サンプル問題2は、{get_customer|ゲット カスタマー}と{lookup_order|ルックアップ オーダー}の取り違えでしたわね。
ずんだもん: そうなのだ。説明が最小限なのが根本原因なので、説明を拡充するのが、最も効果的な最初の一手なのだ。
めたん: フューショットは、前々回も不正解でしたわね。
ずんだもん: トークンが増えるだけで、根本は解決しないのだ。ルーティング層は過剰設計なのだ。
めたん: ツールの統合は？
ずんだもん: 妥当ではあるけど、最初の一手としては重いのだ。「最初の一手」という言葉が決め手なのだ。

## SLIDE: 2.2 MCP の構造化エラー ★
| 種類 | 例 | リトライ |
| 一時的（transient） | タイムアウト、サービス利用不可 | 可（ローカルで） |
| 検証（validation） | 無効な入力 | 入力を直せば可 |
| ビジネス（business） | ポリシー違反（返品期限切れ） | 不可（retriable: false＋顧客向け説明） |
| 権限（permission） | 権限不足 | 不可（エスカレーション等） |

- MCP 仕様：プロトコルエラーは JSON-RPC エラー、**ツール実行エラーはツール結果の isError: true**

めたん: 次は、エラーの返し方ですわ。
ずんだもん: {MCP|エムシーピー}では、ツールの実行エラーを、ツール結果の{isError|イズエラー} {true|トゥルー}で伝えるのだ。プロトコルのエラーは、{JSON-RPC|ジェイソン アールピーシー}のエラーなのだ。
めたん: エラーには、種類がありますのね。
ずんだもん: 4つなのだ。タイムアウトのような一時的なエラーは、リトライしていいのだ。無効な入力の検証エラーは、入力を直せばリトライできるのだ。
めたん: 返品期限切れのような、ビジネスのエラーは？
ずんだもん: リトライしてはダメなのだ。リトライ不可の印と、顧客向けの説明を付けて返すのだ。権限のエラーも、リトライ不可で、エスカレーションなどに回すのだ。

## SLIDE: 構造化エラーの例とひっかけ
```
{"isError": true,
 "content": [{"type": "text", "text": "{\"errorCategory\":\"business\",
   \"isRetryable\":false,\"message\":\"返品受付期間（30日）を過ぎています\",
   \"customerMessage\":\"お受け取りから30日を過ぎているため返品をお受けできません\"}"}]}
```
- × 一律の "Operation failed" → 適切な復旧判断ができない
- ○ サブエージェントは一時的な失敗を **ローカルで復旧**、解決できないものだけ **部分結果と試行内容つき** でコーディネーターへ
- ○ **アクセス失敗**（リトライ判断が必要）と **有効な空の結果**（検索は成功、該当なし）を区別

めたん: 例を見ると、カテゴリ、リトライ可否、メッセージ、顧客向けのメッセージが入っていますわね。
ずんだもん: そうなのだ。逆に、何でも一律に「オペレーション フェイルド」と返すと、エージェントは正しく立て直せないのだ。期限切れなのに、リトライを繰り返したりするのだ。
めたん: サブエージェントが失敗したときは？
ずんだもん: 一時的な失敗は、サブエージェントの中で復旧するのだ。解決できないものだけを、部分的な結果と、何を試したかを付けて、コーディネーターに返すのだ。
めたん: 検索して何も見つからなかった、というのは失敗ですの？
ずんだもん: そこを区別するのが大事なのだ。アクセスに失敗したのか、検索は成功して該当がなかったのか。前者はリトライの判断が要るけど、後者は有効な空の結果なのだ。

## SLIDE: 2.3 ツールの配分と選択
- ツールが多すぎる（**4〜5個ではなく18個**）と選択の信頼性が下がる
- 専門外のツールを持つと誤用する（統合エージェントがウェブ検索を始める）
- **スコープを限定したツールアクセス**：役割に必要なもの＋頻度の高いニーズにだけ役割横断ツール
- 例：統合エージェントに **verify_fact**。複雑なものはコーディネーター経由（サンプル問題9）
- 汎用ツールを **制約付き** の代替に（fetch_url → ドキュメントURLを検証する load_document）
- tool_choice：強制で最初のツールを確定 → 後続はフォローアップのターン。"any" で必ずツール

めたん: ツールは、たくさん持たせたほうが便利ではありませんの？
ずんだもん: 逆なのだ。4、5個ではなく18個もあると、選択の信頼性が下がるのだ。専門外のツールを持つと、統合エージェントがウェブ検索を始めたりするのだ。
めたん: では、役割に必要なものだけ？
ずんだもん: そうなのだ。それに加えて、頻度の高い特定のニーズにだけ、役割をまたぐツールを、スコープを限定して渡すのだ。
ずんだもん: サンプル問題9では、統合エージェントに、簡単な事実確認のための{verify_fact|ベリファイ ファクト}だけを渡すのが正解なのだ。複雑な確認は、今まで通りコーディネーター経由なのだ。
めたん: 誤答は？
ずんだもん: 全部の検索ツールを渡すのは過剰な権限、一括でバッチ処理するのは依存関係でブロック、先回りのキャッシュは予測できない、なのだ。
ずんだもん: 汎用のツールを、制約付きのものに置き換えるのも手なのだ。{fetch_url|フェッチ ユーアールエル}の代わりに、ドキュメントの{URL|ユーアールエル}を検証する{load_document|ロード ドキュメント}にするのだ。

## SLIDE: 2.4 MCP サーバーの統合 ★
| 目的 | 置き場所 |
| チーム共有のツール | プロジェクトスコープ：.mcp.json（リポジトリにコミット） |
| 個人用・実験的なサーバー | ユーザースコープ：~/.claude.json |
| シークレット | .mcp.json で ${GITHUB_TOKEN} のような環境変数展開（${VAR:-default} も可） |

```
{"mcpServers": {"github": {"type": "http", "url": "https://api.githubcopilot.com/mcp/",
   "headers": {"Authorization": "Bearer ${GITHUB_TOKEN}"}}}}
claude mcp add --transport http my-exp https://example.com/mcp --scope user  # 個人用
```

めたん: {MCP|エムシーピー}サーバーの置き場所ですわ。
ずんだもん: チームで共有するなら、プロジェクトスコープの{.mcp.json|ドット エムシーピー ドット ジェイソン}なのだ。リポジトリにコミットするのだ。
めたん: トークンも、一緒にコミットしてしまいますの？
ずんだもん: ダメなのだ。ドル、波かっこで、{GITHUB_TOKEN|ギットハブ トークン}のように、環境変数の展開で参照するのだ。既定値付きの書き方もあるのだ。
めたん: 個人用や、実験中のサーバーは？
ずんだもん: ユーザースコープの{~/.claude.json|ホーム ドット クロード ドット ジェイソン}なのだ。{claude mcp add|クロード エムシーピー アド}に、スコープ ユーザーを付けて追加するのだ。

## SLIDE: MCP の頻出ポイント
- 設定された **すべての MCP サーバーのツールが接続時に検出され、同時に利用可能**
- **MCP リソース**：コンテンツカタログ（課題サマリー、ドキュメント階層、DBスキーマ）を公開 → **探索的なツール呼び出しを減らす**
- ツール＝アクション、リソース＝読むためのデータ
- ○ MCP ツールの説明を充実させ、エージェントが **組み込みツール（Grep など）を優先してしまう** のを防ぐ
- ○ 標準的な統合（Jira など）は **既存のコミュニティ MCP サーバー**、カスタムはチーム固有ワークフローに
- 現行：.mcp.json のサーバーは初回に承認が必要

めたん: ほかに、{MCP|エムシーピー}で問われることは？
ずんだもん: 設定したすべての{MCP|エムシーピー}サーバーのツールは、接続時に見つかって、同時に使えるのだ。
めたん: {MCP|エムシーピー}リソース、というのは？
ずんだもん: 課題のサマリーや、ドキュメントの階層、データベースのスキーマのような、コンテンツのカタログを公開するものなのだ。
ずんだもん: 探索のためのツール呼び出しを減らせるのだ。ツールはアクション、リソースは読むためのデータなのだ。
めたん: エージェントが、{MCP|エムシーピー}ツールより{Grep|グレップ}ばかり使ってしまうときは？
ずんだもん: {MCP|エムシーピー}ツールの説明を充実させるのだ。ここでも、説明が鍵なのだ。
ずんだもん: それから、{Jira|ジラ}のような標準的な統合は、既存のコミュニティの{MCP|エムシーピー}サーバーを使うのだ。カスタムで作るのは、チーム固有のワークフローなのだ。

## SLIDE: 2.5 組み込みツールの選び方 ★
| ツール | 用途 | 例 |
| Grep | ファイルの内容を検索 | 関数の全呼び出し元、エラーメッセージの発生箇所、import文 |
| Glob | ファイルのパス・名前のパターン一致 | **/*.test.tsx |
| Read ／ Write | ファイル全体の読み込み・書き込み | — |
| Edit | 一意なテキスト一致による的を絞った変更 | — |
| Bash | コマンド実行 | テスト実行など |

めたん: 最後は、組み込みツールですわ。
ずんだもん: {Grep|グレップ}は、ファイルの中身を検索するのだ。関数の呼び出し元や、エラーメッセージの発生箇所を探すのだ。
めたん: {Glob|グロブ}は？
ずんだもん: ファイルのパスや名前の、パターン一致なのだ。テストファイルを全部見つける、などなのだ。
めたん: 中身なら{Grep|グレップ}、名前なら{Glob|グロブ}ですわね。逆に選ぶのが、ひっかけですのね。
ずんだもん: その通りなのだ。{Read|リード}と{Write|ライト}はファイル全体、{Edit|エディット}は一意なテキストの一致で、的を絞って変更するのだ。{Bash|バッシュ}はコマンドの実行なのだ。

## SLIDE: 組み込みツールの頻出ポイント
- ○ Edit が「一致が一意でない」で失敗 → **Read で全体を読み込み、Write で書き戻す**
- ○ 最初に全ファイルを読まない：**Grep でエントリポイント → Read で import をたどる**
- ○ ラッパーモジュール越しの使用箇所：まず **エクスポート名をすべて特定 → 各名前で Grep**
- × 内容検索に Glob、ファイル名探しに Grep
- 模試より（オリジナル）："PAYMENT_DECLINED" の発生箇所と流れ → **Grep で特定 → Read で呼び出し元をたどる**

めたん: {Edit|エディット}が、一致が一意でない、と失敗したら？
ずんだもん: {Read|リード}でファイル全体を読み込んで、{Write|ライト}で書き戻すのだ。ガイドに書いてあるフォールバックなのだ。
めたん: 不慣れなコードベースでは、まず全部のファイルを読みますの？
ずんだもん: 読まないのだ。{Grep|グレップ}で入口を見つけて、{Read|リード}でインポートをたどって、段階的に理解するのだ。
ずんだもん: ラッパーのモジュール越しに使われている場合は、まずエクスポートされている名前を全部洗い出して、その名前ごとに{Grep|グレップ}するのだ。
めたん: 模擬試験にも、エラーメッセージの発生箇所を調べる問題がありましたわね。
ずんだもん: {Grep|グレップ}で特定して、{Read|リード}で呼び出し元をたどる。これが正解なのだ。

## SLIDE: まとめ（分野2）
- ツール選択ミス → まず **ツール説明の拡充**（入力形式・例・エッジケース・境界）。重複は **改名・分割**
- エラーは **isError＋構造化**（errorCategory、isRetryable、説明）。ビジネスエラーは **リトライ不可**
- **アクセス失敗 ≠ 有効な空結果**。一時的な失敗はローカルで復旧
- ツールは **役割ごとに4〜5個**、役割横断は **スコープ限定（verify_fact）**
- 共有 MCP＝ **.mcp.json＋${TOKEN}**、個人 MCP＝ **~/.claude.json**。リソースで探索を減らす
- 内容検索＝ **Grep**、ファイル名＝ **Glob**、Edit 失敗＝ **Read＋Write**
- 次回：分野5（15%）コンテキスト管理と信頼性

めたん: では、わたくしがまとめますわね。
めたん: ツールの選択ミスには、まずツール説明の拡充。重複は改名か分割。
めたん: エラーは{isError|イズエラー}と構造化。ビジネスのエラーはリトライ不可。アクセス失敗と、有効な空の結果は違う。
めたん: ツールは役割ごとに4、5個。役割をまたぐのは、スコープを限定した{verify_fact|ベリファイ ファクト}。
めたん: 共有の{MCP|エムシーピー}は{.mcp.json|ドット エムシーピー ドット ジェイソン}と環境変数、個人用は{~/.claude.json|ホーム ドット クロード ドット ジェイソン}。中身は{Grep|グレップ}、名前は{Glob|グロブ}、{Edit|エディット}が失敗したら{Read|リード}と{Write|ライト}。
ずんだもん: 完璧なのだ！次回は分野5、コンテキスト管理と信頼性なのだ。
めたん: ご視聴、ありがとうございました。
