## SLIDE: 3.4 プランモード vs 直接実行 ★
| プランモード | 直接実行 |
| 大規模変更、複数の有効なアプローチ、アーキテクチャ上の判断、多ファイル修正 | 単純で範囲が明確（1関数にバリデーションを1つ追加、スタックトレースが明確な単一ファイルのバグ修正） |
| 例：マイクロサービス再構成、45以上のファイルのライブラリ移行、インフラ要件が違う統合方式の選択 | 例：日付バリデーションの条件分岐を追加 |

めたん: プランモードと直接実行は、どう使い分けますの？
ずんだもん: プランモードは、大規模な変更、複数の有効なアプローチがある、アーキテクチャの判断が要る、たくさんのファイルを直す、というときなのだ。
めたん: 例でいうと？
ずんだもん: マイクロサービスへの再構成、45以上のファイルにまたがるライブラリの移行、インフラ要件が違う統合方式の選択なのだ。
めたん: 直接実行は？
ずんだもん: 単純で範囲が明確なものなのだ。1つの関数にバリデーションを1つ足す、スタックトレースがはっきりした、1つのファイルのバグを直す、なのだ。

## SLIDE: プランモードの補足とひっかけ
- 変更を確定する前に **安全に探索・設計** でき、手戻りを防ぐ
- 現行：**Shift+Tab** でモード切替、claude --permission-mode plan、/plan。承認するまで編集しない
- **Explore サブエージェント**：読み取り専用の組み込みサブエージェント。冗長な調査を分離して **要約だけ** 返す
- ○ **組み合わせ**：プランモードで調査・計画 → 直接実行で実装
- × 直接実行で始めて、複雑になったらプランモードへ（複雑さが要件時点で明らか → 最初からプラン。サンプル問題5）
- × 詳細な事前指示を書いて直接実行（コードを調べずに正しい構成を知っている前提）

めたん: プランモードの良いところは？
ずんだもん: 変更を確定する前に、安全に探索して設計できるのだ。承認するまで、編集しないのだ。今は、シフト タブで切り替えられるのだ。
めたん: {Explore|エクスプロア}サブエージェント、というのは？
ずんだもん: 読み取り専用の、組み込みのサブエージェントなのだ。冗長な調査の出力を分離して、要約だけを返すから、メインのコンテキストが枯れないのだ。
めたん: 両方を組み合わせることも、できますの？
ずんだもん: できるのだ。プランモードで調べて計画して、直接実行で実装するのだ。
めたん: サンプル問題5の、ひっかけは？
ずんだもん: 「直接実行で始めて、複雑になったらプランモードに切り替える」なのだ。複雑さが要件の時点で明らかなら、最初からプランモードなのだ。
ずんだもん: 「詳細な事前指示を書いて直接実行」もダメなのだ。コードを調べずに、正しい構成を知っている前提になってしまうのだ。

## SLIDE: 3.5 反復的な改良手法
| 手法 | 使う場面 |
| 具体的な入出力例を2〜3個 | 文章の説明が一貫して解釈されない変換 |
| テスト駆動の反復 | 先にテスト（期待動作・エッジケース・性能要件）を書き、失敗を共有して改善 |
| インタビューパターン | 不慣れな領域で、実装前に Claude に質問させ考慮事項を洗い出す |
| 1メッセージにまとめて伝える | 修正が相互に影響する複数の問題 |
| 順番に1つずつ | 独立した問題 |

めたん: 次は、反復的な改良ですわ。
ずんだもん: 文章で説明しても、毎回解釈がぶれる変換には、具体的な入力と出力の例を2つか3つ見せるのだ。
めたん: テスト駆動の反復は？
ずんだもん: 先に、期待する動作、エッジケース、性能要件のテストを書くのだ。そして失敗した結果を共有して、改善させるのだ。
めたん: インタビューパターン、というのは面白い名前ですわね。
ずんだもん: 不慣れな領域で、実装の前に{Claude|クロード}に質問させるのだ。キャッシュの無効化戦略や障害モードのような、考慮すべき点を洗い出せるのだ。
めたん: 問題が複数あるときは？
ずんだもん: 修正がお互いに影響するなら、1つのメッセージにまとめて伝えるのだ。独立した問題なら、順番に1つずつなのだ。
ずんだもん: それから、移行スクリプトのヌル値のようなエッジケースは、入力例と期待出力つきの、具体的なテストケースで伝えるのだ。

## SLIDE: 模試から：日付の解釈がぶれる（オリジナル）

ずんだもん: 具体的な入力と、期待される出力の例を2、3組見せるのだ。曖昧な形式も含めるのがコツなのだ。

## SLIDE: 3.6 CI/CD への統合：フラグ ★
| フラグ | 役割 |
| -p ／ --print | 非対話モード。結果を stdout に出して終了 → 入力待ちのハングを防ぐ |
| --output-format json | 機械可読な出力（text ／ json ／ stream-json） |
| --json-schema '<schema>' | スキーマに一致する構造化出力（print モードのみ）。結果は structured_output |
| （参考）--max-turns、--allowedTools、--append-system-prompt | ターン上限、許可ツール、システムプロンプト追記 |

めたん: いよいよ、{CI|シーアイ}への統合ですわ。
ずんだもん: いちばん大事なのは、ハイフン ピー、{--print|ハイフン ハイフン プリント}なのだ。非対話モードで、結果を標準出力に出して終了するのだ。
めたん: {CI|シーアイ}で、入力待ちのままハングするのを防げますのね。
ずんだもん: そうなのだ。{--output-format json|アウトプットフォーマット ジェイソン}で、機械が読める出力になるのだ。
ずんだもん: さらに{--json-schema|ハイフン ハイフン ジェイソン スキーマ}で、スキーマに合った構造化出力が得られるのだ。プリントモード専用で、結果は{structured_output|ストラクチャード アウトプット}に入るのだ。

## SLIDE: CI でのレビュー実行例
```
claude -p "このPRの差分をレビューし、バグとセキュリティ問題だけを報告" \
  --output-format json \
  --json-schema "$(cat review-schema.json)" \
  | jq '.structured_output.findings'
# review-schema.json：findings[] に file, line, severity(high/medium/low), issue, fix
```
- ○ CI でハング → **-p を付ける**（サンプル問題10）
- × CLAUDE_HEADLESS=true（**存在しない**）／ --batch（**存在しない**）／ < /dev/null（正しい方法ではない）

ずんだもん: 実行例は、こうなるのだ。ハイフン ピーでレビューを頼んで、{JSON|ジェイソン}で出力して、スキーマで形を決めるのだ。
めたん: 最後に{jq|ジェイキュー}で、{findings|ファインディングズ}を取り出していますわね。
ずんだもん: ファイル、行、重大度、問題、修正案の配列なのだ。インラインコメントに使いやすいのだ。
めたん: サンプル問題10は？
ずんだもん: {CI|シーアイ}でハングする問題なのだ。答えはハイフン ピーなのだ。
めたん: {CLAUDE_HEADLESS|クロード ヘッドレス}イコール{true|トゥルー}や、{--batch|ハイフン ハイフン バッチ}は？
ずんだもん: どちらも存在しないのだ。標準入力に{/dev/null|デブ ヌル}をつなぐのも、正しい方法ではないのだ。

## SLIDE: CI の頻出ポイント
- ○ CI から呼ぶ Claude Code へのプロジェクト文脈（テスト標準、フィクスチャ規約、レビュー基準）は **CLAUDE.md** で渡す
- ○ 再レビュー時は **以前の指摘をコンテキストに含め、新規・未対応だけ報告** → 重複コメントを防ぐ
- ○ テスト生成には **既存テストファイルを渡して** 重複シナリオを避ける
- ○ **セッションコンテキストの分離**：生成した同じセッションは自分の変更をレビューするのが苦手 → **独立したレビューインスタンス**

めたん: {CI|シーアイ}で、ほかに問われることは？
ずんだもん: テスト標準やフィクスチャの規約、レビューの基準みたいなプロジェクトの文脈は、{CLAUDE.md|クロード ドット エムディー}で渡すのだ。
めたん: 修正コミットのたびに、同じ指摘が何度も付いてしまったら？
ずんだもん: 以前の指摘をコンテキストに含めて、新しい問題か、まだ対応されていない問題だけを報告させるのだ。
めたん: テストを生成させるときは？
ずんだもん: 既存のテストファイルを渡すのだ。同じシナリオのテストが重複しないのだ。
ずんだもん: そして、コードを生成したのと同じセッションは、自分の変更をレビューするのが苦手なのだ。レビューは、独立した別のインスタンスでやるのだ。

- 再レビューは **以前の指摘を渡す**。レビューは **独立インスタンス**
