## SLIDE: 1.1 エージェントループの基本
- Claude にリクエスト → **stop_reason** を確認
- **"tool_use"** → ツールを実行 → **tool_result を会話履歴に追加** → 次の反復
- **"end_turn"** → 終了
- 結果を履歴に追加するから、**モデル主導で** 次のアクションを決められる
- ↔ 事前に決めた決定木・固定のツール順序

めたん: まずは、エージェントループですわ。
ずんだもん: {Claude|クロード}にリクエストを送って、{stop_reason|ストップリーズン}を確認するのだ。
ずんだもん: {tool_use|ツールユース}ならツールを実行して、ツールリザルトを会話履歴に追加して、次の反復に進むのだ。{end_turn|エンドターン}なら終了なのだ。
めたん: ツールの結果を、履歴に追加するのはなぜですの？
ずんだもん: 新しい情報を踏まえて、次に何をするかをモデル主導で決められるからなのだ。
めたん: 事前に決めた決定木や、固定のツール順序とは、そこが違いますのね。

## SLIDE: 現行 API の事実：stop_reason と tool_result
- stop_reason：end_turn ／ max_tokens ／ stop_sequence ／ tool_use ／ pause_turn ／ refusal ／ model_context_window_exceeded
- pause_turn：サーバーツールのループが反復上限 → 応答をそのまま送り返して続行
- tool_result は対応する tool_use の **直後のユーザーメッセージ** に置く
- content 配列では **tool_result を先頭** に（テキストは後ろ）。tool_use_id で対応付け、失敗は **is_error: true**
- 1応答に **複数の tool_use**（並列）→ 全部実行し **1つのユーザーメッセージ** で返す

めたん: {stop_reason|ストップリーズン}には、ほかにどんな値がありますの？
ずんだもん: {max_tokens|マックストークンズ}、{stop_sequence|ストップシーケンス}、{pause_turn|ポーズターン}、{refusal|リフューザル}、{model_context_window_exceeded|モデル コンテキストウィンドウ エクシーディッド}なのだ。
めたん: {pause_turn|ポーズターン}は？
ずんだもん: サーバーツールのループが反復の上限に達した、という意味なのだ。応答をそのまま送り返せば、続きを実行するのだ。
めたん: ツールリザルトは、どこに置きますの？
ずんだもん: 対応するツールユースの、直後のユーザーメッセージなのだ。その中では、ツールリザルトを先頭に置いて、テキストは後ろなのだ。
ずんだもん: {tool_use_id|ツールユース アイディー}で対応付けて、失敗したときは{is_error|イズエラー} {true|トゥルー}を付けるのだ。
めたん: 1つの応答に、ツールユースが複数入ることもありますの？
ずんだもん: あるのだ。並列ツール呼び出しなのだ。全部実行して、結果を1つのユーザーメッセージにまとめて返すのだ。

## SLIDE: 最小のエージェントループ（Python SDK）
```
messages = [{"role": "user", "content": user_input}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=2048,
                                  system=SYSTEM, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break  # end_turn（max_tokens 等は別途）
    results = [{"type": "tool_result", "tool_use_id": b.id,
                **run_tool(b.name, b.input)}  # content, is_error
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})
```

ずんだもん: コードで見ると、こうなるのだ。応答を受け取ったら、まずアシスタントの内容を、必ず履歴に追加するのだ。
めたん: {stop_reason|ストップリーズン}が{tool_use|ツールユース}でなければ、ループを抜けますのね。
ずんだもん: そうなのだ。{max_tokens|マックストークンズ}などは、別途ハンドリングするのだ。
めたん: {tool_use|ツールユース}なら、ツールユースのブロックを全部実行して……
ずんだもん: 結果をツールリザルトにして、{content|コンテント}と{is_error|イズエラー}を付けて、1つのユーザーメッセージとして追加して、次の反復なのだ。

## SLIDE: 1.2 コーディネーター・サブエージェントパターン
- **ハブアンドスポーク**：コーディネーターが通信・エラー処理・情報ルーティングを **すべて** 管理
- サブエージェントは **分離されたコンテキスト**。親の履歴を自動では継承しない
- 役割：タスク分解、委任、結果の集約、**複雑さに応じて呼ぶサブエージェントを決める**
- ○ 毎回全パイプラインではなく **必要なサブエージェントだけを動的に選択**
- ○ 範囲を **サブトピックや情報源の種類で分割**して重複を最小化
- ○ **反復的改善ループ**：不足を評価 → 的を絞って再委任 → 統合を再実行

めたん: 次は、コーディネーターとサブエージェントですわ。
ずんだもん: 基本は、ハブアンドスポークなのだ。コーディネーターが、サブエージェント間の通信、エラー処理、情報のルーティングを、すべて管理するのだ。
めたん: サブエージェントは、コーディネーターの会話を見られますの？
ずんだもん: 見られないのだ。分離されたコンテキストで動いて、親の履歴は自動では継承しないのだ。
めたん: コーディネーターの仕事は？
ずんだもん: タスク分解、委任、結果の集約、そしてクエリの複雑さに応じて、どのサブエージェントを呼ぶか決めることなのだ。
ずんだもん: 単純な質問でも、毎回パイプライン全部を回すのはムダなのだ。必要なサブエージェントだけを、動的に選ぶのだ。
めたん: 調査の範囲は、どう分けますの？
ずんだもん: サブトピックや情報源の種類で分けて、重複を減らすのだ。そして統合結果に不足があれば、的を絞って再委任して、統合し直すのだ。

## SLIDE: コーディネーター設計のひっかけ
- ○ 通信は **すべてコーディネーター経由**（可観測性・一貫したエラー処理・制御された情報フロー）
- × サブエージェント同士が直接呼び合う（観測・エラー処理が分散）
- △ **分解が狭すぎる** と網羅性が落ちる（サンプル問題7）
- 例：「クリエイティブ産業」を **ビジュアルアートだけ** に分解
- → 下流のエージェントは正しく動いている。原因は **割り当て自体**

めたん: サブエージェント同士が、直接呼び合うのはどうですの？
ずんだもん: ダメなのだ。観測やエラー処理が分散してしまうのだ。通信は、すべてコーディネーター経由なのだ。
めたん: サンプル問題7も、ここですわね。
ずんだもん: そうなのだ。レポートの網羅性が足りない、という問題なのだ。原因は、コーディネーターの分解が狭すぎたことなのだ。
めたん: クリエイティブ産業を調べるはずが、ビジュアルアートだけに分けてしまった、と。
ずんだもん: そうなのだ。下流の検索や分析のエージェントは、割り当てられた範囲の中では正しく動いているのだ。だから原因は、割り当てそのものなのだ。

## SLIDE: 1.3 サブエージェントの生成とコンテキストの受け渡し
- 生成は **Task ツール**（現行名 Agent）
- コーディネーターの **allowedTools** に **"Task"** が必要
- **AgentDefinition**：**description**（いつ使うか・必須）、**prompt**（システムプロンプト・必須）、tools（省略時は継承）、model など
- 親から子に渡るのは **Task のプロンプト文字列だけ**（＋自身のシステムプロンプト、プロジェクト CLAUDE.md、ツール定義）
- 親の会話履歴・ツール結果・親のシステムプロンプトは **渡らない**

めたん: サブエージェントは、どうやって生成しますの？
ずんだもん: {Task|タスク}ツールなのだ。今の名前は{Agent|エージェント}なのだ。コーディネーターの{allowedTools|アラウドツールズ}に、{Task|タスク}が入っている必要があるのだ。
めたん: サブエージェントの定義は？
ずんだもん: {AgentDefinition|エージェント デフィニション}なのだ。{description|ディスクリプション}は、いつ使うかの説明で、委任の判断材料になるのだ。{prompt|プロンプト}は、そのエージェントのシステムプロンプトなのだ。この2つが必須なのだ。
ずんだもん: {tools|ツールズ}でツールを制限できて、省略すると継承なのだ。
めたん: 親から子には、何が渡りますの？
ずんだもん: {Task|タスク}ツールのプロンプト文字列だけなのだ。あとは、そのエージェント自身のシステムプロンプト、プロジェクトの{CLAUDE.md|クロード ドット エムディー}、ツール定義なのだ。
めたん: 親の会話履歴や、ツールの結果は？
ずんだもん: 渡らないのだ。ここが、いちばんのポイントなのだ。

## SLIDE: Agent SDK：コーディネーター＋サブエージェント定義
```
options = ClaudeAgentOptions(
    allowed_tools=["Task", "Read", "Grep"],  # ガイドの表記は "Task"
    agents={
        "web-searcher": AgentDefinition(
            description="ウェブ検索専門。最新の公開情報が必要なときに使う",
            prompt="各発見に claim, excerpt, url, published_at を付ける",
            tools=["WebSearch", "WebFetch"]),
        "synthesizer": AgentDefinition(
            description="複数の調査結果を出典付きで統合する",
            prompt="claim-source の対応を保持したまま統合する",
            tools=["Read"])})
```

ずんだもん: {Agent SDK|エージェント エスディーケー}の{Python|パイソン}だと、こうなるのだ。{allowed_tools|アラウドツールズ}に{Task|タスク}を入れて、{agents|エージェンツ}にサブエージェントを定義するのだ。
めたん: ウェブ検索担当には、ウェブ検索とウェブフェッチだけ。統合担当には、{Read|リード}だけですのね。
ずんだもん: そうなのだ。役割に必要なツールだけを渡すのだ。そして、検索結果には主張、抜粋、{URL|ユーアールエル}、公開日を付けて返させるのだ。

## SLIDE: コンテキスト受け渡しの頻出ポイント ★
- ○ 先行エージェントの **調査結果全体** を、次のサブエージェントの **プロンプトに直接** 含める
- ○ 内容と **メタデータ（URL・文書名・ページ番号）を分けた構造化形式** で渡す
- ○ **並列実行＝コーディネーターの1つの応答で複数の Task 呼び出し**（別々のターンに分けない）
- ○ コーディネーターのプロンプトは **手順の羅列ではなく、目標と品質基準**
- × サブエージェントは親の履歴を参照できる／メモリを共有する
- × 委任されないので「コーディネーターにも同じツールを与える」→ 逆効果
- **フォーク（fork）**：共通の分析ベースラインから異なるアプローチを探る

めたん: 受け渡しで、試験に出るポイントは？
ずんだもん: 前のエージェントの調査結果全体を、次のサブエージェントのプロンプトに、直接含めるのだ。
ずんだもん: そのとき、内容と、{URL|ユーアールエル}や文書名、ページ番号みたいなメタデータを分けて、構造化して渡すのだ。出典の帰属が保てるのだ。
めたん: 並列に動かしたいときは？
ずんだもん: コーディネーターの1つの応答で、{Task|タスク}の呼び出しを複数出すのだ。別々のターンに分けたら、並列にならないのだ。
めたん: コーディネーターのプロンプトには、手順を細かく書くべきかしら？
ずんだもん: 手順の羅列ではなく、目標と品質基準を伝えるのだ。そのほうが、サブエージェントが状況に適応できるのだ。
めたん: 委任されないから、コーディネーターにも同じツールを与える、というのは？
ずんだもん: 逆効果なのだ。コーディネーターが自分で作業して、ますます委任しなくなるのだ。

## SLIDE: 模試から：委任されない原因は？（オリジナル）
- コーディネーターが、定義したサブエージェント（web-searcher、doc-analyzer）を一度も起動しない
- 設定上まず確認すべき点を **2つ** 選ぶ
- A. サブエージェントが会話履歴を共有する設定か
- B. **各 AgentDefinition の description が、いつ使うべきかを明確に書いているか**
- C. コーディネーターの max_tokens が十分大きいか
- D. コーディネーターにも検索・解析ツールを直接与えているか
- E. **allowedTools に "Task" が含まれているか**

めたん: 本ガイドの模擬試験から、1問いきますわ。コーディネーターが、サブエージェントを一度も起動しない。確認すべき点を2つ。
ずんだもん: 答えはBとEなのだ。{description|ディスクリプション}は、どのサブエージェントに委任するかを判断する材料なのだ。そして{allowedTools|アラウドツールズ}に{Task|タスク}がなければ、そもそも起動できないのだ。
めたん: Aの、会話履歴の共有は？
ずんだもん: そんな自動共有は、ないのだ。Cの{max_tokens|マックストークンズ}は無関係。Dは、さっきの逆効果のパターンなのだ。
