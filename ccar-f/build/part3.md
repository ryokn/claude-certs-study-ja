## 2. 分野3：Claude Codeの設定とワークフロー（Claude Code Configuration & Workflows）— 20%・約12問

シナリオ2（コード生成）、5（CI）、4（開発者生産性）で出ます。**「どのファイルに置くか」「誰に共有されるか」**が問われます。

### 3.1 適切な階層・スコープ・モジュール構成で CLAUDE.md を設定する

| スコープ | 場所 | 共有範囲 | 主な用途 |
|---|---|---|---|
| ユーザーレベル | `~/.claude/CLAUDE.md` | **自分だけ**（全プロジェクト）。VCSで共有されない | 個人の好み |
| プロジェクトレベル | `./CLAUDE.md` または `./.claude/CLAUDE.md` | **チーム**（コミットして共有） | アーキテクチャ、コーディング規約、共通ワークフロー |
| ディレクトリレベル | サブディレクトリの `CLAUDE.md` | そのディレクトリで作業する人 | その領域固有の規約 |
| （参考）ローカル | `./CLAUDE.local.md` | 自分だけ（.gitignore 推奨） | 個人のサンドボックスURL等 |
| （参考）管理ポリシー | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`、Linux `/etc/claude-code/CLAUDE.md` 等 | 組織全員 | 全社規約（IT配布） |

**現行ドキュメントの補足（Claude Code memory）**
- 作業ディレクトリ**より上**の CLAUDE.md / CLAUDE.local.md は起動時に読み込み。**サブディレクトリ**の CLAUDE.md は、Claude がそのディレクトリのファイルを読む/編集するときに**オンデマンド**で読み込み。
- 見つかったファイルは上書きではなく**連結**（ルート側が先、作業ディレクトリに近いものが後）。
- `@path/to/file` で**インポート**（相対パスはインポート元ファイル基準、再帰は最大4ホップ）。インポートは整理には役立つがコンテキスト量は減らない。
- 1ファイル200行未満が目安。`/compact` 後もプロジェクトルートの CLAUDE.md は再読込される（会話だけで伝えた指示は消え得る）。

**頻出ポイント / ひっかけ**
- ✅ 「新メンバーに指示が効かない」→ 指示が**ユーザーレベル**にある。**プロジェクトレベルに移してコミット**。
- ✅ `/memory` で読み込まれているメモリファイルを確認し、セッション間の挙動の不一致を診断。
- ✅ 巨大な CLAUDE.md は `.claude/rules/` のトピック別ファイル（`testing.md`、`api-conventions.md`、`deployment.md`）へ分割。パッケージごとに必要な規約だけ `@import`。
- ❌ 規約を `.claude/settings.json` に書く（settings は権限・フック・env 等の設定）。
- ❌ 共有したい規約を `CLAUDE.local.md` に置く。

```markdown
<!-- packages/billing/CLAUDE.md：必要な規約だけ取り込む -->
# Billing package
@../../docs/standards/money-handling.md
@../../docs/standards/api-errors.md
```

### 3.2 カスタムスラッシュコマンドとスキルを作成し設定する

| 種類 | プロジェクト（チーム共有・VCS） | ユーザー（個人） |
|---|---|---|
| スラッシュコマンド | `.claude/commands/<name>.md` → `/name` | `~/.claude/commands/` |
| スキル | `.claude/skills/<name>/SKILL.md` | `~/.claude/skills/<name>/SKILL.md` |

**SKILL.md のフロントマター（試験に出るもの）**

| フィールド | 意味（試験ガイド） | 補足（現行ドキュメント） |
|---|---|---|
| `context: fork` | スキルを**分離されたサブエージェントのコンテキスト**で実行し、出力がメイン会話を汚さない | サブエージェントは会話履歴を見ない（指示は自己完結に）。`agent` でサブエージェント種別を指定 |
| `allowed-tools` | スキル実行中のツールアクセスを制限（例：書き込み系に限定して破壊的操作を防ぐ） | 現行では「列挙ツールを許可プロンプトなしで使える」事前承認。除外は `disallowed-tools`（§0.3） |
| `argument-hint` | 引数なしで呼ばれたときに必須パラメータの入力を促す | オートコンプリートのヒント（例：`[issue-number]`）。本文では `$ARGUMENTS` / `$0` |
| （参考）`description` | — | Claude がいつ使うか判断する材料（推奨） |
| （参考）`disable-model-invocation: true` | — | Claude の自動起動を禁止し、`/name` の手動起動だけにする |

```markdown
---
name: analyze-deps
description: 依存関係を全体調査し、要約だけ返す
context: fork
argument-hint: [package-name]
allowed-tools: Read Grep Glob
---
$ARGUMENTS の依存関係を調べ、循環依存と未使用依存を表で要約する。
```

**頻出ポイント / ひっかけ**
- ✅ 全員がクローン/プルした時点で使える `/review` → **`.claude/commands/`（リポジトリ内）**（サンプル問題4）。
- ❌ `~/.claude/commands/`（個人用）、CLAUDE.md（コマンド定義の場所ではない）、`.claude/config.json` の commands 配列（**存在しない**）。
- ✅ 冗長な出力（コードベース分析）や探索的な出力（代替案のブレスト）→ `context: fork`。
- ✅ 個人用にカスタマイズしたいときは `~/.claude/skills/` に**別名で**作る（チームのスキルを上書きしない）。
- ✅ **スキル＝オンデマンド**（タスク固有のワークフロー） vs **CLAUDE.md＝常時読み込み**（全体共通の標準）。

### 3.3 パス固有のルール（path-specific rules）で規約を条件付きで読み込む

- `.claude/rules/*.md` の YAML フロントマター `paths` に glob パターン → **一致するファイルを扱うときだけ**読み込まれる（トークン節約・無関係な指示の排除）。
- `paths` なしのルールは起動時に常に読み込み（`.claude/CLAUDE.md` と同じ優先度）。
- 現行ドキュメント：Read/Write/Edit で一致ファイルを扱ったとき（単一ファイルへの `cat` 等も含む）にロード。`paths` は YAML リストまたはカンマ区切り文字列。ルールのフロントマターで読まれるのは `paths` のみ。

```markdown
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
---
# テスト規約
- describe/it は日本語で振る舞いを書く
- 外部APIは必ず msw でモックする
```

| 要件 | 最適解 |
|---|---|
| 規約が**ディレクトリをまたいで散在**するファイル種別に適用（テスト、*.tf） | `.claude/rules/` ＋ `paths` glob |
| 1つのディレクトリ配下だけの規約 | サブディレクトリ CLAUDE.md でも可（ただし散在ファイルには不向き） |
| 全員・常時に効く標準 | プロジェクト CLAUDE.md |
| 必要なときに呼ぶ手順 | スキル / コマンド |

- ❌ サンプル問題6の誤答：ルートCLAUDE.mdに見出しで集約（推測任せ）、スキル化（手動呼び出し依存）、各サブディレクトリにCLAUDE.md（散在に不向き）。

### 3.4 プランモード（plan mode）と直接実行（direct execution）の使い分け

| プランモード | 直接実行 |
|---|---|
| 大規模変更、**複数の有効なアプローチ**、アーキテクチャ上の判断、多ファイル修正 | 単純で範囲が明確（例：1関数にバリデーション1つ追加、スタックトレースが明確な単一ファイルのバグ修正） |
| 例：マイクロサービス再構成、45+ファイルのライブラリ移行、インフラ要件が違う統合方式の選択 | 例：日付バリデーションの条件分岐を追加 |

- プランモードは変更を確定する前に**安全に探索・設計**でき、手戻りを防ぐ。現行：`Shift+Tab` でモード切替、`claude --permission-mode plan`、`/plan`。承認するまで編集しない。
- **Explore サブエージェント**：読み取り専用の組み込みサブエージェント。冗長な調査出力を分離して要約だけ返し、メインのコンテキスト枯渇を防ぐ。
- ✅ **組み合わせ**：プランモードで調査・計画 → 直接実行で実装。
- ❌「直接実行で始めて、複雑になったらプランモードへ」（複雑さが要件時点で明らかなら最初からプラン。サンプル問題5）。
- ❌「詳細な事前指示を書いて直接実行」（コードを調べずに正しい構成を知っている前提）。

### 3.5 反復的な改良手法（iterative refinement）

| 手法 | 使う場面 |
|---|---|
| **具体的な入出力例を2〜3個** | 文章の説明が一貫して解釈されない変換 |
| **テスト駆動の反復** | 先にテスト（期待動作・エッジケース・性能要件）を書き、失敗を共有して改善 |
| **インタビューパターン** | 不慣れな領域で、実装前にClaudeに質問させ考慮事項（キャッシュ無効化戦略、障害モード）を洗い出す |
| **1メッセージにまとめて伝える** | 修正が**相互に影響する**複数の問題 |
| **順番に1つずつ** | **独立した**問題 |

- ✅ エッジケース（移行スクリプトのnull値など）は**入力例と期待出力つきの具体的テストケース**で伝える。

### 3.6 Claude Code を CI/CD パイプラインに統合する

| フラグ | 役割 |
|---|---|
| `-p` / `--print` | **非対話モード**。結果をstdoutに出して終了 → 入力待ちハングを防ぐ |
| `--output-format json` | 機械可読な出力（`text` / `json` / `stream-json`） |
| `--json-schema '<schema>'` | スキーマに一致する構造化出力（print モードのみ）。結果は `structured_output` フィールド |
| （参考）`--max-turns`、`--allowedTools`、`--append-system-prompt` | ターン上限、許可ツール、システムプロンプト追記 |

```bash
claude -p "このPRの差分をレビューし、バグとセキュリティ問題だけを報告" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"findings":{"type":"array","items":{"type":"object","properties":{"file":{"type":"string"},"line":{"type":"integer"},"severity":{"type":"string","enum":["high","medium","low"]},"issue":{"type":"string"},"fix":{"type":"string"}},"required":["file","line","severity","issue"]}}},"required":["findings"]}' \
  | jq '.structured_output.findings'
```

**頻出ポイント / ひっかけ**
- ✅ CIでハング → **`-p` を付ける**（サンプル問題10）。❌ `CLAUDE_HEADLESS=true`（存在しない）、❌ `--batch`（存在しない）、❌ `< /dev/null`（正しい方法ではない）。
- ✅ CI から呼ばれる Claude Code へのプロジェクト文脈（テスト標準、フィクスチャ規約、レビュー基準）は **CLAUDE.md** で渡す。
- ✅ 再レビュー時は**以前の指摘をコンテキストに含め、新規・未対応だけ報告**させて重複コメントを防ぐ。
- ✅ テスト生成には**既存テストファイルを渡して**重複シナリオを避ける。価値のあるテスト基準・利用可能なフィクスチャを CLAUDE.md に書く。
- ✅ **セッションコンテキストの分離**：コードを生成した同じセッションは自分の変更をレビューするのが苦手 → **独立したレビューインスタンス**（4.6）。

## 3. 分野4：プロンプトエンジニアリングと構造化出力（Prompt Engineering & Structured Output）— 20%・約12問

シナリオ5（CI）、6（構造化データ抽出）が中心。

### 4.1 明示的な基準で精度を高め、誤検知（false positives）を減らす

- ✅ 曖昧な指示より**明示的な基準**：「コメントが正確か確認」ではなく「**主張された動作が実際のコードの動作と矛盾する場合のみ**指摘」。
- ❌「保守的に判断せよ」「確信度の高いものだけ報告せよ」→ **カテゴリ別の具体的基準より効かない**。
- 誤検知の多いカテゴリが**正確なカテゴリへの信頼まで損なう** → 誤検知の多いカテゴリを**一時的に無効化**してプロンプトを改善。
- 重大度（severity）は**レベルごとに具体的なコード例**を付けて定義 → 分類が一貫。

### 4.2 few-shot プロンプティングで出力の一貫性と品質を高める

- 詳細な指示だけで一貫しないとき、**few-shot が最も効果的**（形式の一貫性）。
- 曖昧なケースの扱い（曖昧なリクエストでのツール選択、ブランチ単位のテストカバレッジ不足）を示す。**なぜその行動を選び、妥当な代替を選ばなかったか**の推論を含めた例を**2〜4個**。
- 出力形式（場所、問題、重大度、修正案）を例で示す。
- 許容されるパターンと本物の問題を区別する例 → 誤検知削減しつつ**新しいパターンへ汎化**。
- 抽出タスク：多様な文書構造（インライン引用 vs 参考文献リスト、方法論セクション vs 本文埋め込み）を例示 → **必須フィールドが空/nullになる問題**やハルシネーションを低減。
- ⚠️ サンプル問題2では「few-shot 5〜8件」は**不正解**（根本原因はツール説明の不足 → 説明の拡充が「最初の一手」）。few-shotは万能ではない。

### 4.3 ツール使用（tool_use）と JSON スキーマで構造化出力を強制する

| `tool_choice` | 挙動 | 使う場面 |
|---|---|---|
| `{"type":"auto"}`（ツールありの既定） | ツールを呼ぶか、テキストで答えるかをモデルが決める | 通常の対話エージェント |
| `{"type":"any"}` | **何らかのツールを必ず呼ぶ**（どれかは選べる） | 抽出スキーマが複数あり文書種別が不明なとき、構造化出力を保証 |
| `{"type":"tool","name":"extract_metadata"}` | **指定したツールを必ず呼ぶ** | 特定の抽出をエンリッチメントより先に確実に実行（後続はフォローアップのターンで） |
| `{"type":"none"}`（ツールなしの既定） | ツールを使わない | — |

- 現行APIの補足：`any`/`tool` のときAPIはアシスタント応答をプリフィルするので、tool_use の前に自然言語の説明は出ない。手動の拡張思考とは併用不可（§0.3）。
- **tool_use＋JSONスキーマ（strict）＝構文エラーを排除する最も信頼性の高い方法**。ただし**意味的エラー**（明細の合計が総額と合わない、値が別フィールドに入る）は防げない。
- スキーマ設計：
  - 文書に無いかもしれない情報は**任意（nullable）**に → 必須にすると**値を捏造**しがち。
  - 拡張可能なカテゴリは **enum ＋ `"other"` ＋ 詳細文字列**。曖昧なケースは `"unclear"`。
  - 書式がばらつくソースには、スキーマと**あわせて正規化ルールをプロンプトに**。
- 現行の structured outputs（JSON outputs / strict tool use）の制約例：オブジェクトは `additionalProperties: false`、数値の `minimum/maximum` や文字列長の制約は非対応（SDKヘルパーが変換）。enumの大文字小文字は保証されない。`stop_reason` が `refusal` や `max_tokens` のときはスキーマ不一致になり得る。

```json
{
  "name": "extract_invoice",
  "description": "請求書PDFのテキストから請求情報を抽出する。記載がない項目は null。",
  "strict": true,
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "invoice_number": {"type": "string"},
      "po_number": {"type": ["string", "null"]},
      "category": {"type": "string", "enum": ["software", "hardware", "maintenance", "other", "unclear"]},
      "category_detail": {"type": ["string", "null"]},
      "stated_total": {"type": "number"},
      "calculated_total": {"type": "number"},
      "conflict_detected": {"type": "boolean"}
    },
    "required": ["invoice_number", "po_number", "category", "category_detail", "stated_total", "calculated_total", "conflict_detected"]
  }
}
```
（「無いかもしれない」は `["string","null"]` の null 許容型か、`required` から外した任意プロパティで表現。現行の strict スキーマでは任意プロパティは全スキーマ合計24個、union 型は16個までという複雑さ上限がある＝Structured outputs ドキュメント）

### 4.4 検証・リトライ・フィードバックループ（validation, retry, feedback loops）

- **エラーフィードバック付きリトライ**：元の文書＋失敗した抽出結果＋**具体的な検証エラー**を渡して自己修正させる。
- **リトライの限界**：情報が**ソースに存在しない**（提供していない別添付にだけある等）場合は何度やっても無駄 → null・人間レビュー・資料の入手。
- リトライが効く：**形式の不一致、構造的な出力エラー**。
- **意味的な検証エラー**（合計不一致、フィールドの取り違え） vs **スキーマ構文エラー**（tool use で排除）。
- 自己修正フロー：`stated_total` と `calculated_total` を両方抽出して不一致を検出、`conflict_detected` ブール値。
- レビューの指摘に **`detected_pattern`** フィールド → 開発者が却下した指摘のパターンを体系的に分析（誤検知の改善）。

### 4.5 効率的なバッチ処理戦略（Message Batches API）

| 項目 | 内容 |
|---|---|
| コスト | **50%削減**（ガイド） |
| 処理時間 | **最大24時間の処理ウィンドウ、レイテンシSLAの保証なし**（多くは1時間以内に完了＝現行ドキュメント。ただし当てにしない） |
| 対応付け | **`custom_id`** でリクエストとレスポンスを対応（結果の順序に依存しない） |
| 非対応 | **単一リクエスト内でのマルチターンのツール呼び出し**（途中でツールを実行して結果を返せない） |
| 結果種別（現行） | `succeeded` / `errored` / `canceled` / `expired`。結果は作成から29日間取得可。1バッチ最大 100,000 リクエストまたは 256MB |

- ✅ ブロッキングなマージ前チェック → **同期API**。夜間レポート・週次監査・夜間テスト生成 → **バッチ**（サンプル問題11）。
- ✅ SLA計算：**送信間隔（最大待ち時間）＋24時間 ≦ SLA**。例：30時間SLA → 4時間ごとの送信なら最大28時間で満たす（ガイドの例）。
- ✅ 失敗は **custom_id で特定し、失敗分だけ**修正（例：コンテキスト超過の文書をチャンク分割）して再送信。
- ✅ 大量処理の前に**サンプルセットでプロンプトを改良**して初回成功率を上げる。
- ❌「両方バッチにして、遅ければリアルタイムにフォールバック」（不要な複雑さ）、❌「バッチは結果の順序が保証されないから使えない」（custom_id で解決）。

### 4.6 マルチインスタンス・マルチパスのレビューアーキテクチャ

- **セルフレビューの限界**：同じセッションは生成時の推論を保持し、自分の判断を疑いにくい。
- **独立したレビューインスタンス**（生成時の推論コンテキストなし）は、セルフレビュー指示や**拡張思考より**微妙な問題を見つけやすい。
- **マルチパス**：ファイル単位のローカル分析パス＋ファイル横断のデータフロー統合パス（注意の分散・矛盾した指摘を回避）。
- 各指摘に確信度を自己申告させる**検証パス** → キャリブレーションされたレビューのルーティング（※ 確信度は「ラベル付きデータでキャリブレーションして使う」前提。素の自己申告をそのまま信じるのはNG：5.2/5.5）。
