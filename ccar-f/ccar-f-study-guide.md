### 0.4 このガイドの使い方

1. **まず §0.3 と §7（サンプル問題の要点）を読む**：出題者の「正解の型」が分かります。
2. 各分野は「基礎（最小限）→ 頻出ポイント → ひっかけ → 比較表/コード」の順。**ひっかけ**の行だけ拾い読みしても効果があります。
3. §6 のシナリオ別ウォークスルーで「このシナリオなら何が問われるか」を予習。
4. 模擬試験（32問・目標64分）は `ccar-f-mock-exam.html` で時間を計って解き、同じHTMLで解答と解説を確認。スマホでも解けて、進捗が保存されます。
5. 前日〜当日は §9 のチェックリストだけ。

**この試験の「正解の型」（サンプル問題12問から抽出）**
- **根本原因に直接効く、最小で十分な対策**が正解（「最初の一手」なら低労力・高効果のもの）。
- **確実な遵守が必要 → プログラム（フック・前提条件ゲート）**、そうでなければプロンプト（明示的基準＋few-shot）。
- **過剰設計（分類器を別途学習、ルーティング層、上位モデルへの切替、多数決）はたいてい不正解**。
- **自己申告の確信度・感情分析は信頼できない指標**として扱われる。
- エラーは**握りつぶさず、全体も止めず、構造化して伝える**。
- コンテキストは**自動では共有されない**。必要なものは明示的・構造化して渡す。

## 1. 分野1：エージェントアーキテクチャとオーケストレーション（Agentic Architecture & Orchestration）— 27%・約16問

最重要分野。シナリオ1（サポート）、3（マルチエージェントリサーチ）、4（開発者生産性）で横断的に出ます。

### 1.1 自律的なタスク実行のためのエージェントループ（agentic loop）を設計し実装する

**基礎**
- ループ：Claudeにリクエスト → `stop_reason` を確認 → `"tool_use"` ならツールを実行 → `tool_result` を会話履歴に追加 → 次の反復。`"end_turn"` で終了。
- ツール結果を履歴に追加するから、モデルは新しい情報を踏まえて次のアクションを**モデル主導で**決められる（事前に決めた決定木・固定のツール順序との違い）。

**現行APIの事実（Claude API ドキュメント）**
- `stop_reason` の値：`end_turn` / `max_tokens` / `stop_sequence` / `tool_use` / `pause_turn`（サーバーツールのループが反復上限に達した。応答をそのまま送り返して続行）/ `refusal` / `model_context_window_exceeded`。
- `tool_result` は対応する `tool_use` の**直後のユーザーメッセージ**に置き、その content 配列では **tool_result ブロックを先頭**に（テキストは後ろ）。`tool_use_id` で対応付け、失敗時は `is_error: true`。
- 1つの応答に複数の `tool_use`（並列ツール呼び出し）が入ることがある → 全部実行して、結果を**1つのユーザーメッセージ**にまとめて返す。

```python
# 最小のエージェントループ（Claude API / Python SDK）
messages = [{"role": "user", "content": user_input}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=2048,
                                  system=SYSTEM, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})  # 履歴に必ず追加
    if resp.stop_reason == "tool_use":
        results = []
        for b in resp.content:
            if b.type == "tool_use":
                out, err = run_tool(b.name, b.input)
                results.append({"type": "tool_result", "tool_use_id": b.id,
                                "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})  # tool_result を先頭に
        continue
    break  # end_turn（max_tokens 等は別途ハンドリング）
```

**頻出ポイント / ひっかけ**
- ✅ 継続/終了は **stop_reason** で判定。
- ❌「応答に "完了" が含まれたら終了」＝**自然言語シグナルの解析**（アンチパターン）。
- ❌「反復上限◯回を**主要な**停止メカニズムにする」（安全装置として併用は可。主役にしない）。
- ❌「アシスタントの**テキストがあれば完了**」。テキストと tool_use は同じ応答に同居し得る。
- ❌ ツール結果を履歴に追加しない／前回までの履歴を送らない（APIはステートレス。毎回**完全な会話履歴**を送る＝タスク5.1）。

### 1.2 コーディネーター・サブエージェントパターン（coordinator-subagent）でオーケストレーションする

**基礎**
- **ハブアンドスポーク（hub-and-spoke）**：コーディネーターがサブエージェント間の通信・エラー処理・情報ルーティングを**すべて**管理。
- サブエージェントは**分離されたコンテキスト**で動き、コーディネーターの会話履歴を自動では継承しない。
- コーディネーターの役割：タスク分解、委任、結果の集約、**クエリの複雑さに応じて呼ぶサブエージェントを決める**。

**頻出ポイント / ひっかけ**
- ✅ 毎回全パイプラインを回さず、**必要なサブエージェントだけを動的に選択**。
- ✅ リサーチ範囲を**サブトピックや情報源の種類で分割**して重複を最小化。
- ✅ **反復的改善ループ**：統合結果の不足をコーディネーターが評価 → 的を絞ったクエリで検索/分析に再委任 → 統合を再実行（カバレッジが十分になるまで）。
- ✅ 通信は**すべてコーディネーター経由**（可観測性・一貫したエラー処理・制御された情報フロー）。
- ⚠️ **分解が狭すぎる**と網羅性が落ちる（サンプル問題7：「クリエイティブ産業」をビジュアルアートだけに分解）。下流のエージェントが正しく動いていても、**割り当て自体**が原因。
- ❌ サブエージェント同士が直接呼び合う設計（観測・エラー処理が分散）。

### 1.3 サブエージェントの呼び出し、コンテキストの受け渡し、生成（spawning）を設定する

**基礎**
- サブエージェントは **Task ツール**で生成（現行名 `Agent`）。コーディネーターの **`allowedTools` に `"Task"` が必要**。
- **AgentDefinition**：`description`（いつ使うか＝委任判断の材料・必須）、`prompt`（そのエージェントのシステムプロンプト・必須）、`tools`（ツール制限。省略時は継承）、`model` など。
- 親から子に渡るのは**Taskツールのプロンプト文字列だけ**（＋そのエージェント自身のシステムプロンプト、プロジェクトCLAUDE.md、ツール定義）。親の会話履歴・ツール結果・親のシステムプロンプトは渡らない（現行SDKドキュメント）。
- **フォーク（fork）**ベースのセッション管理：共通の分析ベースラインから異なるアプローチを探る。

```python
# Agent SDK（Python）：コーディネーター＋サブエージェント定義（現行ドキュメントの形）
options = ClaudeAgentOptions(
    allowed_tools=["Task", "Read", "Grep"],   # 試験ガイドの表記は "Task"（現行は "Agent"）
    agents={
        "web-searcher": AgentDefinition(
            description="ウェブ検索専門。最新の公開情報が必要なときに使う",
            prompt="あなたはウェブ調査担当。各発見に claim, excerpt, url, published_at を付けて返す",
            tools=["WebSearch", "WebFetch"]),
        "synthesizer": AgentDefinition(
            description="複数の調査結果を出典付きで統合する",
            prompt="受け取った claim-source の対応を保持したまま統合する",
            tools=["Read"]),
    })
```

**頻出ポイント / ひっかけ**
- ✅ 先行エージェントの**調査結果全体**を、次のサブエージェントの**プロンプトに直接**含める（例：検索結果＋文書分析を統合エージェントへ）。
- ✅ 内容と**メタデータ（URL・文書名・ページ番号）を分けた構造化形式**で渡し、出典の帰属を保持。
- ✅ **並列実行＝コーディネーターの1つの応答で複数のTask呼び出しを出す**（別々のターンに分けない）。
- ✅ コーディネーターのプロンプトは**手順の羅列ではなく、目標と品質基準**を伝える（サブエージェントが適応できる）。
- ❌「サブエージェントは親の履歴を参照できる/メモリを共有する」→ 誤り。
- ❌ 委任されない問題に「コーディネーターにも同じツールを与える」→ 逆効果。

### 1.4 強制とハンドオフのパターンで複数ステップのワークフローを実装する

**基礎**
- **プログラムによる強制（programmatic enforcement：フック、前提条件ゲート）** vs **プロンプトベースのガイダンス**。
- 決定論的な遵守が必要（例：金銭操作の前の本人確認）なとき、**プロンプト指示だけでは失敗率がゼロにならない**。
- 途中エスカレーション用の**構造化ハンドオフ**：顧客の詳細、根本原因の分析、推奨アクション。

| 判断軸 | プログラムによる強制（フック/ゲート） | プロンプト（指示・few-shot） |
|---|---|---|
| 保証 | 決定論的（必ず守られる） | 確率的（たまに破られる） |
| 使う場面 | 金銭・本人確認・コンプライアンス・不可逆操作 | 口調、判断基準、曖昧なケースの扱い |
| 例 | get_customer が検証済みIDを返すまで process_refund をブロック | 「エスカレーション基準＋few-shot」 |

**頻出ポイント / ひっかけ**
- ✅ サンプル問題1：12%で本人確認をスキップ → **プログラムによる前提条件**が正解。プロンプト強化・few-shot は確率的なので不十分、ルーティング分類器は「順序」ではなく「利用可否」の対策でズレ。
- ✅ 複数の懸案を含むリクエスト → **個別の項目に分解し、共有コンテキストで並列に調査 → 統一された回答に統合**。
- ✅ 人間の担当者は**会話記録を見られない**前提 → 顧客ID・根本原因・返金額・推奨アクションを**構造化サマリー**で渡す。

### 1.5 Agent SDK のフック（hooks）でツール呼び出しのインターセプトとデータ正規化を行う

**基礎**
- **PostToolUse**：ツール結果をモデルが処理する**前に**インターセプトして変換（正規化、トリミング）。
- **ツール呼び出しのインターセプト（PreToolUse）**：送信前の呼び出しを検査して、ポリシー違反をブロック（例：しきい値超の返金）→ 代替ワークフロー（人間へのエスカレーション）へ誘導。
- フック＝**決定論的な保証**、プロンプト＝**確率的な遵守**。

**現行SDKの事実（Agent SDK hooks ドキュメント）**
- 主なイベント：`PreToolUse`（ブロック/入力変更可）、`PostToolUse`、`PostToolUseFailure`、`UserPromptSubmit`、`Stop`、`SubagentStart`、`SubagentStop`、`PreCompact`、`PermissionRequest`、`Notification`、`SessionStart`/`SessionEnd`（後者2つはTypeScriptのみ）。
- `PreToolUse` の `hookSpecificOutput` で `permissionDecision`（`allow`/`deny`/`ask`/`defer`）、`permissionDecisionReason`（モデルに理由が伝わる）、`updatedInput`。複数フックの判定が割れたら **deny が最優先**。
- `PostToolUse` は `additionalContext`（結果に情報を追記）や `updatedToolOutput`（結果を置換）。
- matcher はツール名（`"Write|Edit"` など）。MCPツールは `mcp__<server>__<tool>`。
- Claude Code の設定ファイル版フック（コマンドフック）では **exit code 2 でブロック**（PreToolUse など、ブロック可能なイベント）。

```python
# $500超の返金をブロックしてエスカレーションへ誘導（Agent SDK / Python）
async def refund_guard(input_data, tool_use_id, context):
    amt = input_data["tool_input"].get("amount", 0)
    if amt > 500:
        return {"hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": "$500超は人間の承認が必要。escalate_to_human で引き継ぐこと"}}
    return {}  # 許可（変更なし）

options = ClaudeAgentOptions(hooks={
    "PreToolUse": [HookMatcher(matcher="mcp__support__process_refund", hooks=[refund_guard])],
    # "PostToolUse": [HookMatcher(matcher="mcp__.*", hooks=[normalize_timestamps])],  # 結果の正規化
})
```

**頻出ポイント / ひっかけ**
- ✅ 異種フォーマット（Unixタイムスタンプ、ISO 8601、数値ステータスコード）の正規化 → **PostToolUse**。
- ❌ 正規化に **PreToolUse** を選ぶ（入力側。結果は変えられない）。
- ❌ 禁止操作を **PostToolUse で事後に取り消す**（もう実行済み）。
- ❌「プロンプトを大文字・太字・繰り返しで強調」→ 確率的。

### 1.6 複雑なワークフローのためのタスク分解戦略を設計する

| | 固定の逐次パイプライン（プロンプトチェーン, prompt chaining） | 動的で適応的な分解（dynamic decomposition） |
|---|---|---|
| 向いている | 予測可能な多面的レビュー（例：ファイルごとの分析 → ファイル横断の統合パス） | オープンエンドな調査（例：レガシーに包括的なテストを追加） |
| 進め方 | 手順が事前に決まっている | 構造把握 → 影響の大きい領域特定 → 優先順位付き計画 → 発見に応じて適応 |

- ✅ 大規模コードレビューは**ファイル単位のローカル分析パス＋別途のファイル横断統合パス**（注意の分散＝attention dilution を回避）。サンプル問題12。
- ❌ 「全部まとめて1回で」「上位モデルで1パス」「3回やって多数決」。

### 1.7 セッションの状態、再開（resume）、フォーク（fork）を管理する

**基礎**
- `--resume <session-name>`：名前付きセッションの再開（Claude Code CLI。`--name`/`-n` で名前を付け、`claude --resume <name>`）。
- `fork_session`：共通の分析ベースラインから独立したブランチを作り、異なるアプローチを比較（CLIは `--fork-session` を `--resume`/`--continue` と併用。SDKはオプションで fork）。フォークは**会話履歴の分岐であってファイルシステムの分岐ではない**（現行SDKドキュメント）。
- コード変更後に再開するなら、**変更されたファイルを具体的に伝えて**的を絞った再分析。
- **古いツール結果を抱えて再開するより、構造化サマリーを注入して新規セッション**の方が信頼性が高い場合がある。

| 状況 | 選択 |
|---|---|
| 以前のコンテキストがおおむね有効、変更は一部 | **再開**＋変更ファイルを具体的に伝える |
| 以前のツール結果が大きく古くなった | **新規セッション＋構造化サマリーの注入** |
| 同じ分析から2つの戦略を比較したい | **fork_session** |

### 3.2 カスタムスラッシュコマンドとスキルを作成し設定する

| 種類 | プロジェクト（チーム共有・VCS） | ユーザー（個人） |
|---|---|---|

**SKILL.md のフロントマター（試験に出るもの）**

| フィールド | 意味（試験ガイド） | 補足（現行ドキュメント） |
|---|---|---|
| `context: fork` | スキルを**分離されたサブエージェントのコンテキスト**で実行し、出力がメイン会話を汚さない | サブエージェントは会話履歴を見ない（指示は自己完結に）。`agent` でサブエージェント種別を指定 |

### 3.3 パス固有のルール（path-specific rules）で規約を条件付きで読み込む

- `.claude/rules/*.md` の YAML フロントマター `paths` に glob パターン → **一致するファイルを扱うときだけ**読み込まれる（トークン節約・無関係な指示の排除）。
- `paths` なしのルールは起動時に常に読み込み（`.claude/CLAUDE.md` と同じ優先度）。
- 現行ドキュメント：Read/Write/Edit で一致ファイルを扱ったとき（単一ファイルへの `cat` 等も含む）にロード。`paths` は YAML リストまたはカンマ区切り文字列。ルールのフロントマターで読まれるのは `paths` のみ。

```markdown
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
---
# テスト規約
- describe/it は日本語で振る舞いを書く
- 外部APIは必ず msw でモックする
```

| 要件 | 最適解 |
|---|---|
| 規約が**ディレクトリをまたいで散在**するファイル種別に適用（テスト、*.tf） | `.claude/rules/` ＋ `paths` glob |
| 1つのディレクトリ配下だけの規約 | サブディレクトリ CLAUDE.md でも可（ただし散在ファイルには不向き） |
| 全員・常時に効く標準 | プロジェクト CLAUDE.md |
| 必要なときに呼ぶ手順 | スキル / コマンド |

| プランモード | 直接実行 |
|---|---|

- プランモードは変更を確定する前に**安全に探索・設計**でき、手戻りを防ぐ。現行：`Shift+Tab` でモード切替、`claude --permission-mode plan`、`/plan`。承認するまで編集しない。

### 3.5 反復的な改良手法（iterative refinement）

| 手法 | 使う場面 |
|---|---|
| **具体的な入出力例を2〜3個** | 文章の説明が一貫して解釈されない変換 |

| **順番に1つずつ** | **独立した**問題 |

- ✅ エッジケース（移行スクリプトのnull値など）は**入力例と期待出力つきの具体的テストケース**で伝える。

## 3. 分野4：プロンプトエンジニアリングと構造化出力（Prompt Engineering & Structured Output）— 20%・約12問

シナリオ5（CI）、6（構造化データ抽出）が中心。

### 4.1 明示的な基準で精度を高め、誤検知（false positives）を減らす

- ✅ 曖昧な指示より**明示的な基準**：「コメントが正確か確認」ではなく「**主張された動作が実際のコードの動作と矛盾する場合のみ**指摘」。
- ❌「保守的に判断せよ」「確信度の高いものだけ報告せよ」→ **カテゴリ別の具体的基準より効かない**。
- 誤検知の多いカテゴリが**正確なカテゴリへの信頼まで損なう** → 誤検知の多いカテゴリを**一時的に無効化**してプロンプトを改善。
- 重大度（severity）は**レベルごとに具体的なコード例**を付けて定義 → 分類が一貫。

### 4.2 few-shot プロンプティングで出力の一貫性と品質を高める

- 詳細な指示だけで一貫しないとき、**few-shot が最も効果的**（形式の一貫性）。
- 曖昧なケースの扱い（曖昧なリクエストでのツール選択、ブランチ単位のテストカバレッジ不足）を示す。**なぜその行動を選び、妥当な代替を選ばなかったか**の推論を含めた例を**2〜4個**。
- 出力形式（場所、問題、重大度、修正案）を例で示す。
- 許容されるパターンと本物の問題を区別する例 → 誤検知削減しつつ**新しいパターンへ汎化**。
- 抽出タスク：多様な文書構造（インライン引用 vs 参考文献リスト、方法論セクション vs 本文埋め込み）を例示 → **必須フィールドが空/nullになる問題**やハルシネーションを低減。
- ⚠️ サンプル問題2では「few-shot 5〜8件」は**不正解**（根本原因はツール説明の不足 → 説明の拡充が「最初の一手」）。few-shotは万能ではない。

### 4.3 ツール使用（tool_use）と JSON スキーマで構造化出力を強制する

| `tool_choice` | 挙動 | 使う場面 |
|---|---|---|
| `{"type":"auto"}`（ツールありの既定） | ツールを呼ぶか、テキストで答えるかをモデルが決める | 通常の対話エージェント |
| `{"type":"any"}` | **何らかのツールを必ず呼ぶ**（どれかは選べる） | 抽出スキーマが複数あり文書種別が不明なとき、構造化出力を保証 |
| `{"type":"tool","name":"extract_metadata"}` | **指定したツールを必ず呼ぶ** | 特定の抽出をエンリッチメントより先に確実に実行（後続はフォローアップのターンで） |
| `{"type":"none"}`（ツールなしの既定） | ツールを使わない | — |

- 現行APIの補足：`any`/`tool` のときAPIはアシスタント応答をプリフィルするので、tool_use の前に自然言語の説明は出ない。手動の拡張思考とは併用不可（§0.3）。
- **tool_use＋JSONスキーマ（strict）＝構文エラーを排除する最も信頼性の高い方法**。ただし**意味的エラー**（明細の合計が総額と合わない、値が別フィールドに入る）は防げない。
- スキーマ設計：
  - 文書に無いかもしれない情報は**任意（nullable）**に → 必須にすると**値を捏造**しがち。
  - 拡張可能なカテゴリは **enum ＋ `"other"` ＋ 詳細文字列**。曖昧なケースは `"unclear"`。
  - 書式がばらつくソースには、スキーマと**あわせて正規化ルールをプロンプトに**。
- 現行の structured outputs（JSON outputs / strict tool use）の制約例：オブジェクトは `additionalProperties: false`、数値の `minimum/maximum` や文字列長の制約は非対応（SDKヘルパーが変換）。enumの大文字小文字は保証されない。`stop_reason` が `refusal` や `max_tokens` のときはスキーマ不一致になり得る。

```json
{
  "name": "extract_invoice",
  "description": "請求書PDFのテキストから請求情報を抽出する。記載がない項目は null。",
  "strict": true,
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "invoice_number": {"type": "string"},
      "po_number": {"type": ["string", "null"]},
      "category": {"type": "string", "enum": ["software", "hardware", "maintenance", "other", "unclear"]},
      "category_detail": {"type": ["string", "null"]},
      "stated_total": {"type": "number"},
      "calculated_total": {"type": "number"},
      "conflict_detected": {"type": "boolean"}
    },
    "required": ["invoice_number", "po_number", "category", "category_detail", "stated_total", "calculated_total", "conflict_detected"]
  }
}
```
（「無いかもしれない」は `["string","null"]` の null 許容型か、`required` から外した任意プロパティで表現。現行の strict スキーマでは任意プロパティは全スキーマ合計24個、union 型は16個までという複雑さ上限がある＝Structured outputs ドキュメント）

### 4.4 検証・リトライ・フィードバックループ（validation, retry, feedback loops）

- **エラーフィードバック付きリトライ**：元の文書＋失敗した抽出結果＋**具体的な検証エラー**を渡して自己修正させる。
- **リトライの限界**：情報が**ソースに存在しない**（提供していない別添付にだけある等）場合は何度やっても無駄 → null・人間レビュー・資料の入手。
- リトライが効く：**形式の不一致、構造的な出力エラー**。
- **意味的な検証エラー**（合計不一致、フィールドの取り違え） vs **スキーマ構文エラー**（tool use で排除）。
- 自己修正フロー：`stated_total` と `calculated_total` を両方抽出して不一致を検出、`conflict_detected` ブール値。
- レビューの指摘に **`detected_pattern`** フィールド → 開発者が却下した指摘のパターンを体系的に分析（誤検知の改善）。

### 4.5 効率的なバッチ処理戦略（Message Batches API）

| 項目 | 内容 |
|---|---|
| コスト | **50%削減**（ガイド） |
| 処理時間 | **最大24時間の処理ウィンドウ、レイテンシSLAの保証なし**（多くは1時間以内に完了＝現行ドキュメント。ただし当てにしない） |
| 対応付け | **`custom_id`** でリクエストとレスポンスを対応（結果の順序に依存しない） |
| 非対応 | **単一リクエスト内でのマルチターンのツール呼び出し**（途中でツールを実行して結果を返せない） |
| 結果種別（現行） | `succeeded` / `errored` / `canceled` / `expired`。結果は作成から29日間取得可。1バッチ最大 100,000 リクエストまたは 256MB |

- ✅ ブロッキングなマージ前チェック → **同期API**。夜間レポート・週次監査・夜間テスト生成 → **バッチ**（サンプル問題11）。
- ✅ SLA計算：**送信間隔（最大待ち時間）＋24時間 ≦ SLA**。例：30時間SLA → 4時間ごとの送信なら最大28時間で満たす（ガイドの例）。
- ✅ 失敗は **custom_id で特定し、失敗分だけ**修正（例：コンテキスト超過の文書をチャンク分割）して再送信。
- ✅ 大量処理の前に**サンプルセットでプロンプトを改良**して初回成功率を上げる。
- ❌「両方バッチにして、遅ければリアルタイムにフォールバック」（不要な複雑さ）、❌「バッチは結果の順序が保証されないから使えない」（custom_id で解決）。

### 4.6 マルチインスタンス・マルチパスのレビューアーキテクチャ

- **セルフレビューの限界**：同じセッションは生成時の推論を保持し、自分の判断を疑いにくい。
- **独立したレビューインスタンス**（生成時の推論コンテキストなし）は、セルフレビュー指示や**拡張思考より**微妙な問題を見つけやすい。
- **マルチパス**：ファイル単位のローカル分析パス＋ファイル横断のデータフロー統合パス（注意の分散・矛盾した指摘を回避）。
- 各指摘に確信度を自己申告させる**検証パス** → キャリブレーションされたレビューのルーティング（※ 確信度は「ラベル付きデータでキャリブレーションして使う」前提。素の自己申告をそのまま信じるのはNG：5.2/5.5）。

## 4. 分野2：ツール設計とMCP統合（Tool Design & MCP Integration）— 18%・約11問

### 2.1 明確な説明と境界を備えたツールインターフェースを設計する

- **ツールの説明（description）はLLMがツールを選ぶ主要な手がかり**。最小限の説明では類似ツール間の選択が不安定。
- 説明に入れるもの：**入力形式、クエリ例、エッジケース、境界（似たツールではなくこれを使う場面／使わない場面）**、出力。
- 曖昧・重複した説明 → 誤ルーティング（例：ほぼ同じ説明の `analyze_content` と `analyze_document`）。
- **システムプロンプトのキーワードに敏感な指示**が、良いツール説明を上書きして意図しない関連付けを生むことがある → レビューする。

| 改善パターン | 例 |
|---|---|
| 改名＋説明更新で重複解消 | `analyze_content` → `extract_web_results`（ウェブ専用の説明） |
| 汎用ツールを目的別に分割（入出力の契約を定義） | `analyze_document` → `extract_data_points` / `summarize_content` / `verify_claim_against_source` |

```json
{"name": "lookup_order",
 "description": "注文番号（例: #12345, A-1029）から注文の状態・明細・配送状況を取得する。顧客の本人確認や連絡先の取得には使わない（それは get_customer）。注文番号が不明なら先に get_customer で顧客IDを得てから customer_id で検索する。",
 "input_schema": {"type": "object", "properties": {
   "order_id": {"type": "string", "description": "#を除いた注文番号"},
   "customer_id": {"type": "string"}}, "required": []}}
```

- ✅ サンプル問題2：説明が最小限 → **説明を拡充**が「最も効果的な最初の一手」。❌ few-shot 5〜8件（トークン増で根本未解決）、❌ キーワードのルーティング層（過剰設計）、△ 統合（妥当だが最初の一手には重い）。

### 2.2 MCPツールの構造化されたエラーレスポンスを実装する

- MCPの **`isError` フラグ**でツール失敗をエージェントに伝える（MCP仕様：プロトコルエラーはJSON-RPCエラー、**ツール実行エラーはツール結果の `isError: true`**）。

| 種類 | 例 | リトライ |
|---|---|---|
| 一時的（transient） | タイムアウト、サービス利用不可 | 可（ローカルで） |
| 検証（validation） | 無効な入力 | 入力を直せば可 |
| ビジネス（business） | ポリシー違反（返品期限切れ） | **不可**（`retriable: false`＋顧客向け説明） |
| 権限（permission） | 権限不足 | 不可（エスカレーション等） |

```json
{"isError": true,
 "content": [{"type": "text", "text": "{\"errorCategory\":\"business\",\"isRetryable\":false,\"message\":\"返品受付期間（30日）を過ぎています\",\"customerMessage\":\"恐れ入りますが、お受け取りから30日を過ぎているため返品をお受けできません\"}"}]}
```

- ❌ 一律の `"Operation failed"` → 適切な復旧判断ができない。
- ✅ サブエージェントは一時的な失敗を**ローカルで復旧**し、解決できないものだけを**部分結果と試行内容つき**でコーディネーターへ。
- ✅ **アクセス失敗**（リトライ判断が必要）と**有効な空の結果**（検索は成功、該当なし）を区別。

### 2.3 エージェント間でツールを適切に配分し、ツール選択を設定する

- ツールが多すぎる（例：**4〜5個ではなく18個**）と選択の信頼性が下がる。
- 専門外のツールを持つと誤用する（統合エージェントがウェブ検索を始める）。
- **スコープを限定したツールアクセス**：役割に必要なものだけ＋頻度の高い特定ニーズにだけ役割横断ツール（例：統合エージェントに `verify_fact`。複雑なものはコーディネーター経由）＝サンプル問題9。
- 汎用ツールを**制約付き**の代替に（`fetch_url` → ドキュメントURLを検証する `load_document`）。
- `tool_choice`：`"auto"` / `"any"` / 強制 `{"type":"tool","name":"..."}`（表は §4.3）。強制で最初のツールを確定 → 後続はフォローアップのターン。`"any"` で「会話テキストではなく必ずツール」。

### 2.4 MCPサーバーを Claude Code とエージェントワークフローに統合する

| 目的 | 置き場所 |
|---|---|
| チーム共有のツール | **プロジェクトスコープ：`.mcp.json`**（リポジトリにコミット） |
| 個人用・実験的なサーバー | **ユーザースコープ：`~/.claude.json`** |
| シークレット | `.mcp.json` で **`${GITHUB_TOKEN}`** のような**環境変数展開**（`${VAR:-default}` も可）。`command`/`args`/`env`/`url`/`headers` で使える |

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {"Authorization": "Bearer ${GITHUB_TOKEN}"}
    }
  }
}
```
```bash
claude mcp add --transport http my-exp https://example.com/mcp --scope user   # 個人用
```

- 設定された**すべてのMCPサーバーのツールが接続時に検出され、同時に利用可能**。
- **MCPリソース（resources）**：コンテンツカタログ（課題サマリー、ドキュメント階層、DBスキーマ）を公開して**探索的なツール呼び出しを減らす**。ツール＝アクション、リソース＝読むためのデータ。Claude Code では `@server:protocol://path` で参照可能（現行ドキュメント）。
- ✅ MCPツールの説明を充実させ、エージェントが**組み込みツール（Grepなど）を優先してしまう**のを防ぐ。
- ✅ 標準的な統合（Jiraなど）は**既存のコミュニティMCPサーバー**、カスタムはチーム固有ワークフローに。
- 現行補足：`.mcp.json` のサーバーは初回に承認が必要。同名サーバーが複数スコープにあると local > project > user の優先順位。

### 2.5 組み込みツール（Read, Write, Edit, Bash, Grep, Glob）を効果的に選ぶ

| ツール | 用途 | 例 |
|---|---|---|
| **Grep** | ファイル**内容**の検索 | 関数の全呼び出し元、エラーメッセージの発生箇所、import文 |
| **Glob** | ファイル**パス/名前**のパターン一致 | `**/*.test.tsx` |
| **Read / Write** | ファイル全体の読み込み/書き込み | — |
| **Edit** | **一意なテキスト一致**による的を絞った変更 | — |
| **Bash** | コマンド実行 | テスト実行など |

- ✅ Edit が「一致が一意でない」で失敗 → **Read で全体を読み込み、Write で書き戻す**フォールバック（ガイド）。
- ✅ 最初に全ファイルを読まない：**Grep でエントリポイント → Read で import をたどる**段階的理解。
- ✅ ラッパーモジュール越しの使用箇所：まず**エクスポート名をすべて特定 → 各名前で Grep**。
- ❌ 内容検索に Glob、ファイル名探しに Grep。

## 5. 分野5：コンテキスト管理と信頼性（Context Management & Reliability）— 15%・約9問

### 5.1 長いやり取りで重要情報を保持するために会話コンテキストを管理する

- **段階的な要約のリスク**：数値・パーセンテージ・日付・顧客が述べた期待が曖昧になる。
- **lost in the middle**：長い入力の冒頭と末尾はよく処理されるが、中間を見落とすことがある。
- ツール結果は関連性に見合わないトークンを消費（注文照会で40+フィールド返るが必要なのは5つ）。
- 後続のAPIリクエストでは**完全な会話履歴**を渡す。

| 対策 | 内容 |
|---|---|
| **ケースの事実情報（case facts）ブロック** | 金額・日付・注文番号・ステータスを、要約される履歴の外に置き毎回のプロンプトに含める |
| 構造化された課題データ層 | 複数案件のセッションで注文ID・金額・ステータスを別レイヤーに永続化 |
| ツール出力のトリミング | 蓄積する**前に**関連フィールドだけに（PostToolUse フックで実装しやすい） |
| 位置を考慮した配置 | 集約入力の**冒頭に主要な発見の要約**、詳細は明示的なセクション見出しで整理 |
| 上流エージェントの出力を構造化 | 冗長な文章・推論チェーンではなく、主要な事実・引用・関連性スコア・メタデータ（日付、出典、方法論） |

- 現行API補足（範囲外寄り・存在だけ）：**コンテキスト編集（context editing。古いツール結果のクリア、ベータ）**、**コンパクション（compaction）**、Claude Code の `/compact`。プロンプトキャッシング（`cache_control`、既定5分TTL・1時間オプション）は「存在を知っている」レベルでよい（ガイド範囲外の詳細）。

### 5.2 効果的なエスカレーションと曖昧さの解消のパターン

| 状況 | 正しい行動 |
|---|---|
| 顧客が**人間を明示的に要求** | **直ちにエスカレーション**（先に調査しない） |
| 不満を示すが問題は対応可能 | 不満を受け止め**解決を申し出る**。**重ねて**人間を希望したらエスカレーション |
| ポリシーが**曖昧/何も定めていない**（例：自社サイトの価格調整しか規定がないのに競合価格マッチを要求） | エスカレーション |
| 有意義な進展が得られない | エスカレーション |
| ツール結果が**複数の顧客に一致** | ヒューリスティックで選ばず、**追加の識別情報を尋ねる** |

- ✅ エスカレーション基準を**few-shot付きでシステムプロンプトに明示**（サンプル問題3）。
- ❌ **感情分析**ベース、❌ **自己申告の確信度**ベース（実際のケースの複雑さの指標として信頼できない）、❌ 別の分類器モデル（プロンプト改善前の過剰設計）。
- ⚠️ トリガーは「複雑なケース」ではなく「**ポリシーの例外/空白**」。

### 5.3 マルチエージェントシステム全体でのエラー伝播戦略

- ✅ **構造化されたエラーコンテキスト**：失敗の種類、試行したクエリ、部分的な結果、代替アプローチ → コーディネーターが「別クエリでリトライ/代替/部分結果で続行」を判断（サンプル問題8）。
- ❌ 汎用ステータス（「検索を利用できません」）は情報を隠す。
- ❌ **エラーの握りつぶし**（空結果を成功として返す）と ❌ **単一の失敗でワークフロー全体を終了**、の**両方**がアンチパターン。
- ✅ アクセス失敗と有効な空結果を区別。ローカルで復旧できるものはサブエージェント内で。
- ✅ 統合出力に**カバレッジの注記**（十分に裏付けのある知見／情報源が使えず不足している領域）。

```json
{"status": "partial_failure", "failureType": "timeout", "attemptedQuery": "AI music generation market 2025",
 "partialResults": [{"claim": "...", "url": "...", "published_at": "2025-03-01"}],
 "alternatives": ["業界団体レポートで検索", "期間を2024年に広げる"], "retriedLocally": 2}
```

### 5.4 大規模なコードベース探索でコンテキストを効果的に管理する

- **コンテキストの劣化**：長時間セッションで回答が一貫しなくなり、以前見つけた具体的なクラスではなく「典型的なパターン」に言及しだす。
- ✅ **スクラッチパッドファイル**に主要な発見を記録し、以降の質問で参照。
- ✅ 特定の問い（「すべてのテストファイルを見つける」「返金フローの依存関係をたどる」）を**サブエージェント**に委譲し、メインは高レベルの調整に専念。
- ✅ フェーズ間で**主要な発見を要約**し、次フェーズのサブエージェントの初期コンテキストに注入。
- ✅ **クラッシュ復旧**：各エージェントが既知の場所に状態をエクスポート → コーディネーターが再開時に**マニフェスト**を読み込み、プロンプトに注入。
- ✅ 冗長な調査出力でコンテキストが埋まったら **`/compact`**（現行：任意で要約の焦点を指示できる `/compact [instructions]`）。

### 5.5 人間によるレビューのワークフローと確信度のキャリブレーション

- 全体の精度（例：97%）が、**特定の文書種別やフィールドの低性能を覆い隠す**リスク。
- ✅ **層化無作為抽出（stratified random sampling）**で高確信度の抽出のエラー率を継続測定、新しいエラーパターンを検出。
- ✅ **フィールド単位の確信度**を出させ、**ラベル付き検証セットでキャリブレーション**してしきい値を決める。
- ✅ 人間のレビューを減らす前に、**文書種別・フィールド別に**一貫した性能を確認。
- ✅ 確信度が低い／ソースが曖昧・矛盾 → 人間レビューへ（限られたレビュー担当者の工数に優先度）。

### 5.6 複数情報源の統合で情報の出所（provenance）を保持し不確実性に対処する

- 要約のステップで **claim と source の対応**が失われると出典の帰属が消える → サブエージェントに**構造化された主張と情報源の対応付け（URL、文書名、関連する抜粋）**を出させ、統合でも保持・マージ。
- 信頼できる情報源同士の**矛盾する統計**：恣意的に1つを選ばず、**出典付きで矛盾を注記**。文書分析は矛盾を含めたまま完了させ、**どう整合させるかはコーディネーターが判断**。
- **時間的データ**：公開日・データ収集日を構造化出力に含める（時期の違いを矛盾と誤解しない）。
- レポートは**確立された知見と異論のある知見**をセクションで区別し、元の特徴付けと方法論の文脈を保持。
- コンテンツ種別に応じた表現：**財務データ＝表、ニュース＝文章、技術的知見＝構造化リスト**（画一的な形式にしない）。

### シナリオ1：カスタマーサポート解決エージェント（分野1・2・5）

  - 「人間と話したい」→ 即エスカレーション／不満だけ → 解決を申し出る（5.2）
  - 同姓同名で複数一致 → **追加の識別情報を尋ねる**（5.2）
  - 長い会話で金額・日付が曖昧に → **case facts ブロック**（5.1）
  - 人間への引き継ぎ → **構造化ハンドオフ**（1.4）
  - 返金ツールのエラーが一律 → **構造化エラー（カテゴリ・リトライ可否）**（2.2）

### シナリオ2：Claude Codeによるコード生成（分野3・5）
- 前提：コード生成・リファクタリング・デバッグ・ドキュメント。カスタムスラッシュコマンド、CLAUDE.md、プランモード vs 直接実行。
- 典型的な問い

  - 散在するテストファイルの規約 → `.claude/rules/` ＋ `paths`（サンプル6）
  - 冗長なスキル出力 → `context: fork`（3.2）
  - マイクロサービス化・45+ファイル移行 → プランモード／単一ファイルの明確なバグ → 直接実行（3.4、サンプル5）
  - 変換仕様がぶれる → 入出力例2〜3個、テスト駆動、インタビューパターン（3.5）
  - 長い探索でコンテキストが劣化 → Explore サブエージェント、`/compact`、スクラッチパッド（3.4/5.4）

### シナリオ3：マルチエージェントリサーチシステム（分野1・2・5）
- 前提：コーディネーター＋サブエージェント（ウェブ検索、文書分析、統合、レポート生成）。出典付きの包括的レポート。
- 典型的な問い
  - レポートの網羅性不足 → **コーディネーターの分解が狭すぎる**（サンプル7）
  - サブエージェントに情報が届かない → **プロンプトで明示的に・構造化して渡す**（1.3）
  - 並列化 → **1応答で複数のTask呼び出し**（1.3）
  - 委任されない → allowedTools に `"Task"`、`description` の明確化（1.3）
  - 検索サブエージェントのタイムアウト → **構造化エラーコンテキスト**（サンプル8、5.3）
  - 統合エージェントの事実確認の往復 → **スコープ限定の verify_fact**（サンプル9、2.3）
  - 統計の矛盾・出典の消失・時期の違い → claim-source マッピング、日付、矛盾の注記（5.6）
  - 下流のコンテキスト予算が小さい → 上流に**構造化データ**を返させる（5.1）

### シナリオ4：Claudeによる開発者の生産性向上（分野2・3・1）
- 前提：Agent SDK、組み込みツール（Read/Write/Bash/Grep/Glob）、MCPサーバー統合。不慣れなコードベースの探索、レガシー理解、ボイラープレート生成、反復作業の自動化。
- 典型的な問い
  - Grep vs Glob、Edit 失敗時の Read+Write、段階的なコード理解（2.5）
  - MCPツールより Grep を使ってしまう → **MCPツールの説明を充実**（2.4）
  - チーム共有MCPと個人MCP、トークン管理 → `.mcp.json`＋`${VAR}`、`~/.claude.json`（2.4）
  - 探索の繰り返しを減らす → **MCPリソース**でカタログ公開（2.4）
  - レガシーへのテスト追加 → **動的・適応的な分解**（1.6）
  - セッションの再開/フォーク、変更ファイルの通知（1.7）
  - 異種データ形式 → PostToolUse で正規化（1.5）

### シナリオ5：継続的インテグレーションのためのClaude Code（分野3・4）
- 前提：CI/CDで自動コードレビュー、テストケース生成、PRへのフィードバック。**実用的なフィードバックと誤検知の最小化**。
- 典型的な問い
  - ハングする → `-p`（サンプル10）
  - インラインコメント用の構造化出力 → `--output-format json` ＋ `--json-schema`（3.6）
  - 重複コメント → 以前の指摘を渡し新規/未対応だけ（3.6）
  - 誤検知 → 明示的なカテゴリ基準、高誤検知カテゴリの一時停止、重大度の具体例（4.1）
  - 出力形式のぶれ → few-shot で形式提示（4.2）
  - 14ファイルのPRで矛盾 → ファイル単位＋統合パス（サンプル12、4.6）
  - 生成と同じセッションでのレビュー → 独立インスタンス（4.6）
  - コスト削減の Batch 化 → マージ前は同期、夜間はバッチ（サンプル11、4.5）
  - テスト生成の質 → 既存テストを渡す、CLAUDE.md にテスト標準・フィクスチャ（3.6）

### シナリオ6：構造化データ抽出（分野4・5）
- 前提：非構造化文書から抽出、JSONスキーマで検証、高精度、エッジケース処理、下流システム統合。
- 典型的な問い
  - JSON構文エラー → **tool_use＋JSONスキーマ（strict）**（4.3）
  - 文書種別が不明で抽出スキーマが複数 → `tool_choice: "any"`／特定の抽出を先に → 強制選択（4.3）
  - 値の捏造 → **nullable/任意フィールド**、`"other"`＋詳細、`"unclear"`（4.3）
  - 合計不一致 → 意味的エラーはスキーマでは防げない → `calculated_total` vs `stated_total`、`conflict_detected`（4.4）
  - リトライが効く/効かない（4.4）
  - 多様な文書構造で空抽出 → few-shot（4.2）
  - 大量処理・SLA → Batches、custom_id、失敗分だけ再送（4.5）
  - 97%の精度で完全自動化？ → 種別・フィールド別、層化抽出、キャリブレーション（5.5）

### 高頻出ひっかけ 総復習（これだけは落とさない）
1. ループ終了は **stop_reason**（`tool_use`→継続、`end_turn`→終了）。テキストの有無・自然言語・反復上限を主役にしない。
2. サブエージェントは**親の履歴を継承しない** → プロンプトで**明示的・構造化**して渡す。並列は**1応答で複数Task**。コーディネーターの allowedTools に **"Task"**（現行名 Agent）。
3. 確実な遵守（本人確認、金額しきい値）＝**フック/前提条件ゲート**。プロンプト強調・few-shotは確率的。
4. 結果の正規化＝**PostToolUse**、禁止操作のブロック＝**PreToolUse（呼び出しのインターセプト）**。
5. ツール選択ミス → まず**ツール説明の拡充**（入力形式・例・エッジケース・境界）。重複は改名・分割。
6. エラーは**構造化**（errorCategory、isRetryable、説明、部分結果、試行内容）。握りつぶし・全体停止はどちらもNG。アクセス失敗 ≠ 有効な空結果。
7. ツールは**役割ごとに4〜5個**、役割横断は**スコープ限定**（verify_fact）。
8. `tool_choice`：`auto`＝テキストもあり／`any`＝どれか必ず／`{"type":"tool","name":...}`＝指定ツール必ず。
9. 共有MCP＝**`.mcp.json`＋`${TOKEN}`**、個人MCP＝**`~/.claude.json`**。
10. 内容検索＝**Grep**、ファイル名＝**Glob**、Edit 失敗＝**Read＋Write**。
11. CLAUDE.md：ユーザー（`~/.claude/CLAUDE.md`、非共有）／プロジェクト（`./CLAUDE.md` or `.claude/CLAUDE.md`、共有）／ディレクトリ。`@import`、`.claude/rules/`、`/memory`。
12. 散在ファイルの規約＝**`.claude/rules/` ＋ `paths` glob**。
13. チーム共有コマンド＝**`.claude/commands/`**、冗長スキル＝**`context: fork`**、引数の催促＝**`argument-hint`**。
14. 大規模・複数案・アーキテクチャ判断＝**プランモード**、明確な単一修正＝**直接実行**、冗長な探索＝**Explore サブエージェント**。
15. CI＝**`-p`**、構造化＝**`--output-format json` ＋ `--json-schema`**。`CLAUDE_HEADLESS`/`--batch` は**存在しない**。
16. 誤検知 → **具体的なカテゴリ基準**、高誤検知カテゴリの**一時停止**。「保守的に」「確信度の高いものだけ」は効かない。
17. **tool_use＋スキーマ＝構文エラー排除**、でも**意味的エラーは残る**。無いかもしれない値は **nullable**、カテゴリは **enum＋"other"＋詳細**。
18. リトライが効く＝形式・構造の誤り。効かない＝**情報がソースに無い**。
19. Batches＝**50%安い、最大24時間、SLAなし、custom_id、ツールの往復不可** → マージ前は同期、夜間はバッチ。送信間隔＋24h ≦ SLA。
20. レビューは**独立インスタンス**、大規模PRは**ファイル単位＋統合パス**。
21. 長い会話は **case facts ブロック**、ツール出力は**トリミング**、冒頭に要約（lost in the middle）。
22. エスカレーション：**明示的要求は即**、不満だけなら解決を申し出る、**ポリシーの空白**はエスカレーション、複数一致は**追加の識別情報**。感情・自己申告確信度はNG。
23. 長時間探索：**スクラッチパッド**、**サブエージェント委譲**、**マニフェスト**で復旧、`/compact`。
24. 97%でも油断しない：**種別・フィールド別**、**層化無作為抽出**、**ラベル付き検証セットでキャリブレーション**。
25. 矛盾する統計は**両方を出典・日付つきで注記**。財務＝表、ニュース＝文章、技術＝リスト。
