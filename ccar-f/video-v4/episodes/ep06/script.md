## SLIDE: 第1章　明示的な基準で誤検知を減らす
@code_label: 指示の書き方の例（§4.1）
@diagram: ba | 曖昧な指示 と 明示的な基準
@before: ×　曖昧 | 保守的に、\nなどの言い方
@after: ○　明示的 | カテゴリ別の\n具体的な基準
@result: 誤検知の多いカテゴリは改善まで一時停止
@size: 28
```text
×「コメントが正確か確認」

○「コメントの主張が
  実際のコードの動作と
  矛盾する場合だけ指摘」

重大度は
  レベルごとに具体的な
  コード例を付けて定義
```
[L] めたん: コードレビューの誤検知を減らすには、どうしますの？
[L] ずんだもん: 曖昧な指示ではなく、明示的な基準を書くのだ。左の例なのだ。
[L] ずんだもん: 「コメントの主張が、実際のコードの動作と矛盾する場合だけ指摘」と書くのだ。
[R] めたん: 「保守的に判断して」や、「確信度の高いものだけ」は？
[R] ずんだもん: 右の前後比較なのだ。カテゴリ別の具体的な基準より、効かないのだ。よく出るひっかけなのだ。
[R] めたん: 特定のカテゴリだけ、誤検知がひどいときは？
[R] ずんだもん: 正確なカテゴリの指摘まで、信用されなくなるのだ。
[R] ずんだもん: だから、そのカテゴリを一時的に無効にして、プロンプトを直すのだ。

## SLIDE: 第1章　ボットの指摘が無視される

@node: 誤検知が多く指摘が無視される
@node: 報告する問題とスキップする問題を定義
@node: 誤検知の多いカテゴリを一時停止
@node: プロンプトを改善して再開
@size: 30
```text
状況:
  命名スタイルと
  コメントの正確性で
  誤検知が多発

既に書いてある指示:
  「確信度の高い指摘のみ」
  → 効果が出ていない
```
[L] めたん: 模擬試験のような例ですわ。誤検知が多くて、開発者がボットの指摘を無視するようになりましたの。
[L] めたん: 確信度の高いものだけ、とは、もう書いてありますわ。
[R] ずんだもん: 右の流れ図なのだ。まず、報告すべき問題と、スキップすべき問題を、具体的なカテゴリの基準で定義するのだ。
[R] ずんだもん: バグやセキュリティは報告、軽いスタイルや局所的な慣習はスキップ、という具合なのだ。
[R] めたん: 命名スタイルとコメントの正確性は？
[R] ずんだもん: 改善できるまで、一時的に無効にするのだ。

## SLIDE: 第3章　tool_choice の4種類
@code_label: tool_choice の設定値（§4.3）
@diagram: table | 挙動と使う場面
@cols: 挙動 | 使う場面
@row: auto | ツールかテキストか\nモデルが決める | 通常の対話
@row: any | どれかのツールを\n必ず呼ぶ | 文書種別が不明
@row: tool | 指定ツールを\n必ず呼ぶ | 抽出を先に実行
@row: none | ツールを使わない | —
@size: 26
```text
{"type":"auto"}
{"type":"any"}
{"type":"tool",
 "name":"extract_metadata"}
{"type":"none"}

auto はツールありの既定
none はツールなしの既定
```
[L] めたん: {tool_choice|ツールチョイス}は、星印付きですわね。
[L] ずんだもん: 左の4種類なのだ。{auto|オート}は、ツールがあるときの既定なのだ。
[R] ずんだもん: 右の比較表なのだ。{auto|オート}は、ツールを呼ぶか、テキストで答えるかを、モデルが決めるのだ。
[R] めたん: {any|エニー}は？
[R] ずんだもん: 何かしらのツールを、必ず呼ぶのだ。
[R] ずんだもん: 抽出スキーマが複数あって、文書の種類が分からないときに、構造化出力を保証できるのだ。
[R] めたん: ツール名を指定する形は？
[R] ずんだもん: 指定したツールを、必ず呼ぶのだ。メタデータの抽出を、先に確実に実行させたいときなのだ。
[R] ずんだもん: 後続は、フォローアップのターンで処理するのだ。

## SLIDE: 第3章　構造化出力の強みと限界
@code_label: ツールとスキーマ（現行）
@diagram: ba | 防げるもの と 防げないもの
@before: ○　防げる | 構文エラー\nstrict が最も確実
@after: ×　残る | 意味的エラー\n合計の不一致など
@result: 構文は保証されても、中身の正しさは別に検証する
@size: 28
```text
any / tool のとき
  API が応答をプリフィル
  → tool_use の前に
    自然言語の説明は出ない

意味的エラーの例:
  明細の合計が総額と不一致
  値が別フィールドに入る
```
[L] めたん: ツールユースとスキーマを使うと、何がうれしいですの？
[L] ずんだもん: {JSON|ジェイソン}スキーマと{strict|ストリクト}モードは、構文エラーをなくす、最も信頼性の高い方法なのだ。
[R] めたん: では、抽出のミスもなくなりますの？
[R] ずんだもん: そこが落とし穴なのだ。右の前後比較のとおり、意味的なエラーは防げないのだ。
[R] ずんだもん: 明細の合計が総額と合わないとか、値が別のフィールドに入るとかなのだ。
[L] ずんだもん: 左の補足なのだ。{any|エニー}や指定のときは、ツール呼び出しの前に、自然言語の説明は出ないのだ。

## SLIDE: 第3章　スキーマ設計のコツ
@code_label: 請求書の抽出ツール（概念）
@diagram: grid | スキーマ設計の3原則
@card: 任意にする | 無いかもしれない値は\nnull を許す
@card: 拡張に備える | enum に other と\n詳細の文字列
@card: 曖昧は逃がす | 迷うときは\nunclear を選べる
```text
po_number:
  ["string", "null"]
category: enum
  software / hardware /
  maintenance / other /
  unclear
category_detail:
  ["string", "null"]
```
[L] めたん: スキーマ設計のコツは？
[L] ずんだもん: 左が、請求書の抽出ツールの例なのだ。発注番号は、文字列かヌルなのだ。発注番号がない請求書もあるからなのだ。
[R] ずんだもん: 右の整理図なのだ。文書に無いかもしれない情報は、ヌルを許すのだ。必須にすると、モデルが値を捏造しがちなのだ。
[R] めたん: カテゴリには、{other|アザー}と{unclear|アンクリア}がありますわね。
[R] ずんだもん: 増えるかもしれないカテゴリは、{other|アザー}を足して、詳細の文字列を付けるのだ。曖昧なときは{unclear|アンクリア}なのだ。
[R] ずんだもん: 書式がばらばらなソースには、正規化のルールを、プロンプトにも書くのだ。

## SLIDE: 第3章　strict スキーマの制約
@code_label: strict の制約（現行ドキュメント）
@diagram: table | 覚える点と参考
@cols: 内容
@row: 必須 | additionalProperties: false
@row: 非対応 | 数値の最小最大・文字列長
@row: 非保証 | enum の大文字小文字
@row: 注意 | refusal や max_tokens は不一致も
@size: 28
```text
無いかもしれない値:
  ["string", "null"]
  または required から外す

複雑さの上限（参考）
  任意プロパティ 24個
  union 型 16個
※数値は【要確認】
```
[L] めたん: {strict|ストリクト}モードには、制約もありますのね。
[R] ずんだもん: 右の比較表なのだ。今のドキュメントでは、オブジェクトは{additionalProperties|アディショナル プロパティーズ}を{false|フォールス}にするのだ。
[R] ずんだもん: 数値の最小、最大や、文字列の長さの制約は使えないのだ。列挙型の大文字と小文字も、保証されないのだ。
[R] めたん: 停止の理由によっては？
[R] ずんだもん: {stop_reason|ストップリーズン}が{refusal|リフューザル}や{max_tokens|マックストークンズ}のときは、スキーマに合わないことがあるのだ。
[L] めたん: 試験では、どこまで覚えればよろしいの？
[L] ずんだもん: 無いかもしれない値を、ヌル許容か任意で表すこと、なのだ。数の上限は、参考程度でいいのだ。

## SLIDE: 第3章　確認クイズ：tool_choice とスキーマ（オリジナル）
@code_label: 問題（オリジナル）
@diagram: table | 試験での答え
@cols: 答え
@row: 先に抽出 | tool で名前を指定
@row: 種別が不明 | any
@row: PO番号が無い | null 許容にする
@row: 新カテゴリ | enum + other + 詳細
@row: 構文エラー | tool_use + strict
@size: 30
```text
1 extract_metadata を
  必ず最初に実行したい
2 文書種別が不明で
  どれかのツールを必ず使う
3 PO番号が3割の請求書に無い
4 カテゴリに新しいものが出る
5 JSON の構文エラーをなくす
```
[L:0] めたん: 確認クイズですわ。左の5つの困りごとの、答えを選んでくださる？
[L:0] めたん: 1つ目、メタデータの抽出を、必ず最初に実行させたいですわ。
[R] ずんだもん: ツール名を指定して強制するのだ。後続は、フォローアップのターンなのだ。
[L] めたん: 2つ目、文書の種類が分からない。どれかの抽出ツールを、必ず使わせたいですわ。
[R] ずんだもん: {any|エニー}なのだ。
[L] めたん: 3つ目、発注番号が、3割の請求書にありません。4つ目、カテゴリに、ときどき新しいものが現れますわ。
[R] ずんだもん: 3つ目はヌルを許す。必須にすると捏造するのだ。4つ目は、列挙型に{other|アザー}と詳細なのだ。
[L] めたん: 最後、{JSON|ジェイソン}の構文エラーをなくしたいですわ。
[R] ずんだもん: ツールユースと、{strict|ストリクト}スキーマなのだ。全問正解なのだ！
