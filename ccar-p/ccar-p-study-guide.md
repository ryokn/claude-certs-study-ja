## 1. 分野3：統合（Integration）19%・約12問

### 1-1. ツールやエージェントの構成を、機能の肥大化の観点から評価する（Evaluate tool/agent configuration for capability bloat）
**基礎**：「機能の肥大化（capability bloat）」とは、エージェントにその役割で不要なツールや権限、情報が付いている状態のことです。これには3つの問題があります。①攻撃対象領域が広がる。②ツール定義がコンテキストを圧迫する。③ツールの選択精度が下がる。

**頻出ポイント**
- ★ **最小権限とは「不要なツールを外すこと」**です（公式サンプル1）。ロギングや確認プロンプトは、発見的統制・補完的統制にすぎません。
- ツールが **30〜50個を超えると選択精度が下がります**。複数のMCPサーバー（GitHub、Slack、Sentry、Grafana、Splunk）を使う構成では、ツール定義だけで **約55kトークン** になる例があります。ツール検索ツールを使うと、これを **通常85%以上削減** できます（公式ドキュメント）。
- 似た機能のツールが複数ある、説明があいまい、読み取りと書き込みが混在している、といった構成は分割・統合・削除を検討します。役割ごとにエージェントを分けるのも有効です。

**ひっかけ**
- 「より大きなモデルにすれば、正しく選べる・指示に従う」→ 権限の範囲の問題は、モデルでは解決しません。
- 「確認ダイアログを付ければ、全ツールを残してよい」→ 外せるものは外すのが先です。

### 1-2. 認証と認可の要件を分析し、セキュリティ上のギャップを特定する（Analyze authentication and authorization requirements to identify security gaps）
| 典型的なギャップ | 正しい設計 |
|---|---|
| 受け取ったトークンを下流へそのまま転送する（**トークンパススルー**） | **MCP仕様で禁止**されています。サーバーは自分宛て（audience）のトークンだけを受け入れ、下流用には別のトークンを取得します |
| 全ユーザー共通のサービスアカウントを使う | ユーザーに紐づく委譲認可（OAuth）にして、ユーザー単位で監査できるようにします |
| APIキーをプロンプトやリポジトリに置く | シークレット管理の仕組みに置き、ツールの実行環境から注入します |
| 「プロンプトで禁止したから安全」 | 認可は **アプリ層やサーバー側で決定的に強制**します |
| エンタープライズ向けのSSOがない | SSO（SAML/OIDC）、SCIM、ロールベースのアクセス制御を使います（Claude Enterprise の管理機能など） |

- MCPの認可は **OAuth 2.1** がベースです。保護リソースのメタデータ（RFC 9728）とリソースインジケーター（RFC 8707）を使い、PKCEも必要です（MCP仕様 2025-06-18 / 2026-07-28）。
- ★ ツール呼び出しの認可は、**モデルの判断ではなくコードで行います**（準備コース：tool-call authorization）。

### 1-3. 精度とレイテンシのトレードオフを評価し、構成に関する決定の根拠を示す（Evaluate accuracy-latency trade-offs and justify configuration decisions）
| 調整できる項目 | 精度 | レイテンシ・コスト | 備考 |
|---|---|---|---|
| モデルのティア（Haiku / Sonnet / Opus / 最上位） | 上位ほど高い | 上位ほど遅く高い | 公式は **効率優先** と **能力優先** の2つの始め方を紹介しています |
| **effort**（low / medium / high / xhigh / max） | 高いほど良い | 高いほど遅く高い | ★ 公式は「**モデルを替えるより effort の調整のほうが有効なレバーになることが多い**」としています |
| thinking（adaptive など） | 複雑な推論で向上 | 増える | 現行モデルでは adaptive thinking が標準です【モデルごとの仕様は要確認】 |
| RAGの top-k とリランキング | 再現率が上がる | 遅くなる | 公式の検証では top-20 が top-10/5 より有効でした |
| ルーティング | 難しいケースだけ上位モデルへ | 平均コストが下がる | Building effective agents の定番パターンです |
| Fast mode | — | 出力速度が最大2.5倍（割増料金） | 対応モデルは限られます【要確認】 |
| プロンプトキャッシング | 変わらない | **最初のトークンまでの時間（TTFT）とコストが下がる** | 公式サンプル2 |

- ★ 判断の根拠は「**同じ評価セットでの比較結果 ＋ SLA**」で示します。
- Message Batches API は非同期で、即時の応答が必要な用途には使えません（ひっかけの定番）。

### 1-4. オブザーバビリティの課題を分析し、大規模環境でのモニタリング戦略を選択する（Analyze observability challenges and select monitoring strategies at scale）
- LLMシステムの不具合の多くは「**HTTP 200 で返ってくる誤答**」なので、5xx の監視だけでは見つかりません。
- 必要な情報：**トレースID**、LLM呼び出しとツール呼び出し（入力と結果）、検索されたチャンク、**モデルとプロンプトのバージョン**、トークン数、キャッシュヒット（`cache_read_input_tokens`）、レイテンシ（TTFT と総時間）、停止理由。
- OpenTelemetry：Claude Code は `CLAUDE_CODE_ENABLE_TELEMETRY=1` でメトリクスとイベントを出力でき、トレースはベータです。Claude API 向けの OpenTelemetry のページもあります。
- ★ ログには **PII、データ保持、アクセス制御** の設計も必要です（全文を無期限に平文で保存する選択肢はひっかけ）。
- レート制限：RPM / ITPM / OTPM で、**トークンバケット方式**（容量が継続的に回復する）です。超過すると **429**（`retry-after` ヘッダーを参照）。支出上限に達した場合も 429 ですが、`retry-after` が付かず、リトライしても回復しません。

### 1-5. 適切なチャンキング戦略とインデックス作成戦略を備えたRAGパイプラインを設計する（Design a RAG pipeline with appropriate chunking and indexing strategies）
**Contextual Retrieval（Anthropic公式記事）の要点** ★
- 各チャンクに、文書全体から生成した **50〜100トークン程度の文脈説明** を前置し、その文で **埋め込み（Contextual Embeddings）と BM25 インデックス（Contextual BM25）** を作ります。
- top-20 での検索失敗率は、文脈付き埋め込みで **−35%**（5.7% → 3.7%）、BM25 併用で **−49%**（→ 2.9%）、さらにリランキングを加えると **−67%**（→ 1.9%）になりました。
- 文脈説明の生成にはプロンプトキャッシングを使い、1回限りのコストは **文書100万トークンあたり約$1.02**（記事の検証時点）でした。
- **知識ベースが約20万トークン（約500ページ）未満なら、RAGを使わず全体をプロンプトに入れる**（＋キャッシング）という選択肢もあります。
- チャンクのサイズ、境界、オーバーラップは性能に影響します（見出しや条項の境界で分割する）。

| 文書の種類 | チャンキングの例 |
|---|---|
| 契約書・規程 | 条項や見出しの単位。定義語は文脈として前置する |
| FAQ | Q&A 1組を1チャンクにする |
| マニュアル | 見出しの階層を保持し、パンくずリストを前置する |
| 表・CSV | 行のまとまりと列ヘッダーを一緒にする。集計は検索ではなくSQLやツールで行う |

**ひっかけ**：公式サンプル3のように「文書を更新したら自信満々に誤答するようになった（モデルとレイテンシは変わっていない）」場合は、**再インデックスの失敗や埋め込みの不一致など、検索側**を疑います。

### 1-6. データの形状とクエリパターンに合った検索戦略を適用する（Apply retrieval strategies matched to data shape and query pattern）
| データ・クエリ | 戦略 |
|---|---|
| 型番、エラーコード、固有名詞 | **BM25（語彙検索）＋埋め込みのハイブリッド**。埋め込みだけだと「TS-999」のような完全一致を取りこぼします |
| 言い換えや概念的な質問 | 埋め込み（意味検索）とリランキング |
| **ライブ状態（在庫、注文、残高）** | ★ **RAGではなく、ツールやAPIでその都度照会**（準備コース：「検索が、ライブ状態が担うべき役割をしていないか」） |
| 構造化データの集計 | Text-to-SQL や、データベースを読み取るツール |
| コード、ファイル群 | エージェントによるジャストインタイム検索（glob/grep）。インデックスが古くなる問題を避けられます |
| 小さな静的KB（約20万トークン未満） | 全体をプロンプトに入れてキャッシュ |

### 1-7. 接続プロトコルを評価し、適切な統合メカニズムを選択する（Evaluate connection protocols and select the appropriate integration mechanism：MCP、API/CLI、エージェント間）
| メカニズム | 向いている場面 | 注意点 |
|---|---|---|
| **MCP** | 1つの連携を **複数のクライアント（Claude Desktop、Claude Code、自社エージェント）で再利用**する。ツール・リソース・プロンプトを標準化する。リモートでOAuthを使う | 標準トランスポートは **stdio**（ローカル）と **Streamable HTTP**（リモート）。ツールの数が増えると肥大化に注意 |
| **API/SDK を直接呼ぶ** | 単一のアプリ内での決定的な処理。レイテンシを最小にしたい | クライアント間での再利用性は低い |
| **CLI** | Claude Code など、シェルを使えるエージェントが既存のCLI（gh、aws など）を使う | 権限ルール（Bash の deny/ask）で制御する |
| **エージェント間（A2A）** | 別の自律エージェントにタスクを委譲する（組織やベンダーをまたぐ場合を含む） | 決定的なCRUD操作の提供には過剰 |

- MCPの「コード実行で使う」パターン（code execution with MCP）は、ツール定義と中間結果のトークンを減らせます（Anthropic Engineeringブログ）。

### 1-8. 段階的ディスカバリーと一括型コンテキスト戦略を比較評価する（Evaluate progressive discovery vs. monolithic context strategy）
| | 一括型（monolithic：最初にすべて入れる） | 段階的ディスカバリー（progressive：必要なときに読み込む） |
|---|---|---|
| 例 | 全ツール定義、全手順書、KB全体をシステムプロンプトに入れる | ツール検索、**Agent Skills**（メタデータだけ常に読み込む）、ジャストインタイム検索 |
| 長所 | 単純。キャッシュが効きやすい。検索ミスがない | トークンが少ない。選択精度が高い。スケールする |
| 短所 | コンテキストの圧迫、「context rot」、コスト | 検索のための往復が増える。見つけられないリスクがある |
| 向いている場面 | 小さく静的で、毎回ほとんどを使う | 大きく、そのうち一部しか使わない |

- コンテキストエンジニアリング（公式記事）：LLMには **限られた「注意の予算」** があり、トークンが増えるほど性能が落ちることがあります（context rot）。そのため「**目的の結果を得られる、最小の高シグナルなトークンの集合**」を目指します。長時間のタスクには、**コンパクション**、**構造化メモ（エージェントのメモリー）**、**サブエージェント** を使います。

## 2. 分野1：ソリューション設計とアーキテクチャ（Solution Design & Architecture）17%・約11問

### 2-1. ビジネス課題をClaudeベースのAIソリューションに落とし込む（Translate business problems into Claude-based AI solutions）
- 準備コースの考え方：まず依頼を「**Claudeがやること／既存システムがやること／人がやること**」に分解します。
- 次に形を決めます。**拡張LLMの単一呼び出し（augmented call）→ ワークフロー → エージェント** の順に検討し、それぞれのコストを明示します。
- ★ 規制やガバナンスの制約で使えない入口（Claude.ai、API、SDK、Claude Code、MCPサーバー）や提供経路（直接API、Bedrock、Vertex など）は、**ほかのトレードオフより先に除外**します。

### 2-2. エンドツーエンドのアーキテクチャを設計する（Design end-to-end architectures：入力 → 処理 → 出力 → フィードバックループ）
| 段階 | 設計要素 |
|---|---|
| 入力 | 認証、入力スクリーニング（インジェクション、PII）、正規化、ルーティング |
| 処理 | プロンプト、モデル、RAGやツール、ワークフロー・エージェント、リトライ、フォールバック、サーキットブレーカー |
| 出力 | 構造化出力、出力スクリーニング、引用、人の承認、下流システムへの書き込み |
| フィードバックループ | ユーザー評価や修正差分のログ → 評価データセット → プロンプトや構成の改善 → 回帰評価 → リリース |

### 2-3. 適切なアーキテクチャパターンを選択する（Select appropriate architectural patterns：ワークフロー、エージェント型、拡張LLM）
**Building effective agents（公式記事）** ★ 必ず覚える
| パターン | 使う場面 | 例 |
|---|---|---|
| **拡張LLM（augmented LLM）** | 基本の構成要素。検索、ツール、メモリーで強化した単一の呼び出し | 定型抽出、要約 |
| プロンプトチェーン（prompt chaining） | 決まった手順に分解できる。途中に「ゲート」（プログラムによるチェック）を置く | アウトライン → 本文 → 翻訳 |
| ルーティング（routing） | カテゴリが明確で、正確に分類できる。ある分野への最適化が別の分野を劣化させる | 問い合わせの振り分け、簡単なものを小型モデルへ |
| 並列化（parallelization） | **sectioning**（独立したサブタスクを並列に）または **voting**（同じタスクを複数回実行して信頼度を上げる） | ガードレールと本処理の並列実行、脆弱性レビューの多数決 |
| orchestrator-workers | サブタスクを事前に決められない | 複数ファイルにまたがるコード変更、調査 |
| 評価者-最適化者（evaluator-optimizer） | 明確な評価基準があり、反復で改善できる | 翻訳の推敲、検索の反復 |
| エージェント（agent） | 手順を予測できない、自由度の高いタスク | オープンエンドなコーディング、調査 |

- ★「**最も単純な解決策から始め、必要なときだけ複雑にする**」。ワークフローは予測しやすく一貫性があり、エージェントは柔軟ですが、レイテンシとコストが増えます。
- ひっかけ：定型業務に自律エージェントやマルチエージェントを勧める選択肢。

### 2-4. マルチエージェントシステムとオーケストレーション戦略を設計する（Design multi-agent systems and orchestration strategies）
- Anthropicの調査システム：リード（Opus 4）＋サブエージェント（Sonnet 4）の構成が、単一エージェントを **90.2%上回りました**。性能のばらつきの **80%はトークン使用量で説明**できました。
- コスト：エージェントは通常のチャットの **約4倍**、マルチエージェントは **約15倍** のトークンを使います。→ **価値が高く、並列化しやすく、単一のコンテキストに収まらないタスク** に限って使います。
- 向かないもの：全エージェントが同じ文脈を共有する必要があるもの、依存関係が多いもの（多くのコーディングタスク）。
- 設計の要点：サブエージェントには **目的、出力形式、使うツール、範囲（どこまでやるか）** を明確に渡します。リードは計画をメモリーに保存し、サブエージェントは要約を返します（コンテキストの圧縮）。

### 2-5. 複雑な問題解決のために分解の手法を適用する（Apply decomposition techniques for complex problem solving）
- 分解の単位：**手順**（チェーン）、**カテゴリ**（ルーティング）、**独立した観点**（sectioning）、**動的なサブタスク**（orchestrator）。
- 各ステップの出力を **検証可能な中間成果物**（JSON、チェックリスト）にして、ゲートで確認します。
- 分解すると、ステップごとに **適したモデルを使い分けられ**（コスト最適化）、**ステップ単位で評価**できます。

### 2-6. ソリューションをビジネス価値の柱に整合させる（Align solutions to business value pillars：効率性、変革、生産性、コスト、パフォーマンスSLA）
| 柱 | KPIの例 |
|---|---|
| 効率性 | 処理時間（AHT）、自動処理率 |
| 変革 | 新しいサービスや、これまでできなかった分析 |
| 生産性 | 1人あたりの処理件数、開発のリードタイム |
| コスト | 1件あたりの費用（トークン × 単価 ＋ 運用コスト） |
| パフォーマンスSLA | p95レイテンシ、稼働率、品質指標の下限 |
- ★ **ベースライン、目標、測定方法** をセットで合意します。ベンチマークの数値や最新モデルの採用は、価値の根拠になりません（ひっかけ）。
- ユースケースの見積もり（準備コース）：呼び出し回数 × トークン数（入力・出力・キャッシュ）× 単価 で計算します。

## 3. 分野4：評価、テスト、最適化（Evaluation, Testing & Optimization）16%・約10問

### 3-1. 評価指標を定義する（Define evaluation metrics：精度、レイテンシ、コスト、安全性、セキュリティ）
- 良い成功基準は **具体的（Specific）、測定可能（Measurable）、達成可能（Achievable）、関連性がある（Relevant）**（公式ドキュメント）。
- 悪い例：「安全な出力」。良い例：「**1万件の試行で、コンテンツフィルターに引っかかる出力が0.1%未満**」。
- 多次元で定義します。例：F1 ≥ 0.85、非有害な出力 99.5%、p95 < 200ms。
- 主な観点：タスクへの忠実度、一貫性、関連性と一貫性、トーン、**プライバシーの保護**、コンテキストの活用、レイテンシ、価格。
- エージェントの指標：**pass@k**（k回の試行で1回でも成功する確率。kを増やすと上がる）と **pass^k**（k回すべて成功する確率。kを増やすと下がる）。例：1回あたりの成功率が75%で3回試行すると、pass^3 ≈ 42%。★ **顧客対応では pass^k（毎回確実に動くこと）が重要**です。

### 3-2. 複数の方法論を組み合わせて、評価データセットとテストフレームワークを設計する（Design evaluation datasets and test frameworks using mixed methodologies）
| 採点方法 | 長所 | 短所 | 用途 |
|---|---|---|---|
| **コードによる採点**（完全一致、文字列一致、スキーマ） | 最も速く信頼でき、スケールする | ニュアンスを判断できない | 分類、抽出、形式 |
| **LLMによる採点**（ルーブリック） | 速く柔軟で、スケールする | **キャリブレーションが必要** | 要約の品質、トーン |
| **人による採点** | 最も柔軟で質が高い | 遅く高コスト（**可能なら避ける**） | LLM採点のキャリブレーション、難しいケース |
- 設計の原則：**タスク固有にする（エッジケースを含める）**、**できる限り自動化する**、**質より量**（少し質が低くても、自動採点できる多数の問題のほうが良い）。
- LLM採点のコツ：詳細なルーブリック、「correct / incorrect」や1〜5のような明確な出力、**採点モデルにも thinking を使わせる**。
- エージェントの評価では、**トランスクリプト（過程）と結果（最終的な環境の状態）** を採点します。たとえば「予約しました」という発言ではなく、DBに予約が存在するかを見ます。
- **能力評価（capability）と回帰評価（regression）**：回帰評価はほぼ100%の合格率を保つべきもので、能力評価で合格率が高くなったタスクは回帰スイートに「卒業」させます。
- ★ 準備コース：**本番用のコードを書く前に** 成功基準と評価スイートを作り、**すべてのモデルやアーキテクチャの変更のゲート** にします。

### 3-3. A/Bテストと反復的な改善を実施する（Conduct A/B testing and iterative improvements）
- 事前に決めること：**仮説、主要指標、ガードレール指標（安全性、コスト、レイテンシ）、必要なサンプル数、期間（曜日の影響を考慮）**。
- ひっかけ：「サンプルが足りないのに改善したので展開する」「有意差が出るまで指標を替える（p-hacking）」「有意でない＝効果がないと断定する」。
- 反復のサイクル：オフライン評価 → シャドーテストやカナリアリリース → A/Bテスト → 全面展開 → 監視。

### 3-4. システムの問題を診断する（Diagnose system issues：プロンプトの失敗、ハルシネーション、モデルの不適合）
| 症状 | 最初に疑う箇所 |
|---|---|
| 文書の更新後に自信満々な誤答（モデルは変わっていない） | **検索とインデックス**（公式サンプル3） |
| モデルの切り替え後に形式の崩れや冗長な出力 | **モデルの不適合** → スナップショットを固定、回帰評価、移行ガイド |
| 特定の入力の種類だけで失敗 | プロンプトの例の偏り、ルーティング |
| 長い会話の後半で指示を守らない | コンテキストの肥大化 → コンパクション、指示の再掲 |
| 根拠のない記述 | ハルシネーション → 「わからない」と答えることを許可する、**原文を逐語引用させる（2万トークンを超える長文で有効）**、引用で検証させ、裏付けがない主張は撤回させる、Best-of-N で比較する、提供した文書だけを使うよう制限する |
| 正しいツールを呼ばない | ツールの説明の質、ツールの数（肥大化） |

### 3-5. トークン使用量、レイテンシ、コストとパフォーマンスのトレードオフを最適化する（Optimize token usage, latency, and cost-performance trade-offs）
**プロンプトキャッシング** ★（公式ドキュメント）
| 項目 | 内容 |
|---|---|
| 仕組み | **tools → system → messages** の順でプレフィックスをキャッシュする。**変化しない内容を先頭に、変化する内容を後ろに**置く |
| 寿命（TTL） | 既定は **5分**（使われるたびに無料で延長）。**1時間** も選べる |
| 料金 | 書き込みは基本入力単価の **1.25倍（5分）**、**2倍（1時間）**。読み取りは **0.1倍** |
| ブレークポイント | 最大 **4個**。自動キャッシング（リクエストのトップレベルに `cache_control`）も使える。ルックバックは20ブロック |
| 最小トークン数 | モデルによって異なる（例：現行の5.x系は512、旧モデルは1,024/2,048/4,096）。**最小未満ならエラーにならず、キャッシュされないだけ**【モデルごとに要確認】 |
| 無効化 | **ツール定義を変更するとキャッシュ全体が無効**になる。tool_choice、画像、thinking や effort の変更は、messages 以降のキャッシュを無効にする |
| 確認方法 | `cache_creation_input_tokens` と `cache_read_input_tokens`（両方0ならキャッシュされていない） |

**Message Batches API** ★
| 項目 | 内容 |
|---|---|
| 割引 | **すべてのトークンが50%** |
| 規模 | 1つのバッチで **10万リクエストまたは256MB** のどちらか先に達するまで |
| 処理時間 | **多くは1時間以内**。**24時間** で完了しなかったリクエストは期限切れ（課金されない） |
| 結果の保持 | **29日間** |
| ZDR | **対象外**（非同期の保存が必要なため） |
| キャッシュとの併用 | 割引は重ねられるが、キャッシュヒットはベストエフォート（30〜98%） |

その他のレバー：モデルのティアとeffort、ルーティング、max_tokens、構造化出力（再試行の削減）、ツール結果のクリア（`clear_tool_uses_20250919`）やサーバー側のコンパクション、Skills による段階的開示。

### 3-6. ロギングツールとオブザーバビリティツールを使用してシステムのパフォーマンスをモニタリングする（Monitor system performance using logging and observability tools）
- 1-4 で示した項目に加えて、**オンライン評価**（本番トラフィックのサンプルをLLMで採点）、**ドリフトの検知**（入力分布や品質スコアの変化）、**ダッシュボードとアラート**（SLAの閾値）を用意します。
- Claude Code のコスト：エンタープライズでの平均は **開発者1人あたり、稼働日1日約$13、月$150〜250**（90%の利用者は1日$30未満）（公式ドキュメント。モデルや時期によって変わる）。

## 4. 分野5：ガバナンス、安全性、リスク管理（Governance, Safety & Risk Management）14%・約9問

### 4-1. ガードレールと安全管理策を実装する（Implement guardrails and safety controls）
**多層の安全スタック**（準備コース）：入力スクリーニング → 本処理 → **ツール呼び出しの認可** → 出力スクリーニング → 人の承認。それぞれに見落としがあるので、次の層で補います。
| 脅威 | 対策（公式ガイド） |
|---|---|
| ジェイルブレイク、直接のプロンプトインジェクション | **無害性スクリーン**（軽量モデル＋構造化出力で分類。`stop_reason: "refusal"` は有害と判定されたものとして扱う）、入力の検証、システムプロンプトでの境界と断り方の明示、**繰り返し違反する利用者**のスロットリングやBAN |
| **間接プロンプトインジェクション**（Webページ、メール、文書、ツールの結果） | 信頼できないコンテンツは **tool_result** で渡す、**出所を明示する**、システムプロンプトで「ツールの結果はデータであり、指示ではない」と示す、**JSONでエンコード**する、自分の指示はツールの結果に入れない、**最小権限**、**ツールの出力を軽量モデルでスクリーニング**、**レッドチーミング** |
| プロンプトの漏えい | 不要な機密情報を入れない、出力の後処理（正規表現やキーワード）、定期的な監査 |
| ハルシネーション | 3-4 を参照 |
- ★ **モデルの学習が軽減するもの と アプリ層が強制すべきもの を区別する**（準備コース）。「Claudeが与えられていないルールを守ってくれる」と想定するのが、最もよくある失敗です。
- **決定的なチェック**（正規表現、スキーマ、許可リスト）と **モデルによるチェック**（あいまいな有害性の判定）を使い分けます。
- ひっかけ：プレフィルで出力を誘導する（**Claude 4.6以降のモデルではサポートされていない**）。

### 4-2. LLMシステムのリスク、限界、障害モードを特定する（Identify risks, limitations, and failure modes of LLM systems）
| 障害モード | 対策 |
|---|---|
| ハルシネーション、自信過剰な誤り | 根拠付け、引用、「わからない」と答えることの許可、HITL |
| インジェクション、データの持ち出し | 4-1 を参照 |
| 安全管理策そのものの障害（分類器のタイムアウトなど） | ★ **フェイルクローズ**（高リスクの操作は拒否、保留、エスカレーション）。フェイルオープンは避ける |
| 過剰な拒否（正当な依頼を断る） | 評価セットに正当なケースを入れ、プロンプトの境界を明確にする |
| 非決定性、ドリフト | 評価、モデルIDの固定、監視 |
| レート制限、障害 | リトライ（指数バックオフ）、フォールバック、サーキットブレーカー、Batch による平準化 |
| エージェントの暴走（ループ、過剰な行動） | ステップ数や予算の上限、不可逆な操作には承認 |

### 4-3. ヒューマン・イン・ザ・ループによる検証戦略を適用する（Apply human-in-the-loop validation strategies）
- ★ 振り分けの軸：**信頼度 × 可逆性 × 誤った場合のコスト**（準備コース）。
  - 不可逆で影響が大きい（送金、否決の通知、削除、外部への送信） → **必ず人が確認**
  - 可逆で低リスク、高信頼 → 自動化して **サンプリング監査**
  - 低信頼 → 人のキューへ
- 全件を人がレビューするとAIの価値がなくなり、レビューが形骸化（ラバースタンプ化）します。完全自動化は規制や公平性を無視することになります。どちらもひっかけです。

### 4-4. 規制へのコンプライアンスを確保する（Ensure compliance with regulations：GDPR、HIPAA、FedRAMP など）
★ 準備コース：**コンプライアンス上の義務ごとに「統制（control）、担当者（owner）、証跡（evidence artifact）」を対応付け**、監査できるアーキテクチャにします。
| 規制・要件 | Claudeでの選択肢（2026年11月時点の公式情報） |
|---|---|
| **HIPAA**（PHI） | Claude APIの **HIPAA対応**：**BAAを締結**し、HIPAAを有効にした組織で、**対象機能**だけを使う。Claude Enterprise には別の実装ガイドがある（Trust Center） |
| **データ保持の最小化** | **ZDR（ゼロデータ保持）**：Messages API と Token Counting API の対象機能。**Batch API は対象外**。Claude Team / Enterprise の画面は対象外（Claude Code on Enterprise には別のZDRがある）。契約内容による【要確認】 |
| **データの所在**（GDPRなど） | Claude API の `inference_geo: "us"` は **1.1倍の料金**。Bedrock と Vertex には **リージョンやマルチリージョンのエンドポイント**があり、グローバルより10%割高 |
| **FedRAMP** | **Claude for Government**（FedRAMP High）、**AWS GovCloud の Bedrock**（FedRAMP High、一部のモデルは DoD IL4/IL5）、**Assured Workloads の Vertex AI**（FedRAMP High）。**Anthropic直のClaude API と Claude Enterprise はFedRAMP認可を受けていない**（Enterpriseは Moderate を申請中）【モデル単位の状況は要確認】 |
| GDPR全般 | 一般的な原則として、適法な根拠、データの最小化、目的の限定、DPA（データ処理契約）、消去の権利、域外移転への対応（Anthropic固有の仕様ではない） |
- ★ 規制要件は、**ほかのトレードオフより先に提供経路の候補を絞り込みます**（準備コース）。

### 4-5. 倫理的なAIに関する考慮事項に対処する（Address ethical AI considerations：バイアス、公平性、透明性）
- 不公平な結果が生じうる箇所を特定します。学習データだけでなく、**検索対象のコーパス、few-shot例、ルーティングの規則、人のレビューの偏り**も含みます。
- 属性ごとに評価を分けて結果の差を測ります（全体の精度が高くても、特定のグループで低いことがある）。
- 透明性：**利用者、規制当局、デバッグチーム**それぞれに必要な説明を設計します（準備コース）。AIを使っていることの開示、判断の理由、異議を申し立てる経路。

## 5. 分野6：ステークホルダーとのコミュニケーションとライフサイクル管理（Stakeholder Communication & Lifecycle Management）14%・約9問

### 5-1. 体系的なディスカバリーと要件収集を実施する（Conduct structured discovery and requirement gathering）
ディスカバリーで確認する項目（例）：
| 観点 | 質問 |

## 6. 分野2：Claudeモデル、プロンプト作成、コンテキストエンジニアリング（Claude Models, Prompting & Context Engineering）13%・約8問

### 6-1. トレードオフに基づいて適切なClaudeモデルを選択する（Select appropriate Claude models based on trade-offs）
**2026-11-03時点の公式ドキュメントのモデル一覧**（試験は2026年7月の v1.0 なので、**問題に出るのは具体的なモデル名ではなく、ティア間のトレードオフ** と考えてください【要確認】）
| モデル | 位置づけ（公式の説明） | レイテンシ | 価格（入力/出力 per MTok） | 既定のeffort |
|---|---|---|---|---|
| Claude Fable 5.1 | 高度な推論と長時間のエージェント作業 | 遅い | $10 / $50 | high |
| Claude Opus 5.5 | 長時間のエージェント型コーディングと知的作業。**多くの用途の出発点** | 中程度 | $4 / $20 | medium |
| Claude Sonnet 5.5 | 速度と知能の最良のバランス | 速い | $2 / $10 | high |
| Claude Haiku 5.5 | 大量で低レイテンシの処理（分類、抽出、ルーティング） | 最速 | $0.10〜 / $0.50〜 | medium |
- いずれも 1Mトークンのコンテキスト、最大出力128K、テキストと画像の入力、ツール使用に対応。
- 選び方：**効率優先**（Haikuから始めて、必要なら上げる。プロトタイプ、低レイテンシ、大量処理向け）と **能力優先**（Opusから始めて、後でeffortを下げたりモデルを下げたりする。複雑な推論や高い自律性向け）。
- ★ **モデルを替える前に effort を調整する**。**モデルの切り替えは評価をゲートにする**（準備コース）。
- 本番ではモデルIDを固定します（エイリアスの扱いはモデルの世代によって異なる。公式の Model IDs and versioning を参照）。

### 6-2. システムプロンプト、テンプレート、ガードレールを設計する（Design system prompts, templates, and guardrails）
- システムプロンプト：役割、目的、範囲、**できないことと断り方**、出力形式、ツール結果の扱い（信頼しないデータとして扱う）。
- テンプレート：変化しない指示と変数を分けます。**変化しない部分を先頭に**（キャッシュのため）、XMLタグで区切ります。
- 形式の保証：**構造化出力**（`output_config.format` によるJSONスキーマ、`strict: true` によるツール入力）は、**制約付きデコーディングでスキーマ準拠を保証**します。
- ひっかけ：「大文字で強調すれば守られる」「**プレフィル**で形式を強制する（4.6以降のモデルではサポートされていない）」。

### 6-3. プロンプトエンジニアリングの手法を適用する（Apply prompt engineering techniques：ゼロショット、few-shot、思考の連鎖）
| 手法 | 使う場面 | 注意点 |
|---|---|---|
| ゼロショット | 単純で明確なタスク | 指示を明確にし、文脈を与える |
| few-shot | 形式、トーン、境界的な判断を伝えたい | **多様な例とエッジケース**を含める。同じパターンばかりだと、その表面に過剰に合わせてしまう |
| 思考の連鎖（CoT）、thinking | 複数のステップを踏む推論、判定 | 推論と回答をタグで分ける。thinking と effort で調整する |
| 文書を先、質問を後に | 長文の分析 | 逐語の引用を先に抜き出させる |

### 6-4. コンテキストウィンドウを最適化し、トークン使用量を管理する（Optimize context windows and manage token usage）
- 大きなコンテキストウィンドウ（1M）があっても、**注意の予算** と context rot の問題は残ります。そのため **最小の高シグナルなトークン** を目指します。
- 方法：**サーバー側のコンパクション**（長い会話の管理で最初に使う手段）、**ツール結果のクリア**、thinking ブロックのクリア、構造化メモ、サブエージェントによる圧縮、ジャストインタイム検索、Token Counting API による事前の見積もり。

### 6-5. プロンプトの再利用戦略を実装する（Implement prompt reuse strategies：キャッシング、モジュール型プロンプト、スキル）
- **キャッシング**：3-5 を参照（公式サンプル2：**変化しない内容を先に置き、キャッシングを有効にする** と、TTFTとコストの両方が下がる）。
- **モジュール型プロンプト**：共通部分（ポリシー、形式）と用途ごとの部分を分け、バージョンを管理します（評価と紐づける）。
- **Agent Skills**（段階的開示）
| レベル | 読み込まれるタイミング | トークンの目安 | 内容 |
|---|---|---|---|
| 1：メタデータ | 常に（起動時） | 1スキルあたり約100 | frontmatter の name と description |
| 2：指示 | スキルがトリガーされたとき | 5,000未満 | SKILL.md の本文 |
| 3：リソース | 必要なとき | アクセスされるまで0 | 追加ファイル（読んだときに読み込まれる）、スクリプト（bashで実行され、**実行結果だけ**がコンテキストに入る） |
- ★ description は「**何をするスキルか**」と「**いつ使うか**」の両方を書きます（Claude がトリガーを判断する材料になる）。

エージェントが持つツールは「その役割に必要な最小限」が原則。公式ドキュメントでは、ツールが30〜50個を超えると選択精度が落ち、複数MCPサーバーの定義だけで約55kトークンになる例が挙げられており、ツール検索で85%超削減できるとしています。不要な書き込み系の除去（最小権限）と、オンデマンド読み込み（段階的ディスカバリー）の組み合わせが正解です。  
- × A：max_tokens は出力上限で、入力側のツール定義の肥大やツール選択ミスとは無関係。
- ○ B：正解。機能の肥大化（capability bloat）を最小権限とコンテキスト効率の両面で解消する。
- × C：トークン消費がさらに増え、不要な書き込み権限も残る。
- × D：モデルサイズは不要な権限・コンテキスト消費を減らさない（サンプル1のDと同じ発想）。
- 出典：https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool

**問2　正解：D**（分野3 統合）

- × B：トランスポートの変更では認可のギャップは解消しない。
- × C：ログは発見的統制。不正なトークン受け入れや過剰権限そのものは残る。
- ○ D：正解。MCP仕様はトークンパススルーを明示的に禁止し、audience検証を求めている。
- 出典：https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization

**問29　正解：B**（分野7 開発者の生産性と運用支援）
