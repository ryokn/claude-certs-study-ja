## SLIDE: 4-3 出力の処理（2.6%）★
- **構造化出力**（JSON outputs）：output_config.format に {"type": "json_schema", "schema": ...}
- SDK の **messages.parse()**（Pydantic や Zod）なら検証済みの **parsed_output**
- ツール入力のスキーマを保証したいなら **厳格なツール使用**（strict: true）
- スキーマに合っていても **中身が正しいとは限らない**
- → **業務ルールで検証する**（合計の整合性、日付の範囲など）

めたん: 最後は、出力の処理ですわね。
ずんだもん: {JSON|ジェイソン}で受け取りたいときは、構造化出力を使うのだ。{output_config|アウトプットコンフィグ}の{format|フォーマット}に、{JSON|ジェイソン}スキーマを指定するのだ。
めたん: {SDK|エスディーケー}で、楽にできますの？
ずんだもん: {messages.parse|メッセージズ ドット パース}を使えば、{Pydantic|パイダンティック}や{Zod|ゾッド}で、検証済みの{parsed_output|パースドアウトプット}が得られるのだ。
めたん: ツールの入力の形も、保証できますの？
ずんだもん: 厳格なツール使用、{strict|ストリクト} {true|トゥルー}なのだ。
めたん: スキーマに合っていれば、もう安心ですわね。
ずんだもん: そこが、ひっかけなのだ！スキーマに合っていても、中身が正しいとは限らないのだ。
めたん: では、どうしますの？
ずんだもん: 業務ルールで検証するのだ。合計の整合性や、日付の範囲などなのだ。

## SLIDE: コード例：構造化出力（JSON outputs）
```
resp = client.messages.create(
  model=MODEL, max_tokens=512,
  messages=[{"role": "user", "content": f"<invoice>{text}</invoice> から抽出"}],
  output_config={"format": {"type": "json_schema", "schema": {
     "type": "object", "additionalProperties": False,
     "properties": {"total": {"type": "number"}, "date": {"type": "string"}},
     "required": ["total", "date"]}}})
data = json.loads(resp.content[0].text)
assert data["total"] >= 0  # 業務ルールの検証を省かない
```
- 請求書は **<invoice> タグ** で区切る ／ スキーマは **required ＋ additionalProperties: False**

ずんだもん: コードで見ると、こうなるのだ。請求書の本文は、{invoice|インボイス}タグで区切っているのだ。
めたん: スキーマには、{required|リクワイアード}と{additionalProperties|アディショナルプロパティーズ} {False|フォルス}。第2回のスキーマ設計ですわね。
ずんだもん: そうなのだ。そして最後の行。合計が0以上かどうか、業務ルールを検証しているのだ。
めたん: 形が正しくても、中身は自分で確かめる。大事ですわね。
