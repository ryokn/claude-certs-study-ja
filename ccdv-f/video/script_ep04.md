## SLIDE: 2-1 LLMの基礎：範囲と非決定性
- 試験ガイドの範囲：トークン、コンテキストウィンドウ、サンプリング、非決定性、次トークン生成
- モデルのオプション：高速モード、拡張思考、適応型思考、エフォートレベル
- ゼロショット・シングルショット・マルチショット
- **非決定性**：temperature を0にしても **完全には決定的にならない**（公式の用語集）
- テストは完全一致ではなく **ルーブリックやスキーマで判定**し、**複数回試行**する

めたん: まずは、{LLM|エルエルエム}の基礎ですわ。
ずんだもん: 範囲は、トークン、コンテキストウィンドウ、サンプリング、非決定性、次トークン生成。
ずんだもん: それに、高速モードや思考、エフォートなどのモデルのオプションと、ゼロショット、シングルショット、マルチショットなのだ。
めたん: 非決定性、というのは？
ずんだもん: 同じ入力でも、出力が毎回同じとは限らない、ということなのだ。
めたん: {temperature|テンパラチャー}を0にすれば、毎回同じになりますわよね？
ずんだもん: それが、ひっかけなのだ！公式の用語集には、0にしても完全には決定的にならない、と書いてあるのだ。
めたん: では、テストはどうしますの？
ずんだもん: 完全一致で比べるのではなく、ルーブリックやスキーマで判定するのだ。そして、複数回試行するのだ。

## SLIDE: コンテキストウィンドウと max_tokens ★
- **コンテキストウィンドウ**：入力と出力を合わせたトークンの上限
- 2026年11月時点の現行モデル：**1Mトークン**、最大出力 **128K**（試験時点の数値は要確認）
- **max_tokens** は **出力** の上限で、**思考も含む**
- 入力の肥大化対策にはならない

めたん: コンテキストウィンドウは、どういうものですの？
ずんだもん: 入力と出力を、合わせたトークンの上限なのだ。
ずんだもん: 2026年11月時点の現行モデルは、100万トークン。最大出力は128Kなのだ。ただ、試験時点の数値は要確認なのだ。
めたん: では、{max_tokens|マックストークンズ}は？
ずんだもん: 出力の上限なのだ。しかも、思考のトークンも含むのだ。
めたん: 入力が長すぎるときに、{max_tokens|マックストークンズ}を増やせば……
ずんだもん: 入らないのだ！入力の上限は、コンテキストウィンドウなのだ。{max_tokens|マックストークンズ}は、入力の肥大化対策にはならないのだ。

## SLIDE: effort と高速モード
- **effort**（output_config.effort）：low ／ medium ／ high ／ xhigh ／ max
- **low**：最も効率的（サブエージェントなどの単純なタスク向け）　**max**：最大性能
- **既定値はモデルによって違う**（例：Opus 5.5 と Haiku 5.5 は medium、それ以外の多くは high。2026年11月時点）
- xhigh に対応していないモデルもある
- **高速モード**：speed: "fast" で出力速度が **最大2.5倍**。割増料金、対応モデルは限られる
- 速度の設定を切り替えると **system と messages のキャッシュが無効** になる

めたん: {effort|エフォート}というのは、何ですの？
ずんだもん: 応答全体のトークン消費を制御する、主要なパラメータなのだ。{low|ロー}、{medium|ミディアム}、{high|ハイ}、{xhigh|エックスハイ}、{max|マックス}の5段階なのだ。
めたん: どう使い分けますの？
ずんだもん: {low|ロー}は最も効率的で、サブエージェントなどの単純なタスク向き。{max|マックス}は最大性能なのだ。
めたん: 既定値は、どれですの？
ずんだもん: モデルによって違うのだ。2026年11月時点では、{Opus|オーパス} 5.5と{Haiku|ハイク} 5.5は{medium|ミディアム}、それ以外の多くは{high|ハイ}なのだ。
ずんだもん: {xhigh|エックスハイ}に対応していないモデルもあるのだ。
めたん: 高速モード、というのもありましたわね。
ずんだもん: {speed|スピード}を{fast|ファスト}にすると、出力速度が最大2.5倍になるのだ。ただし割増料金で、対応モデルは限られるのだ。
めたん: 何か、注意点は？
ずんだもん: キャッシュとの関係なのだ。速度の設定を切り替えると、{system|システム}と{messages|メッセージズ}のキャッシュが無効になるのだ。

## SLIDE: 2-2 技術的な基礎（6.1%）★
- 試験ガイドの範囲：REST API をラップする SDK との統合、WebSocket
- 公式の Client SDK は **REST API のラッパー**
- 一時的な失敗（接続エラー、429、5xx）を **既定で2回**、指数バックオフで **自動リトライ**、retry-after に従う
- 回数は **max_retries**（TypeScript では maxRetries）で変更
- エラーとレスポンスには **request_id**（request-id ヘッダー）。SDK では **_request_id**
- **WebSocket**：双方向の常時接続（音声などのリアルタイム用途）。Messages API は **ストリーミング（SSE）**

めたん: 次は、2-2「技術的な基礎」。6.1パーセントもありますのね。
ずんだもん: 範囲は、{REST API|レスト エーピーアイ}をラップする{SDK|エスディーケー}との統合と、{WebSocket|ウェブソケット}なのだ。
ずんだもん: 公式の{Client SDK|クライアント エスディーケー}は、{REST API|レスト エーピーアイ}のラッパーなのだ。
めたん: 第2回のコード例で、自動リトライが出てきましたわね。
ずんだもん: そうなのだ。接続エラー、429、500番台のような一時的な失敗を、既定で2回、指数バックオフで自動リトライするのだ。{retry-after|リトライアフター}にも従うのだ。
めたん: 回数は変えられますの？
ずんだもん: {Python|パイソン}なら{max_retries|マックスリトライズ}、{TypeScript|タイプスクリプト}なら{maxRetries|マックスリトライズ}なのだ。
めたん: 問い合わせのときに役立つものは？
ずんだもん: {request_id|リクエストアイディー}なのだ。エラーにもレスポンスにも付いていて、{SDK|エスディーケー}ではアンダースコア{request_id|リクエストアイディー}で取れるのだ。
めたん: {WebSocket|ウェブソケット}は？
ずんだもん: 双方向の常時接続で、音声などのリアルタイム用途で出てくるのだ。{Claude|クロード}の{Messages API|メッセージズ エーピーアイ}は、{SSE|エスエスイー}のストリーミングを使うのだ。{WebSocket|ウェブソケット}を使う{API|エーピーアイ}の詳細は、要確認なのだ。

## SLIDE: 2-4 コストとトークンの管理（2.8%）
- **usage** でトークンを追跡する
- コストのモデル化：**入力 × 単価 ＋ 出力 × 単価 ＋ キャッシュの書き込み・読み出し**
- 組み合わせて下げる：
- キャッシュのブレークポイント設計 ／ **バッチの50%割引**
- **小さいモデルへのルーティング** ／ **effort の調整** ／ **出力を短くする指示**

めたん: 最後は、コストとトークンの管理ですわ。
ずんだもん: まず、{usage|ユーセージ}でトークンを追跡するのだ。
ずんだもん: コストは、入力かける単価、足す、出力かける単価、それにキャッシュの書き込みと読み出し、でモデル化するのだ。
めたん: 下げるには、どうしますの？
ずんだもん: 組み合わせ技なのだ。キャッシュのブレークポイント設計、バッチの50パーセント割引、小さいモデルへのルーティング。
ずんだもん: それに、{effort|エフォート}の調整と、出力を短くする指示なのだ。
めたん: 第1回のバッチとキャッシュが、ここでも出てきますのね。
ずんだもん: そうなのだ。コスト削減の問題では、この組み合わせを思い出すのだ。
