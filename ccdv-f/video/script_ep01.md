## SLIDE: Messages API の基礎
- Messages API は **ステートレス**
- 会話の履歴は **毎回 messages に入れて送る**
- ロールは **user と assistant が交互**
- システム指示は **トップレベルの system** に置く

めたん: まずは、{Messages API|メッセージズ エーピーアイ}の基本から。
ずんだもん: {Messages API|メッセージズ エーピーアイ}は、ステートレスなのだ。
めたん: ステートレス……サーバー側が、会話を覚えていないということかしら？
ずんだもん: その通りなのだ。だから会話の履歴は、毎回{messages|メッセージズ}に入れて送るのだ。
めたん: ロールの決まりはありますの？
ずんだもん: {user|ユーザー}と{assistant|アシスタント}が、交互になるのだ。
めたん: システムへの指示は、どこに書きますの？
ずんだもん: トップレベルの{system|システム}に置くのだ。

## SLIDE: レスポンスの stop_reason と usage
- **stop_reason** の主な値（公式「stop reasons」ページ）
- end_turn ／ max_tokens ／ stop_sequence ／ tool_use
- pause_turn ／ refusal ／ model_context_window_exceeded
- **usage** に入るもの
- input_tokens ／ output_tokens
- cache_creation_input_tokens ／ cache_read_input_tokens

めたん: レスポンスで、見るべきところはどこですの？
ずんだもん: まずは{stop_reason|ストップリーズン}。応答が止まった理由なのだ。
ずんだもん: 主な値は、{end_turn|エンドターン}、{max_tokens|マックストークンズ}、{stop_sequence|ストップシーケンス}、{tool_use|ツールユース}、{pause_turn|ポーズターン}、{refusal|リフューザル}、それに{model_context_window_exceeded|モデル コンテキストウィンドウ エクシーディッド}なのだ。
めたん: 7つもありますのね。{tool_use|ツールユース}は？

ずんだもん: もう一つが{usage|ユーセージ}。入力と出力のトークン数に加えて、キャッシュの書き込みと読み出しのトークン数も入るのだ。
めたん: キャッシュが効いたかどうか、ここで確かめられますのね。

## SLIDE: リアルタイムとバッチの使い分け ★
| 観点 | Messages API（同期） | Message Batches API |
| レイテンシ | 即時。ストリーミングも可 | 非同期。多くは1時間以内、最長24時間（過ぎると期限切れ） |
| 料金 | 通常料金 | 50%割引 |
| 上限 | — | 1バッチ 100,000リクエスト または 256MB |
| 結果 | 即座に返る | 作成から29日間ダウンロード可。順序は保証されない → custom_id で照合 |
| 用途 | チャット、対話型エージェント | 夜間の一括分類・要約・評価の実行 |

めたん: 次は、リアルタイムとバッチの使い分けですわ。
ずんだもん: 普通の{Messages API|メッセージズ エーピーアイ}は同期で、すぐに返ってくるのだ。ストリーミングもできて、チャットや対話型エージェント向きなのだ。
めたん: バッチの方は？
ずんだもん: {Message Batches API|メッセージ バッチズ エーピーアイ}は非同期なのだ。多くは1時間以内、最長24時間で、24時間で終わらなければ期限切れなのだ。
ずんだもん: そのかわり、料金はなんと50パーセント割引なのだ！
めたん: 半額ですの！夜間の一括分類や要約、評価の実行に、ぴったりですわね。
めたん: 上限はありますの？
ずんだもん: 1バッチあたり10万リクエスト、または256メガバイトなのだ。
めたん: 結果は、いつまで取れますの？
ずんだもん: 作成から29日間なのだ。そして、ここが大事なのだ。結果の順序は、保証されないのだ。
めたん: 順番がばらばら……では、どうやって対応づけますの？
ずんだもん: リクエストごとに{custom_id|カスタムアイディー}を付けて、それで照合するのだ。

## SLIDE: バッチの作り方と、ひっかけ
```
batch = client.messages.batches.create(requests=[
    {"custom_id": f"ticket-{i}",
     "params": {"model": MODEL, "max_tokens": 256,
                "messages": [{"role": "user", "content": f"分類して: {t}"}]}}
    for i, t in enumerate(["返金したい", "ログインできない"])
])
# processing_status が "ended" → results を custom_id で突き合わせる
```
- ひっかけ：同期の並列送信で安くなる → **単価は変わらない。安くするならバッチかキャッシュ**
- 公式サンプル問題1：夜間の非緊急な1万件 → **Message Batches API**

ずんだもん: {Python|パイソン}だと、こんな感じなのだ。リクエストごとに、{ticket|チケット}0、{ticket|チケット}1のような{custom_id|カスタムアイディー}を付けて作るのだ。
めたん: 終わったかどうかは、どう分かりますの？
ずんだもん: {processing_status|プロセッシングステータス}が{ended|エンディッド}になったら結果を取って、{custom_id|カスタムアイディー}で突き合わせるのだ。
めたん: 「同期の並列送信で安くなる」というのは、ひっかけですわね？
ずんだもん: その通りなのだ。並列にしても、単価は変わらないのだ。安くしたいなら、バッチかキャッシュなのだ。
ずんだもん: 公式のサンプル問題にも、夜間の急がない1万件をどう処理するか、という問題があるのだ。答えは、{Message Batches API|メッセージ バッチズ エーピーアイ}なのだ。

## SLIDE: プロンプトキャッシング（1）仕組み ★
- プレフィックスは **tools → system → messages** の順
- ある階層を変えると、**その階層と後ろがすべて無効**
- 自動キャッシュ：トップレベルに cache_control を1つ → 最後のキャッシュ可能ブロックに
- 明示的なブレークポイント：ブロックごとに指定、**最大4つ**
- ブレークポイントは **変わらない部分の最後** に置く

めたん: では、そのキャッシュ。プロンプトキャッシングですわ。
ずんだもん: プレフィックスは、{tools|ツールズ}、{system|システム}、{messages|メッセージズ}の順に作られるのだ。ある階層を変えると、その階層と後ろが、全部無効になるのだ。
めたん: ということは、ツールの定義を変えると……
ずんだもん: いちばん前だから、キャッシュ全体が無効なのだ。ツールの並び順を毎回変えるのも、ダメなのだ。
めたん: 使い方は、どうしますの？
ずんだもん: 2つあるのだ。1つ目は自動キャッシュ。トップレベルに{cache_control|キャッシュコントロール}を1つ付けると、最後のキャッシュ可能なブロックに、ブレークポイントが置かれるのだ。
ずんだもん: 2つ目は、明示的なブレークポイント。ブロックごとに指定して、最大4つまでなのだ。
めたん: ブレークポイントは、どこに置けばよろしいの？
ずんだもん: 変わらない部分の最後なのだ。タイムスタンプやユーザー入力のように、毎回変わる部分の末尾に置くのは、典型的なひっかけなのだ。

## SLIDE: プロンプトキャッシング（2）TTL・料金・落とし穴
- TTL 既定 **5分**（使うたびに無料で延長）／ "ttl": "1h" で1時間
- 書き込み：基本入力単価の **1.25倍**（1時間TTLは **2倍**）
- 読み出し：基本単価の **10%**（モデル差あり：要確認）
- **最小キャッシュ可能長** 未満は **エラーなしで黙ってキャッシュされない**
- → cache_creation_input_tokens と cache_read_input_tokens がどちらも0
- 振り返り（lookback）は **20ブロック** → 長い会話は途中にもブレークポイント

めたん: {TTL|ティーティーエル}と料金も、教えてくださる？
ずんだもん: {TTL|ティーティーエル}は既定で5分。使うたびに、無料で延長されるのだ。1時間を指定することもできるのだ。
ずんだもん: 書き込みは基本入力単価の1.25倍、1時間なら2倍。読み出しは、基本単価の10パーセントなのだ。モデルによって差がある点は、要確認なのだ。
めたん: 短いプロンプトでも、効きますの？
ずんだもん: 最小キャッシュ可能長に満たないと、キャッシュされないのだ。しかも、エラーは返らないのだ。
めたん: 黙って、ですの？どうやって気づけばよろしいの？
ずんだもん: {usage|ユーセージ}のキャッシュ書き込みと読み出しのトークン数が、どちらも0になるのだ。
めたん: 長い会話で、気をつけることは？
ずんだもん: 振り返り、ルックバックは20ブロックなのだ。会話が伸びると、前回の書き込み位置が窓の外に出て、ヒットしなくなることがあるのだ。
めたん: そのときは、どうしますの？
ずんだもん: 途中にも、ブレークポイントを置くのだ。

## SLIDE: キャッシュのひっかけ ★
| ひっかけ | 正しくは |
| 毎回変わる部分の末尾にブレークポイント | 変わらない部分の最後に置く |
| ツールの並び順を毎回変えても問題ない | ツール定義を変えるとキャッシュ全体が無効 |
| キャッシュは短いプロンプトでも効く | 最小長未満は黙ってキャッシュされない |
| 並列の同期リクエストでコストが下がる | 単価は変わらない。バッチかキャッシュ |
| バッチでもキャッシュは確実にヒットする | バッチでのヒットはベストエフォート |

めたん: キャッシュのひっかけを、まとめて確認しますわ。わたくしが間違いを言いますわね。
ずんだもん: どんと来いなのだ！
めたん: 毎回変わる部分の末尾に、ブレークポイントを置く。
ずんだもん: ブブー、なのだ。変わらない部分の最後なのだ。
めたん: ツールの並び順を変えても、平気。
ずんだもん: ダメなのだ。キャッシュ全体が無効になるのだ。
めたん: 短いプロンプトでも、キャッシュは効く。
ずんだもん: 最小長未満は、黙ってキャッシュされないのだ。
めたん: バッチでも、キャッシュは確実にヒットする。
ずんだもん: バッチでのヒットは、ベストエフォートなのだ。確実ではないのだ。

## SLIDE: キャッシュのコード例
```
resp = client.messages.create(
    model=MODEL, max_tokens=512,
    system=[{"type": "text", "text": LONG_POLICY_TEXT,
             "cache_control": {"type": "ephemeral"}}],  # 変わらない部分の最後
    messages=[{"role": "user", "content": user_question}],  # 可変部分
)
print(resp.usage.cache_creation_input_tokens, resp.usage.cache_read_input_tokens)
```
- 固定の長い文書を system に置き、その **最後のブロックに cache_control**
- 可変のユーザー入力は messages 側へ

ずんだもん: コードで見ると、長いポリシーの文章を{system|システム}に入れて、そのブロックに{cache_control|キャッシュコントロール}を付けるのだ。
めたん: 変わらない部分の最後、ですわね。ユーザーの質問は、{messages|メッセージズ}の方に置く。
ずんだもん: そうなのだ。最後に{usage|ユーセージ}を表示して、書き込みと読み出しを確かめるのだ。

## SLIDE: ストリーミング・ビジョン・思考
- 長時間の応答や **504 timeout_error** → **ストリーミング**が公式の推奨
- ビジョン：画像を入力できる。PDF などの文書も入力できる
- **適応型思考**（adaptive）：thinking: {"type": "adaptive"}。量はモデルが決め、effort で調整
- **拡張思考**（extended）：{"type": "enabled", "budget_tokens": N}。旧来の手動方式
- 拡張思考は Opus 4.6 / Sonnet 4.6 で非推奨、それより新しいモデルでは受け付けられない
- 試験ガイドには **両方出てくる** → 違いを押さえる

めたん: 続いて、ストリーミング、ビジョン、思考ですわ。
ずんだもん: 長時間かかる応答や、504の{timeout_error|タイムアウトエラー}には、ストリーミングが公式の推奨なのだ。
めたん: 504が出たら、とりあえず再送……ではありませんのね。
ずんだもん: そうなのだ。504には、ストリーミングなのだ。
ずんだもん: ビジョンでは画像を入力できて、{PDF|ピーディーエフ}などの文書も入力できるのだ。
めたん: 思考、というのは？
ずんだもん: 最新モデルは、適応型思考なのだ。思考の量はモデルが決めて、{effort|エフォート}で調整するのだ。
めたん: 拡張思考、というのも聞きますわ。
ずんだもん: 拡張思考は、{budget_tokens|バジェットトークンズ}を指定する、旧来の手動方式なのだ。{Opus|オーパス} 4.6と{Sonnet|ソネット} 4.6では非推奨で、それより新しいモデルでは受け付けられないのだ。
めたん: 試験では、どちらが出ますの？
ずんだもん: 試験ガイドには、両方とも出てくるのだ。だから、違いを押さえておくのだ。

## SLIDE: まとめ（1-1 Claude APIの仕組み）

- 最小長未満は **黙ってキャッシュされない**／lookback は20ブロック
- 504 → **ストリーミング**。思考は **適応型と拡張型の違い**
