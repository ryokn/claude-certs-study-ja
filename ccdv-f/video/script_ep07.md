## SLIDE: 5-1 クライアント側ツールとサーバー側ツール ★
- **クライアント側ツール**：自分のアプリが実行する
- Anthropic がスキーマを定義した **bash** や **text_editor** なども含む
- **サーバー側ツール**：Anthropic の基盤で実行される
- 例：**web_search**、**web_fetch**、**code_execution**、**tool_search**

めたん: ツールには、種類がありますの？
ずんだもん: 2種類あるのだ。クライアント側ツールと、サーバー側ツールなのだ。
めたん: クライアント側は？
ずんだもん: 自分のアプリが実行するツールなのだ。{Anthropic|アンソロピック}がスキーマを定義した、{bash|バッシュ}や{text_editor|テキストエディター}なども含むのだ。
めたん: スキーマが用意されていても、実行するのは自分のアプリ、ですのね。
ずんだもん: そうなのだ。サーバー側ツールは、{Anthropic|アンソロピック}の基盤で実行されるのだ。{web_search|ウェブサーチ}、{web_fetch|ウェブフェッチ}、{code_execution|コードエグゼキューション}、{tool_search|ツールサーチ}などなのだ。

## SLIDE: ツール使用ループの規則 ★
- **stop_reason: "tool_use"** → ツールを実行
- 次の **user** メッセージに **tool_result**（**tool_use_id** で対応付け）を **先頭** に置く。テキストはその後
- tool_use の直後に、別のメッセージを挟まない
- 失敗したら **is_error: true**

めたん: クライアント側ツールは、どういう流れで動きますの？
ずんだもん: レスポンスの{stop_reason|ストップリーズン}が{tool_use|ツールユース}になったら、ツールを実行するのだ。
めたん: 結果は、どう返しますの？
ずんだもん: 次の{user|ユーザー}メッセージに、{tool_result|ツールリザルト}を入れるのだ。{tool_use_id|ツールユースアイディー}で対応付けるのだ。
ずんだもん: ここが大事なのだ。{tool_result|ツールリザルト}は、先頭に置くのだ。テキストは、その後なのだ。
めたん: 間に、別のメッセージを挟んでもよろしいの？
ずんだもん: 挟まないのだ。{tool_use|ツールユース}の直後に、別のメッセージを挟まないのだ。
めたん: ツールが失敗したときは？
ずんだもん: {is_error|イズエラー} {true|トゥルー}を付けて、返すのだ。

## SLIDE: コード例：クライアント側ツールのループ（1/2）
```
msgs = [{"role": "user", "content": "東京の天気は？"}]
while True:
    r = client.messages.create(model=MODEL, max_tokens=1024, tools=TOOLS, messages=msgs)
    msgs.append({"role": "assistant", "content": r.content})
    if r.stop_reason != "tool_use":
        break
    # → 続きは次のスライド：ツールを実行して tool_result を返す
```
- 応答をそのまま **assistant** として履歴に追加（ステートレスなので毎回送る）
- **stop_reason が tool_use でなければ終了**

ずんだもん: コードで見るのだ。まず、ユーザーの質問を{messages|メッセージズ}に入れて、ループで呼び出すのだ。
ずんだもん: 返ってきた応答は、そのまま{assistant|アシスタント}として履歴に足すのだ。
めたん: {Messages API|メッセージズ エーピーアイ}はステートレスだから、履歴は毎回送る。第1回のお話ですわね。
ずんだもん: その通りなのだ。そして、{stop_reason|ストップリーズン}が{tool_use|ツールユース}でなければ、ループを抜けるのだ。

## SLIDE: コード例：クライアント側ツールのループ（2/2）
```
    results = []
    for b in r.content:
        if b.type == "tool_use":
            try:
                out, err = run_tool(b.name, b.input), False
            except Exception as e:
                out, err = str(e), True
            results.append({"type": "tool_result", "tool_use_id": b.id,
                            "content": str(out), "is_error": err})
    msgs.append({"role": "user", "content": results})  # tool_result を先頭に置く
```

めたん: 後半は、ツールを実行する部分ですわね。
ずんだもん: 応答の中の{tool_use|ツールユース}ブロックごとに、ツールを実行するのだ。
ずんだもん: 失敗したら、例外のメッセージを入れて、{is_error|イズエラー}を{true|トゥルー}にするのだ。
めたん: {tool_use_id|ツールユースアイディー}には、ブロックの{id|アイディー}を入れていますわね。
ずんだもん: そうなのだ。そして、結果をまとめて{user|ユーザー}メッセージとして足すのだ。{tool_result|ツールリザルト}が先頭なのだ。

## SLIDE: tool_choice とツールの説明
- **tool_choice**：auto（既定）／ any ／ tool（特定のツールを指定）／ none
- **disable_parallel_tool_use** で並列呼び出しを止められる
- モデルや設定によっては **any と tool が使えない**（例：手動の拡張思考ではエラー。2026年11月時点では Opus 5.5 や Sonnet 5.5 でも400エラー → **auto と strict**）：要確認
- ツールの説明は「**何をするか、いつ使うか、引数の意味、返り値**」を具体的に
- ツールの **数と重複は最小限**／破壊的なツールには **人間の承認やフック**

めたん: ツールを使うかどうかは、指定できますの？
ずんだもん: {tool_choice|ツールチョイス}なのだ。{auto|オート}が既定で、ほかに{any|エニー}、{tool|ツール}、{none|ノン}があるのだ。
ずんだもん: それと、{disable_parallel_tool_use|ディセーブル パラレル ツールユース}で、並列の呼び出しを止められるのだ。
めたん: 必ず特定のツールを使わせたいときは、{tool|ツール}を指定すればよろしいのね。
ずんだもん: ところが、モデルや設定によっては、{any|エニー}と{tool|ツール}が使えないのだ。手動の拡張思考では、エラーになるのだ。
ずんだもん: 2026年11月時点では、{Opus|オーパス} 5.5や{Sonnet|ソネット} 5.5でも400エラーで、代わりに{auto|オート}と{strict|ストリクト}を使うのだ。ここは要確認の注意点なのだ。
めたん: ツールの説明は、どう書けばよろしいの？
ずんだもん: 何をするか、いつ使うか、引数の意味、返り値を、具体的に書くのだ。ツールの数と重複は、最小限にするのだ。
めたん: 削除のような、危ないツールは？
ずんだもん: 破壊的なツールには、人間の承認やフックを挟むのだ。

## SLIDE: 5-2 MCPサーバーの開発（2.1%）
| プリミティブ | 誰が制御するか |
| ツール | モデルが制御する |
| リソース | アプリが制御する読み取り専用のデータ |
| プロンプト | ユーザーが明示的に呼び出すテンプレート |
- 標準のトランスポート：**stdio** と **Streamable HTTP**（旧 HTTP+SSE の後継）
- stdio では **サーバーは stdout に MCP メッセージ以外を書いてはならない**。ログは **stderr**

めたん: 次は、{MCP|エムシーピー}サーバーの開発ですわ。
ずんだもん: {MCP|エムシーピー}には、3つのプリミティブがあるのだ。ツール、リソース、プロンプトなのだ。
めたん: 違いは何ですの？
ずんだもん: 誰が制御するか、なのだ。ツールはモデルが制御するのだ。リソースは、アプリが制御する、読み取り専用のデータなのだ。
ずんだもん: プロンプトは、ユーザーが明示的に呼び出すテンプレートなのだ。
めたん: モデル、アプリ、ユーザー。覚えやすいですわ。通信の方法は？
ずんだもん: 標準のトランスポートは、{stdio|スタンダード アイオー}と、{Streamable HTTP|ストリーマブル エイチティーティーピー}なのだ。旧来の{HTTP|エイチティーティーピー}プラス{SSE|エスエスイー}の後継なのだ。
めたん: 注意点は、ありますの？
ずんだもん: 大ありなのだ！{stdio|スタンダード アイオー}では、サーバーは標準出力に、{MCP|エムシーピー}メッセージ以外を書いてはいけないのだ。
めたん: デバッグのために、{print|プリント}したくなりますわ。
ずんだもん: それが、ひっかけなのだ。ログは、標準エラー出力に出すのだ。

## SLIDE: 5-3 エージェントのカスタマイズ（4.1%）★
| 手段 | 向いているもの | 注意 |
| 組み込みツール | 汎用的なファイル操作・シェル・Web 検索 | 任意の社内 API には自動でつながらない |
| カスタムツール | 1つのアプリ固有の関数呼び出し | アプリごとに実装・保守が必要 |
| スキル（Skills） | 手順・知識・スクリプトを SKILL.md にまとめ、必要なときに読み込む | description が自動で呼び出されるかを左右する。Claude Code では /skill-name でも呼べる。カスタムコマンドはスキルに統合 |
| MCP | 外部システムとの接続を複数のアプリで共有し、独立して保守したい | サーバーの権限・認証の設計が必要 |

めたん: エージェントに機能を足す方法は、どれを選べばよろしいの？
ずんだもん: 4つあるのだ。組み込みツールは、汎用的なファイル操作、シェル、ウェブ検索向きなのだ。ただし、社内の{API|エーピーアイ}には、自動ではつながらないのだ。
ずんだもん: カスタムツールは、1つのアプリ固有の関数呼び出し向きなのだ。アプリごとに実装と保守が必要なのだ。
めたん: スキルは？
ずんだもん: 手順や知識、スクリプトを{SKILL.md|スキル エムディー}にまとめて、必要なときに読み込むのだ。{description|ディスクリプション}が、自動で呼び出されるかどうかを左右するのだ。
ずんだもん: {Claude Code|クロードコード}では、スラッシュとスキル名で、明示的にも呼べるのだ。カスタムコマンドは、スキルに統合されたのだ。
めたん: {MCP|エムシーピー}は？
ずんだもん: 外部システムとの接続を、複数のアプリで共有して、独立して保守したいときなのだ。サーバーの権限と認証の設計が必要なのだ。

## SLIDE: 公式サンプル問題3 と ひっかけ ★
- サンプル問題3：社内の REST API を **複数アプリで再利用** → **MCP サーバー**
- 不正解の典型：プロンプトにハードコード、データの貼り付け、組み込みツール
| ひっかけ | 正しくは |
| stdio の MCP サーバーで print デバッグ | stdout は MCP メッセージ専用。ログは stderr |
| 社内 API を各アプリにハードコード | MCP サーバーで共有する |
| 組み込みツールで社内 API につながる | 任意の社内 API には自動でつながらない |

めたん: 公式のサンプル問題にも、出てきますのね。
ずんだもん: サンプル問題3は、社内の{REST API|レスト エーピーアイ}を、複数のアプリで再利用したい、という問題なのだ。答えは、{MCP|エムシーピー}サーバーなのだ。
めたん: 不正解の典型は？
ずんだもん: プロンプトにハードコードする、データを貼り付ける、組み込みツールを使う、なのだ。
めたん: では、ひっかけクイズですわ。{stdio|スタンダード アイオー}の{MCP|エムシーピー}サーバーで、{print|プリント}デバッグ。
ずんだもん: ブブー、なのだ。標準出力は{MCP|エムシーピー}メッセージ専用。ログは標準エラー出力なのだ。
めたん: 社内{API|エーピーアイ}を、各アプリにハードコード。
ずんだもん: ダメなのだ。{MCP|エムシーピー}サーバーで共有するのだ。
めたん: 組み込みツールなら、社内{API|エーピーアイ}にもつながる。
ずんだもん: つながらないのだ。任意の社内{API|エーピーアイ}には、自動ではつながらないのだ。

## SLIDE: まとめ（分野8）

- tool_use → 実行 → 次の user に **tool_result を先頭**、tool_use_id で対応、失敗は **is_error: true**

- 複数アプリで共有するなら **MCP サーバー**、手順や知識は **スキル**
