### 0-3. CCDV-F 合格者向け：どこが「Professional」なのか

公式の準備コースページの言い方では、Foundations が「**作れるか（build）**」を問うのに対し、Professional は「**本番で運用できるか（operate）**」を問います。試験ガイド §3 も「Professional の受験者は作って出荷するだけでなく運用する」と書いています。

| 観点 | CCDV-F で問われたこと | CCDV-P で上乗せされること |
|---|---|---|
| アーキテクチャ | 要件に対してワークフローかエージェントかを選ぶ | **稼働中のシステム**を、コスト・信頼性・品質の**本番データ**を見て移行するかを判断する。中断・再起動・**モデル更新**を越えて続く耐久性 |
| 統合 | API呼び出しやエラー処理の不具合を見つける | 停止理由・エラーの**種類ごとに分岐する**フォールバック、バックプレッシャー、マルチテナントのクォータ、段階的ロールアウトとロールバック |
| 評価 | 品質目標に合った評価を作る | 評価を**リリースのゲート**として運用する。ジャッジのキャリブレーション、スイートの汚染・飽和、ライブトラフィックでの測定 |
| デバッグ | トレースから失敗モードを特定する | マルチエージェント・非決定的な障害の**発生源の切り分け**（モデル出力／ハーネス／ツール／データ）とインシデント対応 |
| コスト | 主なコスト要因を見つける | フリート全体・テナント単位で**モデル化、予測、予算の強制** |
| セキュリティ | 多層ガードレール、最小権限、APIキーの扱い | レッドチーム設計、ツール／メモリのポイズニング、流出経路、**ワークロードIDフェデレーション**、監査ログ |
| Claude Code | Claude Code を操作・拡張する | **コーディングエージェントのフリート**を指揮する（worktree、AIコードレビュー、無人実行、組織全体の設定） |
| オブザーバビリティ | 独立した分野なし | **独立した分野（12%）**：トレース、SLI/SLO、ドリフト、大量トレースの分析 |

> 本ガイドでは、CCDV-F の知識で答えられる基礎も各章に短く書いています（他の人と共有できるように）。CCDV-F 合格者は「**基礎**」を飛ばし、「**頻出ポイント**」「**ひっかけ**」と、**【P】** の付いた Professional 固有の論点を優先してください。

## 1. 分野2：本番環境の統合、信頼性、知識グラウンディング（Production Integration, Reliability, and Knowledge Grounding）20%・約12問

### 1-1. Claudeサービスの信頼性エンジニアリング（Reliability Engineering for Claude Services）★
**基礎**：Claude を呼ぶ側の失敗には、「**HTTPエラー**（リクエストが失敗した）」と「**停止理由**（HTTP 200 で返ったが途中で止まった・断られた）」の2系統があります。リトライ設計はこの区別から始まります。

| 観測されるもの | 種類 | 正しい扱い |
|---|---|---|
| 429 `rate_limit_error`（`retry-after` あり） | レート制限・ランプ制限 | `retry-after` に従い、ジッター付き指数バックオフでリトライ |
| 429 `rate_limit_error`（`retry-after` **なし**、`error.details.error_code: enforced_spend_limit_reached`） | 組織ティアの**月間支出上限**に到達 | **リトライしても回復しない**（SDKの自動リトライも失敗し続ける）。上限の引き上げ・ティア変更・利用者への通知 |
| 400 `invalid_request_error`（「specified API usage limits」） | 自分で設定した支出上限 | 上限を変える。リトライでは直らない |
| 529 `overloaded_error` ／ 500 `api_error` | 一時的な過負荷・内部エラー | バックオフ付きリトライ。続くなら別リージョン・別プラットフォームへのフォールバックを検討 |
| 504 `timeout_error` | 長いリクエストのタイムアウト | **ストリーミング**に切り替える（長時間の非ストリーミング要求を避ける） |
| 400 / 401 / 403 / 404 / 413 | 要求そのものの誤り | **リトライしない**。修正する |
| `stop_reason: "max_tokens"` | 出力上限で切れた | 同じ要求の再送は同じ切れ方を再現する。`max_tokens` を上げるか、続きを生成させる。不完全な `tool_use` ブロックは再試行が必要 |
| `stop_reason: "model_context_window_exceeded"` | コンテキストウィンドウが埋まった | 切れた応答として扱う。コンパクション・コンテキスト編集など**入力側**の対処 |
| `stop_reason: "refusal"`（HTTP 200） | 安全性分類器による拒否 | **同じモデルへの再送は再び拒否されやすい**。公式は「別のフォールバックモデルで再試行」または安全性の処理経路へ回すことを推奨 |
| `stop_reason: "pause_turn"` | サーバーツールのループが反復上限に達した | アシスタントの内容を返して続行させる（エラーではない） |

- ★ **公式サンプル1の核心**：レート制限・長さ切れ・拒否を**同じリトライ経路**に入れると、コスト増と品質低下が同時に起きる。正解は「**停止条件で分岐する**」。
- 【P】**拒否（refusal）のフォールバック**（2026-11-20時点のドキュメント）：拒否は HTTP 200 なので、5xx やエラー率だけの監視では見えません。公式の注意点は「**別モデルで再試行**」「リトライ予算は**リクエスト単位**で（エージェント＋サブエージェントで1ターンに複数の拒否が起こりうる）」「**すべての経路**（リトライ処理、エラー回復、バックグラウンドワーカー、サブエージェント呼び出し）にフォールバックを設定」「フォールバックは共有フラグではなく**リクエストの属性**にする」「拒否と、フォールバックで応答した件数を別々に計測し、その差にアラート」。
  - 方式は3つ：サーバー側フォールバック（`fallbacks`、ベータ。Claude API と Claude Models on Google Cloud（Anthropic managed）のみ）／SDKミドルウェアによるクライアント側フォールバック（どのプラットフォームでも可）／自前のリトライ＋**フォールバッククレジット**（プロンプトキャッシュはモデルごとなので、別モデルで再試行するとキャッシュを書き直すコストがかかる。それを相殺する仕組み）。
- 【P】**サーキットブレーカー**：失敗率がしきい値を超えたら、一定時間はプライマリへの呼び出しを止めて代替経路（別モデル、別リージョン、キャッシュ済み応答、機能縮退）に切り替える。リトライの嵐（retry storm）で429を増幅させないための仕組みです。
- 【P】**グレースフルデグラデーション**：全機能停止より、「要約だけ返す」「低コストモデルで暫定回答し後で更新」「非同期キューに回す」など、価値を残した縮退を選ぶ。
- 【P】**プラットフォーム間の機能の差異（feature parity）**：同じモデルでも、提供先（Claude API、Claude Platform on AWS、Amazon Bedrock、Claude Models on Google Cloud（Google managed / Anthropic managed）、Microsoft Foundry）によって使える機能やベータが違います。例：サーバー側フォールバックは一部のみ、Managed Agents は Claude API・Claude Platform on AWS・Google Cloud（Anthropic managed）のみ（いずれもベータ）、Bedrock のキャッシュ最小トークン数は AWS 側のドキュメントで定義。**別プラットフォームへのフォールバックは、使っている機能が先方にもあるか確認してから**。

**ひっかけ**
- 「リトライ回数を増やし、バックオフを広げる」→ 失敗の種類を区別していないので、長さ切れ・拒否・支出上限では無駄なコストが増えるだけ（公式サンプル1の A）。
- 「フォールバックモデルにすべてのトラフィックを恒久的に切り替える」「フォールバックを無効にする」→ 一方の失敗を別の失敗に置き換えるだけ。
- 「429 なら必ず待てば直る」→ 支出上限の429は `retry-after` がなく、待っても月が変わるまで（または上限変更まで）回復しない。

```python
# 停止条件・エラーの種類で分岐する（最小例・オリジナル）
resp = call_claude(req)                      # 例外は SDK のエラー型で分類
if resp.stop_reason == "refusal":
    return safety_path(req, resp.stop_details)   # 同じモデルへ再送しない
if resp.stop_reason in ("max_tokens", "model_context_window_exceeded"):
    return continue_or_shrink(req, resp)         # 予算を上げる／入力を減らす
return resp
# except RateLimitError as e: retry-after があればバックオフ、なければ支出上限として通知
```

### 1-2. スケールとスループットの管理（Scale and Throughput Management）★
**基礎**：Messages API のレート制限は **RPM（リクエスト/分）・ITPM（入力トークン/分）・OTPM（出力トークン/分）** をモデルクラスごとに測ります。**トークンバケット方式**で、容量は固定間隔でリセットされず継続的に回復します。60 RPM が「1秒1件」として適用されることもあり、短いバーストで429が出ます。

| 事実（Rate limits のドキュメント） | 試験での使い方 |
|---|---|
| **ITPM はキャッシュされていない入力だけを数える**（`input_tokens` と `cache_creation_input_tokens` は数える、`cache_read_input_tokens` は数えない） | ★ ITPM が律速なら、**プロンプトキャッシュでスループットが上がる**。例：ITPM 200万・キャッシュヒット率80%なら、実質1,000万入力トークン/分を処理できる |
| OTPM は実際に生成したトークンで数え、`max_tokens` の値は影響しない | `max_tokens` を下げてもレート制限対策にならない |
| **ランプ制限**：急な増加は、ITPM/OTPM の上限内でも429になりうる。上限は最近のピーク＋一定の幅で、使うほど上がる | 「上限内なのに429」→ 急な立ち上げ・数秒のバーストを疑う。**徐々に増やす** |
| Message Batches：1バッチ最大10万件または256MB、多くは1時間以内、**24時間で期限切れ**（期限切れ分は課金なし）、結果は**29日間**取得可、**料金は50%オフ** | 即時性が不要な大量処理はバッチへ。ZDR の対象外（29日保持）なので、ZDR要件のあるデータには使えない |

- 【P】**律速要因（binding constraint）を見分ける**（試験ガイドの明記事項）：
  - RPM が先に尽きる → 小さいリクエストが大量。まとめる、キューで平滑化する。
  - ITPM が先に尽きる → 長いプロンプト。**キャッシュ**（ITPM に数えない）、コンテキストの削減。
  - OTPM が先に尽きる → 長い出力。出力形式の簡素化、effort の調整、モデル選択。
  - 待てる処理が大半 → **バッチの経済性**（50%オフ）が支配的。
- 【P】**キューイングとバックプレッシャー**：上流の受け付けを無制限にせず、キューの深さ・待ち時間で受け付けを絞る（429 を返す、優先度で間引く）。キューを無制限に積むと、レイテンシが SLO を超えた「死んだ仕事」を処理し続けることになる。
- 【P】**マルチテナントのクォータと分離**：組織のレート制限は全テナントで共有されるので、1テナントのバーストが全員の429になる（noisy neighbor）。テナント単位のトークンバケット・同時実行数の上限・優先度キューで分離する。**ワークスペース**で用途を分け、ワークスペース単位の支出上限を使う手もある（キャッシュも Claude API ではワークスペースごとに分離される点に注意）。
- サービスティア：Standard が既定。Priority Tier は**新規購入できない**（既存契約のみ。2026-11-20 時点のドキュメント）。

**ひっかけ**
- 「429が増えたのでリトライを即時・多数にする」→ リトライの嵐で悪化。バックオフ＋ジッター＋同時実行数の制限。
- 「`max_tokens` を下げて OTPM 対策」→ OTPM は実際の生成量で数える。
- 「夜間の大量レポートをリアルタイムAPIで並列化」→ 待てる処理はバッチが安い。ただし24時間以内に終わらない可能性・ZDR対象外を条件で確認。

### 1-3. 本番環境のMCPと変更管理（Production MCP and Change Management）
**基礎**：MCP サーバーは、ローカル（stdio）とリモート（Streamable HTTP）で運用の論点が違います。リモートの認可は OAuth 2.1 ベースで、トークンの**パススルーは仕様で禁止**です（サーバーは自分宛てのトークンだけを受け入れる）。

- 【P】**ツールとスキーマのバージョン管理**：ツール名・引数の変更は呼び出し側（プロンプト、評価、他チームのエージェント）を壊す破壊的変更です。互換性を保つ追加を基本にし、破壊的変更は新しい名前・バージョンで並行提供してから旧版を廃止する。また、**ツール定義を変えるとプロンプトキャッシュ全体が無効になる**（tools → system → messages の階層の先頭のため）。
- 【P】**モデルバージョンの移行**：モデルIDは**固定スナップショット**です（4.6世代以降は日付なしIDも固定）。非推奨（deprecated）になったモデルには引退日が設定され、公開モデルは**少なくとも60日前**に通知されます。引退後のリクエストは失敗します。
  - ★ 移行は「**同じ評価スイートで新旧を比較 → 動作の破壊的変更（出力形式、ツール選択、拒否の傾向、effort の既定値など）を確認 → 段階的ロールアウト**」。例：effort の既定値はモデルによって違う（多くは `high`、一部は `medium`）ので、明示していないとモデル更新でコストと品質が変わる。
- 【P】**プロンプトのバージョン管理と段階的ロールアウト**：プロンプトをコードと同じく版管理し、**カナリア（一部トラフィック）→ 指標を監視 → 拡大**、悪化したら**直前の版に即ロールバック**できるようにする。トレースに**プロンプト版とモデルID**を記録しておかないと、回帰の原因を特定できない。
- 【P】**構成の一貫性とゲートウェイ／ルーティング**：複数のプラットフォームや環境（開発・本番）にまたがるとき、モデルID・ベータヘッダー・地域設定のずれが障害の原因になります。LLMゲートウェイを置くと、資格情報をサーバー側に集約し、ルーティング・利用量の計測・ポリシーを1か所で管理できます（Claude Code もゲートウェイ経由で使える）。

**ひっかけ**
- 「新モデルはベンチマークが高いので、評価なしで全トラフィックを切り替える」→ 動作変更で回帰する。評価ゲート＋段階的ロールアウト。
- 「エイリアスを使えば自動で最新になって安全」→ 自動で変わること自体が、評価を経ない変更になる。本番は固定IDで明示的に移行する。

### 1-4. 大規模な検索と知識グラウンディング（Retrieval and Knowledge Grounding at Scale）★
**基礎**：RAG は「取り込み（チャンキング・埋め込み）→ 検索 → リランキング → 生成（引用）」の段階でできています。障害は**段階ごとに切り分けます**。

| 症状 | 疑う段階 | 確認方法 |
|---|---|---|
| 正解の文書が上位k件に入っていない | **検索**（埋め込み、BM25、チャンク境界、インデックスの鮮度） | ゴールデン質問の recall@k |
| 正解は取れているが下位で、使われていない | **リランキング**・コンテキストへの詰め方 | 順位とコンテキスト内位置 |
| 正しいチャンクがコンテキストにあるのに答えが違う | **生成**（指示、グラウンディング） | 引用と根拠の一致（groundedness） |
| 文書を更新したら自信満々に誤答する | **インデックスの更新失敗**・埋め込みモデルの不一致 | 取り込みジョブのログ、版の比較 |
| 型番・エラーコードを取りこぼす | 埋め込みだけの検索 | **ハイブリッド（BM25＋埋め込み）** |

- **Contextual Retrieval**（Anthropic 公式記事）：各チャンクに文書全体から生成した短い文脈説明を前置して、埋め込みと BM25 を作る。上位20件の検索失敗率は、文脈付き埋め込みで −35%、BM25 併用で −49%、リランキングを加えて −67%（記事の検証時点）。知識ベースが小さい（約20万トークン未満）なら、RAG を使わず全文をプロンプトに入れてキャッシュする選択肢もある。
- 【P】**エージェント型検索とRAGのトレードオフ**：エージェントがツールで検索を繰り返す方式は、複雑な質問・最新情報・構造化データに強いが、**レイテンシとトークンが増え、結果がばらつく**。定型の質問が多く、レイテンシ目標が厳しいなら事前インデックスの RAG。ライブ状態（在庫、残高）は検索ではなくツール／API で照会する。
- **グラウンディングの手法**：Citations 機能（文書・**検索結果コンテンツブロック**を渡すと、出典つきで回答）、「根拠がなければ分からないと言う」許可、引用を先に抜き出してから答えさせる、確信度のシグナル（根拠の数・一致度）を出力させてしきい値で人に回す。

**ひっかけ**
- 「回答が不正確なので、より大きなモデルに替える」→ 検索段階の失敗はモデルでは直らない。まず段階を切り分ける。
- 「チャンクを大きくすれば必ず精度が上がる」→ 無関係な内容が混ざり、順位付けが悪化することもある。評価で決める。

## 2. 分野1：高度なエージェントアーキテクチャとオーケストレーション（Advanced Agent Architecture and Orchestration）17%・約10問

### 2-1. マルチエージェントのオーケストレーション（Multi-Agent Orchestration）★
**基礎**：スーパーバイザー（オーケストレーター）が仕事を分解し、ワーカー（サブエージェント）に委任して結果を統合します。サブエージェントは**独立したコンテキスト**で動くので、メインのコンテキストを汚さずに探索できます。

- Anthropic のマルチエージェント調査システム（公式エンジニアリング記事）：リードに Opus 4、サブエージェントに Sonnet 4 を使った構成は、単一の Opus 4 より社内評価で **90.2%** 良かった。一方で、エージェントはチャットの**約4倍**、マルチエージェントは**約15倍**のトークンを使う。性能の分散の **80%** はトークン使用量で説明できた。→ **価値の高い、並列化しやすい広い調査**に向く。依存関係の強い作業や、全員が同じコンテキストを共有すべき作業には向かない。
- ★ **委任の質**：サブエージェントへの指示には、目的・出力形式・使うツールや情報源・**作業範囲の境界**・終了条件を書く。曖昧な委任は、重複作業や範囲外の作業を生む。
- 【P】**コンテキスト分離の境界**：サブエージェントは親の会話履歴を自動では持たない。必要な情報は明示的に渡し、結果は**要約・構造化して**返させる（全文を返すと親のコンテキストを圧迫する）。
- 【P】**エージェント間の障害**：あるワーカーの誤った出力が、そのまま次の判断材料になって増幅される（エラーの連鎖）。対策は、ワーカーの出力スキーマの検証、事実と推測の区別、**統合前の検証ステップ**、ワーカー単位のタイムアウトと部分結果の扱い。
- 【P】**human-in-the-loop と承認のフロー**：取り消しのできない操作（送金、本番デプロイ、外部送信）は、**実行前**に人の承認を入れる。承認待ちで長時間止まる設計なら、状態を永続化して再開できるようにする（2-2）。
- Claude Managed Agents には、1つのセッション内で複数のエージェントを協調させる**マルチエージェントオーケストレーション**の機能がある（ベータ）。

### 2-2. 耐久性のある実行と状態管理（Durable Execution and State Management）【P】★
| 仕組み | 何を保存するか | 使う場面 |
|---|---|---|
| Agent SDK のセッション（continue / resume / fork） | **会話履歴**（ファイルシステムは含まない） | プロセス再起動後の再開（continue）、特定セッションの再開（resume）、元を残した分岐（fork） |
| ファイルチェックポイント（Agent SDK） | エージェントが変更した**ファイル** | 変更の巻き戻し。セッションだけではファイルは戻らない |
| Managed Agents のセッション | サーバー側の状態つきリソース（トランスクリプトは削除するまで残る） | 長時間・非同期の作業。ハーネスと実行環境を自前で持たない |
| メモリツール（`memory_20250818`） | `/memories` 配下のファイル（**クライアント側**で保存先を制御） | 会話をまたいで学んだことを持ち越す。パストラバーサルの防止は実装側の責任 |
| 外部の進捗ファイル・タスクリスト | 何を終えたか、次に何をするか | 長時間エージェントの「次のコンテキストウィンドウ」への引き継ぎ |

- ★ **セッションは会話を、チェックポイントはファイルを**保存する（ひっかけの定番）。
- 【P】**再開可能性**：外部への副作用（メール送信、チケット作成）を伴うステップは、再開時に二重実行しないよう**冪等キー**や完了記録を持つ。
- 【P】**モデルバージョンの変更をまたぐ**：長時間のセッション中にモデルが変わると、思考ブロックの扱いやキャッシュ、ツールの挙動が変わる。セッションの状態は「モデル非依存の形式（進捗ファイル、構造化された状態）」で持つと移行しやすい。キャッシュはモデルごとなので、切り替え直後はキャッシュ書き込みが発生する。

### 2-3. 大規模環境でのアーキテクチャの選択（Architecture Selection at Scale）【P】
- 基本（Building effective agents）：**最も単純で十分な構成から始め、必要なときだけ複雑にする**。ワークフロー（あらかじめ決めた手順：プロンプトチェーン、ルーティング、並列化、オーケストレーター・ワーカー、評価者・最適化者）と、エージェント（モデルが手順を決める）を使い分ける。
- ★ CCDV-P では「**稼働中のシステムを移行すべきか**」を**本番データ**で判断します。

| 本番データの例 | 判断 |
|---|---|
| エージェントのトレースを見ると、9割の実行が同じ3ステップをたどっている | **ワークフローへ寄せる**（コスト・レイテンシ・ばらつきが減る）。残りの1割だけエージェントに回すルーティングも可 |
| 固定ワークフローで、想定外の入力が増え、例外処理の分岐が膨らみ続けている | 例外部分を**エージェントに任せる**ことを検討（評価で品質を確認しながら） |
| エージェントの品質は十分だがコストが予算を超える | まずコンテキスト・キャッシュ・モデルルーティングを見直す（第8章）。構成変更はその後 |

- **ハーネス・フレームワークの標準化**：Messages API で自前ループ（最大の制御）／Agent SDK（Claude Code と同じハーネスをライブラリとして）／Managed Agents（ハーネスと実行環境を Anthropic が運用、長時間・非同期向け）。チームの標準は、**運用要件（状態の保持、ZDR の可否、実行環境の分離、可観測性）**で選ぶ。例：Managed Agents は ZDR の対象外（自己ホスト版を除く）。
- **再利用可能なパターン**：Skills（手順をパッケージ化して共有）、プラグイン、共有 MCP サーバー。共有前の検証（第7章 7-4）とセット。

### 2-4. コンテキストとメモリのアーキテクチャ（Context and Memory Architecture）★
| 手法 | 仕組み | キャッシュへの影響 | 向く場面 |
|---|---|---|---|
| **コンパクション** | 会話を要約して置き換える（オンデマンド／しきい値。ベータ） | 要約で置き換えた以降は新しい接頭辞 | 長い会話を続けたい |
| **ツール結果のクリア**（`clear_tool_uses_20250919`） | しきい値を超えたら古いツール結果を消す | **消すたびにキャッシュが無効化**。`clear_at_least` で一度に十分な量を消す | ツールの多いエージェント |
| 思考ブロックのクリア（`clear_thinking_20251015`） | 以前のターンの思考ブロックを消す／残す（`keep`） | 残せばキャッシュ維持、消せばその地点で無効化 | 推論の連続性とコンテキストのトレードオフ |
| **メモリツール** | 必要な知識をファイルに外出しして必要時に読む | 会話の接頭辞は変えない | 会話をまたいだ知識の持ち越し |
| **ツール検索**（`defer_loading: true`） | 大量のツール定義を最初は読み込まず、検索で必要なものだけ出す | ツール定義の常時展開を避ける | ツール数が多い（大規模なツールカタログ） |
| **会話途中の system メッセージ** | `role: "system"` のメッセージを会話の途中に追加 | **キャッシュ済みの接頭辞を壊さずに**指示を変えられる（対応モデルのみ） | 途中でポリシーやモードを切り替える |
| 会話途中のツール変更（`tool_addition` / `tool_removal`、ベータ） | `tools` 配列を編集せずにツールを追加・削除 | `tools` の編集はキャッシュ全体を無効にするが、これなら維持 | 途中で使えるツールを変える |

- ★ 「**会話の途中で指示を変えたいので、トップレベルの `system` を書き換える**」→ キャッシュが無効になる。キャッシュを保つなら会話途中の system メッセージ（試験ガイドの「キャッシュを損なわずに指示を変更する」）。
- 【P】判断軸は「**コンテキストの上限**」と「**コストの上限**」のどちらに先に当たるか。前者はコンパクション・クリア、後者はキャッシュを壊さない手法の優先、と考える。

**ひっかけ**
- 「コンテキストが溢れそうなので、より大きいコンテキストウィンドウのモデルに替える」→ コストとレイテンシが増え、情報の埋没（context rot）も解決しない。
- 「全ツールの説明を短く要約して残す」→ 使わないツールは外す／遅延読み込みが先。

## 3. 分野3：オブザーバビリティと本番環境のモニタリング（Observability and Production Monitoring）12%・約7問【P：CCDV-F にない分野】

### 3-1. テレメトリと計装（Telemetry and Instrumentation）★
**基礎**：LLMシステムの失敗の多くは **HTTP 200 の誤答・拒否・長さ切れ**なので、HTTP のエラー率だけでは見えません。

| 記録すべきもの | 目的 |
|---|---|
| トレースID／親子関係（エージェントループ → LLM呼び出し → ツール呼び出し） | マルチステップの因果をたどる |
| モデルID、プロンプト版、ツール定義の版、effort | 回帰が「何を変えたときか」を特定 |
| `stop_reason`、`stop_details`（拒否のカテゴリ） | 長さ切れ・拒否を独立したシグナルにする |
| `input_tokens`、`output_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens` | コストとキャッシュ効率 |
| TTFT と総レイテンシ、ツールごとの所要時間 | レイテンシの内訳 |
| 検索されたチャンクのID・スコア、引用 | グラウンディングのトレーサビリティ |
| `request-id`（エラー本文では `request_id`） | Anthropic サポートへの問い合わせ |

- **Claude API の OpenTelemetry トレース**（ベータ）：Messages API のリクエスト、ツール使用、Managed Agents のセッションのスパンを出力できる。**コンテンツモード**で、プロンプトと応答を含めるか（Full content）、メタデータだけにするかを選ぶ。
  - ★ **ZDR でも Full content は使える**（Messages API では、API は送信先に渡すまでメモリにだけ保持）。ただし保存先の監視基盤のアクセス・保持設定が組織の要件を満たすか確認する。HIPAA・FERPA・K-12 のデータ制限がある組織では、送信先にはメタデータだけが出力される。
- **キャッシュ診断（cache diagnostics）**：リクエストに `diagnostics` オブジェクトを付け、前の応答の `id` を渡すと、接頭辞がどこで分岐したか（モデル、system、tools、メッセージ履歴）を教えてくれる。予想外のキャッシュミス（タイムスタンプの混入、ツールの並び順の変化など）の原因特定に使う。
- **Claude Code の監視**：`CLAUDE_CODE_ENABLE_TELEMETRY=1` で OpenTelemetry のメトリクスとイベントを出力。**ユーザープロンプトの内容（`OTEL_LOG_USER_PROMPTS`）、ツールの詳細（`OTEL_LOG_TOOL_DETAILS`）などは既定で記録しない**（オプトイン）。

**ひっかけ**
- 「デバッグのために全プロンプトと応答を無期限に平文で保存」→ プライバシー・保持要件に反する。コンテンツモード、マスキング、保持期間、アクセス制御で設計。
- 「ZDR だからトレースに内容は一切出せない」→ Claude API の OTel は ZDR でも Full content を選べる（要件次第）。

### 3-2. 本番環境のモニタリングとアラート（Production Monitoring and Alerting）
- **SLI の例**：可用性（エラー率）だけでなく、**TTFT の p95**、タスク成功率、拒否率、長さ切れ率、評価器による品質スコア（サンプリング）、1リクエストあたりのコスト、キャッシュヒット率。
- **SLO とアラート**：エラーバジェットの消費速度（burn rate）でアラートし、単発のスパイクで鳴らさない。コストは**テナント別・機能別**のダッシュボードで、異常な増加（ループ暴走、キャッシュ崩壊）を検知する。
- ★【P】**モデル更新後のドリフト**：モデル移行やプロンプト変更の直後は、品質スコア・出力長・拒否率・ツール呼び出し回数を**変更前のベースライン**と比べる。変更をデプロイイベントとしてダッシュボードに重ねる。
- 異常な使用状況：特定のキーやテナントからの急増は、漏えい・悪用・暴走ループの兆候。

### 3-3. 大規模なトレース分析（Trace Analysis at Scale）【P】
- 個々のトレースを読むだけでは、**頻度の低い系統的な問題**は見えません。手順は「**サンプリング → 集計 → 障害コホートの比較**」。
- サンプリング：一様サンプリングに加え、**失敗・高コスト・高レイテンシ・低評価のトレースを優先的に残す**（テールベースサンプリング）。ただし比率を出すときは、偏ったサンプルから全体の割合を推定しない。
- 集計：モデル版・プロンプト版・テナント・ツール・入力の種類で切って、失敗率の差を見る。
- **障害コホート分析**：「失敗した実行」と「成功した実行」で、属性（特定ツールのエラー、入力言語、文書の種類、ターン数）の分布を比べる。例：失敗の7割が「同じツールのタイムアウトのあと」に集中している → ハーネスのタイムアウト処理を疑う。

## 4. 分野5：評価エンジニアリングと品質保証（Evaluation Engineering and Quality Assurance）12%・約7問

### 4-1. 評価システムの設計（Evaluation System Design）★
**基礎**（Define success criteria and build evaluations）：成功基準は**具体的で測定可能**にし、評価は**タスクに即した**量の多い自動評価を優先する。採点方法はコード（完全一致など）→ LLM による採点 → 人の採点の順に、速さと拡張性が下がる。

| 構成要素 | 役割 |
|---|---|
| **ゴールデンセット** | 正解つきの代表的なケース。本番分布とエッジケースの両方を含める |
| **回帰スイート** | 過去の障害・インシデントを再現するケース（6-2 で追加） |
| **動作チェック** | 形式、禁止事項、ツール呼び出しの順序など、決定的に判定できる性質 |
| **CI/CD の評価ゲート** | プロンプト・モデル・エージェントの変更ごとに自動実行し、基準を下回ればリリースを止める |
| 検索の指標 | 適合率・再現率（recall@k）、**グラウンディング**（回答が根拠に支えられているか） |

- 【P】**リリース基準**：平均スコアだけでなく、「重要なスライスで悪化していない」「安全性のケースで0件の違反」など、**スライス別・必須条件**を組み合わせる。
- 【P】**非決定性への対応**：エージェントは実行ごとに結果がばらつくので、1回の実行で合否を決めない。**複数回試行して成功率（pass@k、pass^k の考え方）**で見る。インフラの揺らぎ（タイムアウト、資源不足）が成績に混ざらないよう、環境のノイズも管理する（Anthropic の記事「Infrastructure noise in agentic coding evals」）。
- ★【P】**スイートの妥当性の維持**：
  - **汚染（contamination）**：評価ケースがプロンプトの例や学習・チューニングの材料に混入 → 点数が実力以上に出る。評価用と開発用を分ける。
  - **飽和（saturation）**：ほぼ全員が満点 → 改善も回帰も見分けられない。難しいケースを追加する。
  - **カバレッジ不足**：本番で起きる入力（新機能、新しい言語、新しい文書形式）がスイートにない。本番トレースから定期的に追加する。

### 4-2. LLM-as-judgeのエンジニアリング（LLM-as-Judge Engineering）【P】★
- ★ **公式サンプル2の核心**：ジャッジがゲートを持つ前に、**人間のラベルとの一致度を測ってキャリブレーション**する。一致が不十分なうちはゲートの権限を持たせない。
- **位置バイアス**：先に出た（または後に出た）応答を選びやすい。対策は**順序のランダム化・入れ替えて2回採点**し、結果が入れ替わるものは引き分けとして扱う。
- **ルーブリック設計**：観点ごとに具体的な基準と例を書く。採点の前に根拠を書かせる。曖昧な「良い／悪い」ではなく、判定可能な条件にする。
- **評価者間信頼性**：人どうしの一致度（Cohen's κ など）を先に測る。人どうしでも一致しない基準は、ジャッジにも再現できない。
- **ジャッジのドリフト**：ジャッジのモデルを更新すると、同じ応答への採点が変わる。ジャッジのモデルIDを固定し、更新時は人間ラベルのセットで**再キャリブレーション**してから使う。
- そのほかのバイアス：長い応答を好む（冗長性バイアス）、自分と同じモデルの出力を好む（自己選好）。

**ひっかけ**：「ジャッジをより大きなモデルに替える」「しきい値を下げる」は、公式サンプル2で明示的に否定された選択肢と同じ型です。

### 4-3. オンラインでの品質測定（Online Quality Measurement）
- **ライブトラフィックのサンプリング評価**：本番の一部を非同期でジャッジや人が採点し、オフライン評価で見えない分布の変化をつかむ。
- **A/Bテスト**：ランダムに割り付け、事前に決めた主要指標とガードレール指標（コスト、レイテンシ、拒否率）で判断する。途中で何度も結果を見て止めると、偽陽性が増える。
- **フィードバックループ**：👍👎、修正、再生成、エスカレーションなどの暗黙のシグナルを集め、評価セットに還元する。ただし声を上げる利用者に偏る。
- ★ **タスクの種類に合った指標**：

| タスク | 主な指標 |
|---|---|
| 抽出 | フィールド単位の完全一致・F1、スキーマ適合率 |
| 生成（要約・文章） | ルーブリックによるジャッジ採点（キャリブレーション済み）、人の評価 |
| エージェント型 | **タスク成功率**（最終状態の検証）、ステップ数、コスト、ツールエラー率 |
| 検索に根拠を置くもの | 検索の再現率・適合率、**グラウンディング率**、引用の正確さ |

## 5. 分野7：ランタイムガードレールと本番環境のセキュリティ（Runtime Guardrails and Production Security）11%・約7問

### 5-1. ランタイムガードレールシステム（Runtime Guardrail Systems）★
**基礎**：ガードレールは**多層**で考えます（入力 → モデル → ツール実行 → 出力）。プロンプトだけに頼らず、**モデルの外で決定的に強制する**層を必ず持ちます。

| 層 | 例 | 性質 |
|---|---|---|
| 入力 | 軽量モデルによる事前スクリーニング、PII のリダクション | 確率的。偽陽性・偽陰性のチューニングが必要 |
| システムプロンプト | 役割と禁止事項の明示 | **強制力はない**（突破されうる） |
| ツール実行の前 | **フック（PreToolUse でブロック）**、許可リスト、承認ゲート、権限モード | **決定的**。取り消しのできない操作はここで止める |
| 実行環境 | **サンドボックス**（ファイルシステムとネットワークの制限）、コンテナ、プロキシ経由の通信 | ツールや Web へのアクセスを許しつつ、本番システムを露出しない |
| 出力 | PII の検出、ポリシー違反の検出、構造の検証 | 確率的なものと決定的なものの組み合わせ |

- ★ **取り消しのできない操作には決定論的な強制**：削除、送金、外部送信、本番への書き込みは、フックやアプリ層の検査で止める。モデルに「慎重に」と頼むのはガードレールではない。
- Claude Code のフック：`PreToolUse` はツール実行前に走り、**ブロックできる**（`permissionDecision: "deny"`、または終了コード2）。管理設定で `allowManagedHooksOnly` 等を使えば、利用者がフックを外せないようにできる。
- **拒否の処理と安全のためのフォールバック**：拒否（`stop_reason: "refusal"`）を利用者にどう見せるか、どの経路で再試行・人へ回すかを決めておく（1-1）。
- 【P】**偽陽性と偽陰性のチューニング**：フィルターを厳しくすると正当な依頼まで止まり（業務が止まる）、緩めると攻撃が通る。**リスクの高い操作ほど偽陰性を嫌う**（承認に回す）、リスクの低い操作は偽陽性を減らす、とリスクに応じて調整し、レッドチームと本番のログで測る。

### 5-2. エージェント型システムの脅威対策と敵対的テスト（Threat Defense and Adversarial Testing for Agentic Systems）【P】★
- ★ **高リスクな組み合わせ**（試験ガイドの明記）：**プライベートデータへのアクセス ＋ 信頼できない入力 ＋ 外部との通信**。この3つがそろうと、インジェクションでデータを外に出せる。**どれか1つを断つ**のが最も確実（公式サンプル3：送信先の許可リスト・外部送信の承認・データアクセスの範囲限定）。
- 攻撃の種類：
  - **プロンプトインジェクション**（直接／間接：Webページ、チケット、メール、ファイルに埋め込まれた指示）
  - **ツールポイズニング**：MCP サーバーのツール説明やツールの結果に悪意ある指示を仕込む。信頼できないサーバーの追加や、説明の無断変更（rug pull）に注意。
  - **メモリポイズニング**：永続メモリに悪意ある内容を書き込ませ、後の会話で発動させる。メモリへの書き込みの検証・出所の記録・範囲の分離。
  - **データ流出の経路**：メール・Webhook だけでなく、**URL のクエリ文字列、画像の読み込み、外部へのリクエスト**も経路になる。ネットワークの外向き通信をプロキシで許可リスト化する。
  - **安全でない自律性**：承認なしで連続実行できる範囲が広すぎる、停止条件がない。
- **多層防御**：信頼できない内容を指示と分けて渡す（タグで区切る）、ツールの権限を最小にする、外向き通信を制限する、取り消しのできない操作に承認を入れる、監査ログを残す。
- **レッドチーム演習の設計**：脅威モデル（資産、攻撃者、経路）から攻撃シナリオを作り、成功率を測る。見つかった攻撃は**回帰評価に追加**する。参照枠組みは **OWASP Top 10 for LLM Applications** と **NIST AI RMF とその生成AIプロファイル**。
- **安全な MCP 構成**：信頼できるサーバーだけを許可リストで許可する、ツール説明の変更を監視する、リモートサーバーは OAuth で認可しトークンを転送しない。

**ひっかけ**（公式サンプル3の誤答の型）
- 「システムプロンプトの警告を強める」→ 強制力のある境界ではない。
- 「effort を下げる」→ 能力は残るので経路は閉じない。
- 「送信をすべてログに残す」→ 検知であって防止ではない。

### 5-3. 大規模環境でのID、シークレット、監査（Identity, Secrets, and Audit at Scale）【P】
- ★ **ワークロードIDフェデレーション（WIF）**：ワークロードが自社の IdP（AWS IAM、Google Cloud、GitHub Actions などの OIDC プロバイダー）から得た**短命の OIDC トークン**を提示し、Anthropic が Console で設定した信頼ルールで検証して、**サービスアカウントに紐づく短命のアクセストークン**を返す。**静的な `sk-ant-...` キーを CI に保存・ローテーションする必要がなくなる**。
  - 構成要素：サービスアカウント（`svac_...`、人ではないID）、フェデレーション発行者（`fdis_...`、IdP の登録）、フェデレーションルール（どのクレームならどのサービスアカウントとして振る舞えるか）。
  - 注意：WIF の強さは上流の IdP の強さに依存する。クレームの条件（リポジトリ、ブランチ、環境）を狭く書く。
  - ワークスペースAPIキーは「資格情報そのもの」、サービスアカウントは「資格情報を**持つ**ID」。ワークロードごとにサービスアカウントを分けると監査しやすい。
- **シークレット管理**：APIキーをプロンプト・リポジトリ・エージェントの環境に置かない。**エージェントの外のプロキシで資格情報を注入**すれば、エージェントは資格情報を見ずに API を呼べる（Agent SDK の安全なデプロイのガイド）。
- **最小権限のツール権限**：エージェントの役割ごとに、使えるツール・操作（読み取りのみ等）・データ範囲を絞る。共有のサービスアカウントで全ユーザーを代行させない（利用者に紐づく委譲認可にする）。
- **監査ログ**：セキュリティに関わるエージェントの操作（誰の依頼で、どのIDで、どのツールを、どの引数で、承認者は誰か）を、改ざんできない形で残す。

## 6. 分野4：高度なデバッグとインシデント対応（Advanced Debugging and Incident Response）10%・約6問

### 6-1. 複雑な障害の診断（Complex Failure Diagnosis）【P】★
- ★ 発生源を **モデルの出力／エージェントハーネス／ツール／データ** の4つから切り分ける。

| 証拠 | 疑う発生源 |
|---|---|
| ツールは正しい結果を返し、コンテキストにもあるのに、モデルが違う結論を出す | **モデルの出力**（指示、プロンプト、モデル変更） |
| ツールの結果がコンテキストに入っていない・切り詰められている・順序が崩れている | **ハーネス**（結果の受け渡し、コンテキスト編集の設定、タイムアウト処理） |
| ツールがエラーや古いデータを返している（`is_error` の扱いも含む） | **ツール** |
| 検索結果に正解の文書がない、文書自体が古い・間違っている | **データ**（取り込み、インデックス） |
| `stop_reason: "refusal"` が特定の入力の種類に集中 | **拒否という障害クラス**（カテゴリ別に計測し、フォールバックや経路を設計） |

- **マルチターン・マルチエージェントの障害**：最初に誤りが入ったステップ（起点）を探す。最終出力だけを見て直すと、起点のワーカーの誤りが残る。
- **非決定的な障害**：同じ入力でも成功・失敗が分かれるなら、1件の再現にこだわらず、**複数回実行した失敗率**と、失敗した実行に共通する属性（3-3 のコホート分析）で調べる。
- 「何が変わったか」から探す：モデルID、プロンプト版、ツールのスキーマ、データの更新、SDK・ハーネスの版。Anthropic のポストモーテム記事（Claude の品質問題の報告）でも、**複数の原因が重なって症状が見えにくくなった**ことが示されている。
- ツール呼び出しのトラブルシューティング（公式ドキュメント）：ツールの説明が曖昧、スキーマが不適切、`tool_result` の順序や形式の誤り（`tool_use` の直後に対応する `tool_result` が必要）などを確認する。

### 6-2. インシデント対応と学習ループ（Incident Response and Learning Loops）【P】
- **トリアージ**：影響範囲（どのテナント・機能・割合）と深刻度を先に把握する。
- ★ **緩和を先に、根本原因の調査は後に**：直前の変更（プロンプト・モデル・設定）が疑わしいなら、まず**ロールバック**や機能フラグで影響を止め、それから原因を調べる。プロンプトを本番で直接いじりながら調べない。
- **コミュニケーション**：影響を受ける利用者・関係者に、分かっていること・分かっていないこと・次の更新時刻を伝える。
- **学習ループ**：インシデントの入力を**回帰評価**に追加 → 検知できなかったなら**モニタリングの対象**を追加 → **非難しないポストモーテム**で、寄与要因と再発防止策（誰が・いつまでに）を残す。
- Claude を使った運用支援（準備コース）：アラートのトリアージ、P1 のときだけ人を呼ぶエスカレーション、ポストモーテムの下書き。ただし最終判断と公開前の確認は人が行う。

**ひっかけ**
- 「原因が分かるまでロールバックしない」→ 影響が続く。緩和が先。
- 「再発防止はプロンプトに注意書きを足すことにする」→ 回帰評価とモニタリングに落とし込まないと再発を検知できない。

## 7. 分野8：ソフトウェア提供のためのエージェントフリート運用（Agent Fleet Operations for Software Delivery）10%・約6問【P】

### 7-1. エンジニアリング作業のための並列エージェントオーケストレーション（Parallel Agent Orchestration for Engineering Work）
- **worktree で分離**：`claude --worktree <name>`（`-w`）で、`.claude/worktrees/<name>/` に新しいブランチ（`worktree-<name>`）の作業ツリーを作って起動する。並列セッションの変更が衝突しない。worktree は新しいチェックアウトなので、依存関係のインストールや `.env` などの持ち込み（`.worktreeinclude`）が必要。
- **タスク分解**：互いに触るファイルが重ならない単位に分ける（モジュール、レイヤー、テストの追加など）。共通の型やインターフェースを先に決めてから並列化する。
- **マージとコンフリクトの戦略**：小さく頻繁にマージする、同じファイルに触る作業は直列にする、マージ後に全体のテストを回す。
- **フリートのテレメトリから障害モードを診断**：エージェントごとの成功率、リトライ回数、コスト、所要時間を集計し、「特定のリポジトリやタスクの種類で失敗が集中」「全エージェントが同じ不安定なテストで止まる」などのフリート全体の問題を見つける。

### 7-2. 検証とAIコードレビューの運用（Verification and AI Code Review Operations）★
- 前提：**生成のペースがレビューのペースを上回る**と、人のレビューがボトルネックになり、確認の質が落ちる。
- ★ **シャドーモードで導入 → 人のレビューとのキャリブレーション → マージゲート化**（試験ガイドの明記）。最初からAIレビューに合否の権限を持たせない。AIの指摘と人の判断の一致・見逃し・誤検知を測ってから、ゲートにするかを決める（4-2 のジャッジと同じ考え方）。
- Claude Code の **Code Review**（Team / Enterprise）：複数のエージェントが PR を読み、検証ステップで誤検知を落とし、重大度順にインラインコメントする。**レビューは PR を承認もブロックもしない**（マージの判断は人に残る）。**ZDR や HIPAA 構成の組織では使えない**。ローカルでは `/code-review` も使える。
- **検証のフィードバックループ**：テスト、型チェック、リンター、スクリーンショットの比較など、エージェントが自分で結果を確かめられる手段を与える（準備コース「Give Claude a feedback loop」）。
- **人による監督の設計**：リスクの高い変更（認証、課金、データ移行）は必ず人がレビューする、など範囲で分ける。

### 7-3. 無人実行とイベント駆動のエージェント運用（Unattended and Event-Driven Agent Operations）
- 実行形態：**目標駆動**（ゴールに向けて長時間動く）、**スケジュール駆動**（定期タスク）、**イベント駆動**（CI の失敗、アラート、Issue の作成を受けて動く。例：CI/CDインシデントの一次対応）。
- ヘッドレス実行：`claude -p "<指示>"`、`--allowedTools` で自動承認するツールを限定、`--output-format` で構造化出力。`--bare` は hooks・skills・MCP・CLAUDE.md などの自動検出を省き、スクリプトや SDK からの呼び出しに推奨される。
  - ★ 注意：`--bare` なしの `-p` は、プロジェクトの `.claude/settings.json` のフックや `.mcp.json` のサーバーを、**ワークスペースの信頼確認なしで**読み込む。信頼していないリポジトリで無人実行するときは要注意。
- **チェックポイント・通知・エスカレーション**：長時間の実行は途中経過を保存し、失敗時は再開できるようにする。完了・失敗・判断が必要な場面で人に通知し、権限を超える操作（本番デプロイ等）は人へエスカレーションする。
- 無人実行の検証：結果を鵜呑みにせず、テスト結果・差分・ログで確認できる形で報告させる（準備コース「Trust it: Verifying unsupervised runs」）。

### 7-4. 組織全体でのコーディングエージェントの構成（Organization-Wide Coding Agent Configuration）★
- **設定の優先順位**（高い順）：**管理設定（managed settings）** → コマンドライン（`--settings`）→ プロジェクトのローカル設定（`.claude/settings.local.json`）→ 共有プロジェクト設定（`.claude/settings.json`）→ ユーザー設定（`~/.claude/settings.json`）。管理設定は `managed-settings.json`、MDM／OSのポリシー、claude.ai の管理コンソールからのサーバー管理設定などで配布し、**利用者の設定では上書きできない**。
- **MCP の許可リスト**：`allowedMcpServers` / `deniedMcpServers`（**拒否リストが優先**）、`managed-mcp.json` で固定のサーバー群だけを配布（空にすれば MCP を無効化）。
- **テレメトリ**：管理設定で OpenTelemetry の送信先を組織として指定し、利用状況・コストを集計する（3-1）。
- **ゲートウェイのルーティング**：LLMゲートウェイ経由にすると、提供元の資格情報をサーバー側に置き、利用者はゲートウェイの資格情報だけを持つ。利用量の計測・予算・ルーティングを一元化できる。
- **共有のガバナンス**：プロンプト、Skills、MCP サーバー、プラグインをチーム間で共有するときは、**品質（評価・レビュー）と安全性（権限、外部通信、出所）の基準**を満たしたものだけを公開する。プラグインのマーケットプレイスは管理設定で制限できる（`strictKnownMarketplaces` など）。

## 8. 分野6：大規模環境でのコストとレイテンシの最適化（Cost and Latency Optimization at Scale）8%・約5問

### 8-1. 大規模環境でのコストアーキテクチャ（Cost Architecture at Scale）
- **コストのモデリング**：1リクエストのコスト ＝ 未キャッシュ入力 × 入力単価 ＋ キャッシュ書き込み × 書き込み単価 ＋ キャッシュ読み取り × 読み取り単価 ＋ 出力 × 出力単価。これにリクエスト数（テナント別・機能別）を掛けて予測する。**エージェントは出力と反復回数**でコストが膨らみやすい。
- **プロンプトキャッシュ**（2026-11-20時点のドキュメント）：既定の寿命は5分（使うたびに無料で延長）、1時間も選べる。書き込みは基本入力単価の1.25倍（5分）／2倍（1時間）、読み取りは原則10%（モデルにより2.5%・5%）。最大4つのブレークポイント、**接頭辞は tools → system → messages の順**、モデルごとの最小トークン数未満は**エラーなしでキャッシュされない**。キャッシュは組織間で共有されず、Claude API などではワークスペース間でも分離される。
  - ★ キャッシュを壊す典型：ツール定義の変更（全体が無効）、system の先頭にタイムスタンプ、ツールの並び順の非決定性、`tool_choice`・画像の有無・思考パラメーター・effort の変更（メッセージ部分が無効）。原因の特定には**キャッシュ診断**（3-1）。
- **モデルルーティングとカスケード**：簡単な入力は小さいモデル、難しい入力だけ上位モデルへ。カスケード（小さいモデルで答え、自信がないときだけ上位へ）は、**エスカレーションの判定基準を評価で検証**しないと品質が落ちる。Advisor ツール（高速な実行役のモデルに、上位モデルが途中で助言する）という選択肢もある。
- **バッチとリアルタイムの経済性**：待てる処理は Batches（50%オフ）。キャッシュとの併用も可能。ただし24時間以内に終わらない可能性と、ZDR の対象外であることを考慮する。
- **テナントごとの予算の適用**：テナント単位で使用量を計測し、上限に近づいたら警告・縮退・停止をアプリ層で強制する。組織・ワークスペースの支出上限は**最後の安全網**（到達すると全体が止まる）なので、テナントの予算管理の代わりにはならない。

### 8-2. レイテンシエンジニアリング（Latency Engineering）
| 症状 | 効く手段 |
|---|---|
| 最初の文字が出るまで遅い（**TTFT**） | **ストリーミング**（体感を改善）、**プロンプトキャッシュ**（長い接頭辞の処理を省く）、入力の削減 |
| 全体の完了が遅い（総レイテンシ） | 出力を短くする、**effort を下げる**、小さいモデル、**並列ツール実行**、作業の並列化 |
| ツール呼び出しが逐次で遅い | **並列ツール呼び出し**（独立した呼び出しは1ターンでまとめて実行し、結果をまとめて返す） |
| ツール入力の生成中に UI が固まる | **ツール呼び出しのストリーミング**（`input_json_delta` で部分的な JSON を受け取る） |

- ★ **TTFT と総レイテンシを区別する**：ストリーミングは TTFT（体感）を改善するが、生成の総時間は減らさない。総時間が SLO を超えているのに「ストリーミングにする」は的外れ。
- **キャッシュのチェックポイント設定**：変わらない部分の末尾にブレークポイントを置く。会話が伸びるときは自動キャッシュ（トップレベルの `cache_control`）でブレークポイントを前に進められる。
- **effort**：`low` / `medium` / `high` / `xhigh` / `max`（モデルにより対応が異なる）。`output_config.effort` で指定。既定値はモデルによって違う。effort の変更もキャッシュのメッセージ部分を無効にしうる。
- ストリームが途中で切れたら、受け取った部分を保存して続きから再開する（4.6以降のモデルでは、続きを書くよう指示するユーザーメッセージを追加する方式）。ツール使用と思考のブロックは部分的に回復できない。

### 11-3. 頻出ひっかけの総復習（★）
| ひっかけ | 正しい考え方 |
|---|---|
| 失敗の種類を区別せず、リトライ回数・バックオフを増やす | レート制限・長さ切れ・拒否・支出上限で**分岐**する |
| 拒否（refusal）を同じモデルにリトライする | 再び拒否されやすい。**別モデルのフォールバック**か安全性の処理経路へ。拒否は HTTP 200 なので**独立したシグナル**として計測 |
| 支出上限の429を待てば直ると考える | `retry-after` がなく、上限変更か月替わりまで回復しない |
| `max_tokens` を下げてレート制限を回避 | OTPM は実際の生成量で数える。ITPM が律速ならキャッシュ（キャッシュ読み取りは ITPM に数えない） |
| 上限内なのに429 → 上限を上げる申請だけ | **ランプ制限**（急増・バースト）。徐々に増やす |
| 新モデルを評価なしで全面切り替え | 同じ評価スイートで比較 → 段階的ロールアウト → ロールバック手段 |
| 検索の失敗をモデルの変更で直す | 段階（取り込み・検索・リランキング・生成）で切り分ける |
| セッションの resume でファイルも元に戻る | セッションは**会話**、ファイルは**チェックポイント**で戻す |
| 途中で指示を変えるために `system` を書き換える | キャッシュが無効になる。**会話途中の system メッセージ** |
| ツール定義を頻繁に変える | キャッシュ全体が無効。遅延読み込み・会話途中のツール変更 |
| 監視は5xxとエラー率で十分 | LLMの失敗の多くは HTTP 200（誤答・拒否・長さ切れ） |
| ZDR だからトレースに内容は出せない | Claude API の OTel は ZDR でも Full content を選べる（保存先の要件は別途確認） |
| LLM-as-judge をすぐゲートに使う／大きいモデルにすれば直る | 人間ラベルでキャリブレーション、位置バイアス対策、一致するまでゲート権限なし |
| 評価スイートは一度作れば十分 | 汚染・飽和・カバレッジ不足を継続的に管理 |
| プロンプトに禁止事項を書けば流出は防げる | **送信先の許可リスト・承認・データ範囲の限定**などモデルの外の制御 |
| 送信をすべてログに残す | 検知であって防止ではない |
| 静的APIキーを CI のシークレットに保存してローテーション | **ワークロードIDフェデレーション**で短命トークン |
| 原因が分かるまでロールバックしない | 緩和（ロールバック）が先、根本原因の調査は後 |
| AIコードレビューに最初からマージの合否を任せる | シャドーモード → 人とのキャリブレーション → ゲート化 |
| 利用者の設定で管理設定を上書きできる | 管理設定が最優先。MCP は拒否リストが優先 |
| ストリーミングで総レイテンシが下がる | 下がるのは TTFT（体感）。総時間は出力量・effort・並列化で |
| 支出上限があるのでテナント別の予算管理は不要 | 組織の上限は全体を止める最後の安全網。テナント予算はアプリ層で強制 |
